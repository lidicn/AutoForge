# `fn` 节点设计评估报告（v1.0.0 交付点 3）

> 结论先行：**1.x 不引入 `fn` 节点（自定义代码），也不嵌入 CEL / Lua 解释器**；
> 表达力经 operand 级白名单函数（v1.0.0 已交付）继续按"声明式 + 纯函数"路线扩充。
> 本报告给出论证、沙箱边界分析与"若未来必须引入"的准入条件。

---

## 1. 背景与问题

IR §12.7「语言阶梯」把表达力按风险分层：

| 层级 | 能力 | 状态 |
|---|---|---|
| 声明式触发/条件 | `on` / `if` / 比较 + 一元状态算子 | G1 起 |
| 声明式变量 | `set`（字面量 / 实体值 / 变量引用） | G1 起 |
| **白名单纯函数** | operand 级 `{"fn": ...}`（math/string/time/list） | **v1.0.0 ✅** |
| `fn` 节点 | 图内自定义代码（`{"lang": "cel"|"lua"|"py", "src": ...}`） | **保留位** |

`fn` 节点的诉求场景：Agent 想表达"无法用比较+函数拼出的计算"（复杂日期运算、字符串解析、
跨实体聚合）。问题是：**引入任意代码后，AutoForge 的安全模型是否还成立？**

## 2. 三个候选方案评估

### 方案 A：CEL（Common Expression Language，cel-python）

| 维度 | 评估 |
|---|---|
| 沙箱 | 设计上无 IO、无循环、强类型、可配执行预算；`cel-python` 实现质量可用 |
| 与现有 IR 的契合 | 与 JSON 表达式树同构（都是"算子树"），可平移 |
| 成本 | 新增依赖（约 2MB+）；Agent 需学一门新 DSL；错误信息多一层包装 |
| 致命点 | **双表达式体系**：`if.expr`（JSON 树）与 `fn(cel)` 并存后，静态扫描器要同时分析两种语法，`collect_entity_refs` / `UNDECLARED_VAR` / 实体 ACL 全部要做 CEL 解析——安全闸复杂度翻倍，而收益只是"写起来短一点" |

### 方案 B：Lua（lupa / 沙箱化 LuaJIT）

| 维度 | 评估 |
|---|---|
| 沙箱 | 历史包袱重：`os` / `io` / `debug` 库、字节码加载、`getfenv` 时代差异；沙箱逃逸 CVE 频发（智能家居领域 HA 官方也曾多次收紧 Lua 沙箱） |
| 与现有 IR 的契合 | 命令式脚本 ≠ 声明式图：静态扫描无法从源码可靠提取**实体引用清单**（白名单/ACL 失效） |
| 成本 | C 扩展依赖，NAS/容器/Windows 三端构建成本；调试体验差 |
| 致命点 | **静态不可分析**。AutoForge 的三道闸（静态扫描 / ACL / L3 白名单）全部建立在"图是可静态分析的声明式数据"之上；脚本打破这一前提 |

### 方案 C：现状路线（声明式白名单函数，已交付）

| 维度 | 评估 |
|---|---|
| 沙箱 | 天然最强：函数是**代码评审过的 Python 纯函数**，无 eval、无 IO、无时钟 |
| 可分析性 | 实体/变量引用可静态收集（`collect_entity_refs` 深入 fn 参数），ACL/白名单照常工作 |
| 资源可控 | 深度 32 / 节点 256 双硬顶，编译期与运行期同一套，DoS 面为零 |
| 表达力边界 | 只能组合白名单内的函数；缺的函数按需补（纯函数 + 测试 + schema 无需改） |

**结论**：方案 C。CEL 的"双表达式体系"成本与 Lua 的"静态不可分析"都直接削弱安全模型，
而白名单函数已覆盖 1.x 的真实诉求（数值规整、字符串归一、时间窗口判断）。

## 3. 沙箱边界分析（若引入 `fn` 必须满足的硬条件）

1. **可静态分析**：执行前必须能从 `src` 提取出与 JSON 树等价的引用清单（实体/变量）；
   提取失败即拒绝（fail-closed）。
2. **无 IO / 无时钟 / 无网络**：解释器启动时移除全部副作用入口；求值只喂快照 + vars。
3. **资源上限**：与 `MAX_EXPR_DEPTH` / `MAX_EXPR_NODES` 同级的时间/步数/内存预算，超限即软失效（走 `on_error`）。
4. **L3 关系**：`fn` 节点本身**必须按 L3 处理**——即使沙箱完备，代码评审不可自动化，
   与"删除类/外网"同级走人工确认 + 白名单（这是把"代码进图"的信任成本显式化的唯一途径）。
5. **版本可回放**：`fn` 源码进 Graph（可 JSON 化红线），diff 可见、归档可回放——不能引用外部文件。

## 4. 与 L3 安全闸的关系

当前 L3（`classify_action`）拦截的是**动作**（高危 domain / 删除类 / http）。`fn` 节点不产生
动作，但它产生**不可静态证明的逻辑**——比 L3 动作更难审计。因此若未来引入，准入顺序必须是：

```
静态引用提取 → 沙箱资源预算 → L3 级人工确认 → canary 灰度（G4）→ 才可 auto 带自主运行
```

即：`fn` 节点的置信度**永久封顶在 ask/shadow 档**（不进 auto），除非后续证据体系能覆盖代码级验证。

## 5. 最终结论

- **不引入** CEL / Lua / 任意代码 `fn` 节点；`fn` 保留位继续由静态扫描 `RESERVED_NOT_IMPLEMENTED` 拦截。
- 表达力走**白名单函数扩充**路线（v1.0.0 已交付 24 个纯函数，schema / 扫描器 / 运行时三端打通）。
- 复核触发条件（满足其一重启评估）：① 出现 ≥3 个真实自动化因缺函数无法表达且无法用
  `set` 拆步解决；② 出现可信的、可静态分析的沙箱运行时且满足 §3 全部五条硬条件。
