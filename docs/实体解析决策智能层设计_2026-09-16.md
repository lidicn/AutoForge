# 实体解析决策智能层设计（供 AutoForge 复用 / 对齐）

> **来源**：AutoFlow v1 实体解析架构评估（2026-09-16，代码取证 `gateway.py` / `state.py` / `mcp_server.py`）。
> **转发目的**：AutoFlow v1 已落地"网关侧机械化 NL→entity_id 解析"并验证有效；其 v2.3.0 计划补"决策智能层"（设备归并 / 集成优选 / 弱信号降权 / 遥测）。AutoForge 作为 agent 创建自动化的平台，在 build 阶段同样要把"自然语言设备描述"绑定到真实 HA entity_id，**面对完全相同的痛点**。本设计把 AutoFlow 验证过的基座模式 + 待补的决策智能层抽象为通用设计，供 AutoForge 开发者（codebuddy）复用、并与 AutoFlow 对齐同一套设备绑定语义，避免两边各造一套不一致的逻辑。
> **性质**：设计参考，非 AutoForge 现状描述。AutoFlow 代码行号仅作"已被验证"的证据，不是 AutoForge 内部实现。

---

## 0. 适用场景

AutoForge 在 `build` 阶段把"自然语言设备描述 / 友好名 / 房间词"绑定到真实 HA `entity_id` 时，需解决：

1. **怪异 / 另类设备混淆**：如"书房电脑"是 switch 开机卡（domain=switch），"房间灯"可能是 light / switch / select 多种域——agent 凭模糊名易选错域。
2. **房间命名歧义**："房间"指单个 room 而非全部房间；"卧室"不应反向吞掉"主卧室"（短词子串碰撞）。
3. **同设备多集成双 entity_id**：一个物理设备既接 `xiaomi home` 又接 `xiaomi miot`，产生两套 entity_id，需优选其一（本地局域网集成天然比云集成通达率高 / 响应快）。
4. **弱信号 / 常离线设备**：wifi 极弱、频繁 `unavailable` 的设备，应降权、让平台尽量少用它编写自动化。

> 这些都是**机械化操作**，应在平台侧完成，而不是消耗 agent token 去查、去猜。

---

## 1. 已被 AutoFlow v1 验证有效的基座模式（直接复用）

- **解析在平台侧机械化完成，不消耗 agent token**：agent 只拿候选列表，不触全量目录。
- **返回候选带 `friendly_name / domain / area / possible_states / confidence`**：`possible_states` 让 agent **不用猜域**（"这是 switch，可能状态 on/off"）。
- **fail-closed（绝不静默猜域）**：歧义 / 多候选时不自动采纳，逼 agent 显式从候选中选择；否则会出现"书房吊灯→select"式静默错配。
- **房间→area 在平台侧**：中文房间词→HA area 注册表映射；已修复短词反向吞长词（卧室/主卧室）的碰撞。

证据（AutoFlow v1，仅证明可行）：`gateway.resolve_entity`（gateway.py:1809-1895）、`_resolve_best` fail-closed（1897-1934）、`_resolve_area`+`_build_room_aliases`（1715-1769，已修 B1）。MCP 暴露为 `autoflow_resolve_entity`（mcp_server.py:97）。

## 2. 当前缺口（AutoFlow v1 与 AutoForge 共同面对）

实体目录 schema 只存 `entity_id / domain / friendly_name / area / device_id / state / capabilities`，**缺 `integration` / `platform` / `connectivity` / `offline` 字段**。后果：

- 同 device_id 多集成 entity_id 平铺返回、无优选 → 命中但可能选错集成（云 vs 本地）。
- 弱信号设备无健康度、仍被返回 → 可能指向离线设备。
- 怪异设备靠返回 domain 自查，风险在模糊排序把它埋没。

→ 这正是"决策智能层"要补的，不是重做检索。

---

## 3. 决策智能层方案（P0 / P1 / P2）

### P0 — 设备归并与集成优选（机械、零风险）
- 首次连 HA 快照 `entity_registry` + `device_registry`，**抓取 `platform` / `config_entry_id`**（HA websocket 直给，零成本）。
- 按 `device_id` **归并**同物理设备的多 entity_id：一个物理设备暴露为一条"设备卡"，下列多个接入路径，并标注集成类型。
- 解析返回时：**首选本地集成**（local LAN > cloud > polling），去重展示。
- **默认沉淀人工选择**：首次人工/agent 选对后写入精确映射（high 置信），下次直中，不再每轮重排。

验收门：同 device_id 双集成实体在候选中归并为一条设备卡、首选本地集成；"书房电脑"二次解析直中。

### P1 — 连通性与健康度（降权 / 优选）
- 目录增 `connectivity_tier`（local > cloud > polling，由 integration/config_entry 推导）。
- 增 `entity_health`（`offline_rate`，由 state 历史 `unavailable` / `unknown` 频次 + `last_seen` 间隔推导）。
- 解析打分纳入**降权 / 优选**，并显式回传 agent（"设备 Y 常离线，建议优先 X"）。

验收门：弱信号设备候选降权且带 health 标注；本地集成排序优先于云集成；离线设备不被静默置顶。

### P2 — 遥测与消歧闭环（收尾、优先级最高）
- 解析出口记 `exact / medium / low / ambiguous / none` 计数 → **给出真实成功率**（否则"成功率"永远拍脑袋，优选/降权效果无法验证）。
- 歧义时回**自然语言消歧提示**（"书房电脑 是 switch 开机卡，不是 light"），让 agent/人澄清有依据。
- 与**验证闸联动**：离线 / 低健康度设备不进自动化候选或明确标注，防假绿。

验收门：遥测可读出成功率漏斗；歧义提示驱动澄清；离线设备被验证标记不可靠。

## 4. 给 AutoForge 的差异化落地建议

- **解析时机**：放 `build` 安全闸**之前**的 binding 阶段，作为 IR 的一个规范化步骤，而非 agent 自由发挥。绑定错误应在 build 安全闸拦截（未知实体 / 歧义未选 → 拒编译）。
- **与双闸对齐**：`build` 安全闸负责"实体是否存在 / 是否歧义未决"；`sim` 逻辑闸负责"绑定实体在孪生中是否可达、状态转变是否成立"。离线设备由 sim 阶段反馈回绑定层降权。
- **数据源**：AutoForge 首次接 HA 时快照 `entity_registry` + `device_registry`（含 `platform` / `config_entry_id` / `area` / `device_id`），字段与 AutoFlow `refresh_catalog` 对齐。
- **学习闭环**：复用 P0 的"沉淀人工选择为精确映射"——AutoForge 的 IR / 经验层可跨会话记住"用户偏好某集成 / 某设备"。

---

## 5. 验收门汇总（建议）

| 层 | 验收门 |
|---|---|
| P0 | 同 device_id 双集成归并为一条设备卡、首选本地；怪异设备二次解析直中 |
| P1 | 弱信号降权 + health 标注；本地集成优先；离线不置顶 |
| P2 | 遥测可读成功率；歧义自然语言提示；离线设备被验证标记不可靠 |

---

## 6. 与 AutoFlow 的对齐约定

两套项目共享同一套**设备绑定语义**：`device_id` 归并、集成优选（local>cloud>polling）、弱信号降权、`possible_states` 防猜域、fail-closed 不静默猜。避免 agent 在 AutoFlow 与 AutoForge 看到不一致的设备解析行为。
