## 2. 行为增量

**修的是一个已承认的缺陷，不是纯新功能**：v1.1.0 的 `area` 只能从 `attributes.area` 取——
而 HA REST `/api/states` **不暴露 area 注册表**，大量实体根本没这个属性。本薄片把数据源从
「REST `/api/states`」升级到「REST + websocket 四注册表」。

**catalog 新增字段**（`resolve` / `list_entities` 候选里直接可见）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `device_id` | `entity_registry` | 物理设备 ID（后续 P0 归并的主键） |
| `platform` | `entity_registry` | 平台实现名（**不是**集成名） |
| `integration` | `config_entry_id → domain` | **真集成名**；无 entry 才回退 platform |
| `area_id` / `area` | `entity.area_id → device.area_id → attributes` | 解析链 |
| `offline_now` | `/api/states` | P1 廉价部分：`state ∈ {unavailable, unknown}` |
| `last_changed` | `/api/states` | P1 廉价部分：弱信号原材料 |

**对外契约变化**：
- 新增可选依赖 `pip install -e ".[ha]"`（与既有 `sim` extra 同模式）。**未安装时目录优雅降级**，核心 `resolve` 照常工作。
- `refresh` 返回新增 `registry: {available, reasons, counts}` 回执。
- IR Schema **未改动**，CLI/MCP/HTTP 接口签名**未改动**（只在候选输出里多了 6 个字段）。

## 6. NAS 真机实测发现（2026-09-16，已修并验证）

薄片在 NAS 对真实 HA（2026.9.2，2888 实体 / 15 区域）实跑，**发现三个原设计未覆盖的问题**：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 四个注册表组全空，且无异常 | `websockets` **默认 `max_size=1 MiB`**，`config/entity_registry/list` 在 2888 实体下超过它 → 服务端发 **1009「message too big」**并断连 | `websockets.connect(..., max_size=64*1024*1024)` |
| 2 | 上一条被**掩盖**成「entity_registry 为空」，看不出真因 | 逐条 `except Exception: continue` 把**连接级故障**也吞了——正是纪律 1 要防的「只靠 except」 | 逐条失败**记录原因**（`ws.recv 失败：…`）并 `break`，reasons 可见 |
| 3 | `config_entries` 恒为 0 | **HA 2026.9.2 未注册任何 config_entry 列表命令**：`config/config_entry/list` / `config_entries/list` / `config/entries/list` / `config/config_entry/entry/list` 全部返回 `unknown_command` | 命令被拒显式记 reason；新增 **`integration_source`** 字段标注可信度（`config_entry` 权威 / `platform` 回退） |

**修复后实测（NAS，真实 HA）**：

```
total=2888
  area              非空=2438  (84%)   ← v1.1.0 缺陷修好（此前 0%，只能从 attributes 取）
  area_id           非空=2438  (84%)
  device_id         非空=2827  (97%)
  platform          非空=2860  (99%)
  integration       非空=2860  (99%)
  integration_source: {'platform': 2860, '': 28}   ← 均为回退（见 #3），已如实标注
抓取回执：available=True，counts={entities:3206, devices:322, areas:15, config_entries:0}
         reasons=["命令 'config/config_entry/list' 被拒：unknown_command"]
```

### 需要回传给 dw 的一条（重要）

他设计里 P0 的**第 4 个 ws 调用 `config/config_entry/list` 在 HA 2026.9.2 上不存在**（4 个候选名实测全 `unknown_command`）。
因此 AutoFlow 侧若按该设计实现，**同样拿不到真集成名**，`integration` 会静默落成 `platform`——
建议两边统一加 **`integration_source` 标注**（`config_entry` / `platform`），否则 P1 的「集成优选 local>cloud>polling」
会拿着一个名为 integration 实为 platform 的字段做排序，属隐性错误。

## 附：本轮规避的两个坑（由用户转达，已实现并测试）

1. **`platform ≠ integration`**：真集成名需第 4 个 ws 调用 `config/config_entry/list` 取 `entry_id → domain`；
   无 `config_entry_id` 才回退 `platform`。只取 `entity_registry` 会把 platform 当集成名 → 隐性错。
   测试：`test_platform_is_not_integration` / `test_platform_fallback_when_no_config_entry`。
2. **area 解析链必须 `entity.area_id → device.area_id`**：大量实体 `area_id` 为空、区域挂在 device 上。
   测试：`test_area_resolution_chain` / `test_refresh_populates_area_via_chain`。
