### 3.1 实际调用的工具

> **结论：AF 不调用任何 MA MCP 工具。**
>
> AF 与 MA 之间唯一的集成是 **单向指标回灌（AF → MA）**：AF 通过 `POST {MA_BASE}/api/metrics/ingest`
> 把自身运行指标推给 MA（实现见 `src/autoforge/af_metrics.py`，契约见 `docs/reference/MA_METRICS_CONTRACT.md`）。
> AF 是 MA 指标的**生产方**，不是 MA MCP 的**消费方**。
>
> - [x] 不直接调用 MA MCP（无 MCP client 集成；全仓 grep `call_tool` / `ClientSession` / `mcp.client` 均无命中，
>       仅 `af_metrics.py` 含 `metrics/ingest` 的 `urllib.request` POST 推送）
> - [ ] get_user_persona
> - [ ] get_data_quality
> - [ ] data_coverage
> - [ ] get_device_usage
> - [ ] 其他 MA 工具

### 3.2 每个工具实际读取的返回字段

> **N/A**：AF 不调用任何 MA MCP 工具，故不读取任何 MA MCP 返回字段。
>
> 补充：AF 推送指标后只判断 MA 的 HTTP 状态码（2xx 成功 / 4xx·5xx·超时失败 → 落离线缓冲重试），
> 不解析 MA 返回的语义字段。因此 MA 侧任何字段重命名（含 Q-A → Q-B）都不会影响 AF。

### 3.3 是否依赖 legacy 特有行为

> - [x] 不依赖，只按固定 REST 契约交互
>   - AF 对 MA 仅有的耦合是 `MA_METRICS_CONTRACT.md` 定义的 `POST /api/metrics/ingest` 契约，

>     `success_rate` / `audit_distribution` / `confidence` / `last_event_at`）全部固定，
>     与 insights 的 Q-A / Q-B 命名体系无任何关系。
>   - 全仓 grep `get_user_persona|get_data_quality|data_coverage|get_device_usage|insights_legacy`
>     在 `src/` 与 `tests/` 中均无对这 4 个工具或 legacy 命名体系的引用；AF 内部的 `/api/insights/*`
>     （pending/approve/reject）是 AF 自有审批队列，与 MA 无关。
> - [ ] 依赖 legacy 的字段命名（Q-A 体系）
> - [ ] 依赖 legacy 的默认值/空值处理
> - [ ] 依赖 legacy 的错误返回格式
> - [ ] 其他（请注明）

### 3.4 切换窗口期

> **N/A / 无影响**：AF 不消费这 4 个 MCP 工具，Q-B 切换不会对 AF 造成任何破坏，
> 因此无需 7 天双跑对账，也无窗口偏好。
>
> 唯一提示：请 MA 在切换时保持 `POST /api/metrics/ingest` 端点与 `MA_METRICS_CONTRACT.md`
> 字段稳定（这是 AF→MA 的唯一契约，与本次 insights 重命名无关，正常情况下不受影响）。
