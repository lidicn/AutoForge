## 2. 行为增量

- **新增能力**：统一故障注入层。五类故障（`unavailable` / `timeout` / `drop` / `reorder` / `drift`）有明确的注入层与期望落点；四类失败（设备故障/超时/取消/业务拒绝）落执行器的语义被显式断言。
- **编译期/运行期闸门**：无变化。故障只改变**测试底座**结果，生产 Runtime 主链路零改动。
- **对外契约**：
  - 无新增 IR 字段；无 CLI 改动。
  - 适配器新增测试用方法 `timeout_next/drop_next/unavailable_next`（`fail_next` 语义与签名不变，向后兼容）。
  - `CallResult.data` 在故障失败时新增 `fault` 标记（`timeout`/`drop`/`unavailable`/`fail`）。
  - 适配器仍严格"单次下发、无重试、无降级"（红线未破）。

## 4. 已知风险 / 残留项

- [ ] `unavailable` 与 `drift` 属**状态层**（`FaultPlan.apply_to_states`），`timeout`/`drop` 属**适配器层**（`apply_to_adapter`）；两层不重复注入（同 spec 只注入一次）。不影响主链路。
- [ ] 真 vhass 下 `HassAdapter`（`af_vhass/bridge.py`）未接故障队列，故 vhass 只覆盖状态层/事件层故障（unavailable/reorder）；适配器层故障由 FakeHA 与本机 mock 路径覆盖。若需 vhass 覆盖适配器超时，后续可给 `HassAdapter` 加同一 `FaultQueue`。
- [ ] `reorder` 目前是确定性打乱（`random.Random(seed)`），用于验证乱序收敛；未做"按 timestamp 逆序"等更细的乱序策略（IR 未要求）。
