BUG-01严重 未注册管理员时，匿名请求可用任意用户名口令换取全权限令牌

src/autoforge/af_api.py:1019-1029（工作区与 HEAD 均存在）　配套：af_api.py:981-984、af_api.py:986-1009、af_auth.py:1053-1155
触发条件

部署满足两个前提：① AUTOFORGE_TOKENS 已配置（TokenRegistry.enabled == True，即生产态、写/live 面处于 fail-closed）；② 管理员用户尚未注册（{store_root}/.auth/admin.json 不存在，或存在但解析失败）。此时对 POST /api/auth/login 发送任意非空 username + 非空 password 即可。

证据

if not (body.username and body.password):
    raise HTTPException(status_code=401, detail="用户名或密码为空")
# 未注册时的兼容模式：任意非空凭据可登录（旧行为）
if not admin_store.has_admin:
    token = registry.issue_for_agent(body.username, ("read", "write", "live"))   # ← 直接签发
    return {"ok": True, "user": {"username": body.username, "role": "admin"},

该端点没有挂任何 dependencies=[Depends(...)]，是匿名面。签发出的令牌是注册表内的真实令牌，requires("write") / requires("live") 会正常放行：

// af_auth.py:261-263 —— enabled 只由已配置令牌决定

// af_api.py:355-402 —— requires() 只校验 scope，不看 subject 是否经过口令验证
后果
  • 未认证的写 + live 提权：攻击者拿到 ("read","write","live") 三域令牌，可调 /api/live/run（真机下发到 Home Assistant）、/api/store/import、/api/graphs/enable、/api/credentials/*、/mcp 的写工具等。整个 requires() 的 fail-closed 设计被这一条旁路绕开。
  • 绕过 AUTOFORGE_TOKENS 的命名治理：令牌被签发到攻击者自选的 subject 名下，进入 issued_tokens.json 与 registry.subjects() 列表，事后审计看到的是一个「正常登录过」的主体。
  • 二次触发路径更隐蔽：has_admin 是 bool(self._username and self._salt and self._hash)（af_auth.py:1101-1104），而 _load 在文件损坏时静默退化为「无用户」。也就是说，一旦 admin.json 因任何原因损坏/被清空，这条旁路会重新打开，而运维在日志里看不到任何异常。
  • README §4.1 把「公开读面」的边界建立在「只在可信 LAN」这一网络前提上；但这条旁路给的是 写与 live，不是读面，网络前提在这里不构成可接受的风险转移。
修复建议
  1. 删掉 login 的兼容分支：not admin_store.has_admin 时应直接 409/403，并提示先去 /api/auth/register，不要签发任何令牌。
  2. 若必须保留「老用户升级不被锁在外面」的过渡语义，改为一次性引导凭据：服务启动时生成 bootstrap secret 打到 stdout/日志一次，只有携带它才走兼容分支，且该分支在首次成功注册后永久自我关闭。
  3. 把 has_admin 的「读不出来」与「确实没有」分开：新增 admin_store.poisoned 标志，损坏时对 register 与 login 双向 fail-closed（当前口径只防了重复注册，没防登录）。
  4. 给 /api/auth/register 与 /api/auth/login 单独挂一个低配 RateLimiter（可复用 af_api.py:303-308 的 bootstrap_*_limiter 形状），当前这两条只受全局 1000/min 的 _rate_limit_dep 约束，口令爆破几乎无成本。
与已有自审记录的关系：HEAD 上已有的 P0-9 把 requires() 收成了 fail-closed，代码注释也明确写了「生产无令牌即拒绝」。BUG-01 指出的是另一条不经过 requires() 的入口，因此不属于「已修的 P0-9」，也不在 .gates-baseline.txt 的 86 条里。

BUG-03高 TokenRegistry.subjects() 无锁遍历令牌表，与签发/清理并发时抛 RuntimeError

src/autoforge/af_auth.py:307-312（无锁）；对照加锁侧 af_auth.py:278-296、316-364
触发条件

两个请求在 FastAPI 线程池里并发：一个走 /api/auth/subjects、/api/user/agents 或 /api/user/pair/{code}/confirm（都调 registry.subjects()），另一个走 /api/auth/login / /api/auth/register / 配对兑换（都调 issue_for_agent）或触发 _purge_expired_locked / _evict_oldest_locked。也就是用户端 WebUI 打开 agent 列表的同时有人登录即可。

证据
// af_auth.py:307-312 —— 没有任何 with self._lock
def subjects(self) -> list[dict[str, Any]]:
    seen: dict[str, set[str]] = {}
    for info in self._tokens.values():        # ← 遍历字典视图
        seen.setdefault(info.subject, set()).update(info.scopes)
    return [{"subject": s, "scopes": sorted(sc)} for s, sc in sorted(seen.items())]

// af_auth.py:316+ —— 同一字典在锁内被插入
def issue_for_agent(...):
    with self._lock:
        self._tokens[token] = info             # ← 并发插入
// af_auth.py:342-364 —— _purge_expired_locked / _evict_oldest_locked 在锁内 pop

authenticate()（:278）与 revoke_by_subject()（工作区版本）都规规矩矩加了 self._lock，唯独 subjects() 漏了——是遗漏，不是设计取舍。

后果

CPython 在遍历期间检测到字典尺寸变化会抛 RuntimeError: dictionary changed size during iteration。该异常未被捕获，会穿过路由层变成 HTTP 500；/api/user/agents 是用户端 WebUI 的主列表接口，/api/user/pair/{code}/confirm 是配对流程的收尾步骤——表现为「偶发 500、刷新一次就好」，是最难被日志复盘的那类故障。令牌量越大（MAX_ISSUED 上限内）插入越频繁，命中概率越高。

修复建议
  1. 在 subjects() 内加 with self._lock:，与 authenticate() 同口径。
  2. 或者在锁内先 list(self._tokens.values()) 做快照，锁外再聚合（减少持锁时间；本函数的聚合是纯计算，无 I/O）。

BUG-13低 SSE 去重表不是真 LRU，容量上限下会提前丢弃仍活跃的事件 ID

src/autoforge/af_live.py:284-303
if len(_seen_ids) > 4096:
    # LRU: 清掉最早的一半
    for k in list(_seen_ids.keys())[:2048]:
        del _seen_ids[k]

注释自称 LRU，实际按插入顺序删除前一半（Python dict 保序，但不会因访问而重排）。在事件密度高、重连频繁的场景下，被删掉的那一半里可能包含刚刚见过、最容易在重连窗口内重复出现的 ID，去重效果弱于真实 LRU。影响是重复事件被再次投递（总线有去重/节流兜底，故后果有限）。

修复建议

换成 collections.OrderedDict + move_to_end，或用有界 LRU 实现；若要保留现在的近似实现，把注释里的「LRU」改成「FIFO 半量淘汰」，避免下一位读者按 LRU 语义推理。

BUG-14低 start_watch 打开的日志句柄未显式关闭

src/autoforge/af_service.py:2549-2556
logf = (root / "watch.log").open("ab")
proc = subprocess.Popen(cmd, stdout=logf, stderr=subprocess.STDOUT,
                        start_new_session=True, env=child_env)

logf 在函数返回后依赖 CPython 引用计数回收来关闭，没有 with 也没有 finally: logf.close()。在非引用计数实现下会一直挂着；在 CPython 下虽然会及时回收，但「子进程继承的句柄在父进程侧何时关闭」在 Windows 上会阻止日志文件被轮转或删除。异常路径（Popen 抛错）同样没有 close。

修复建议

用 with (root / "watch.log").open("ab") as logf: 包住 Popen 调用——Popen 会把 fd 复制给子进程，父进程侧随后关闭是安全的。

3 · 架构缺陷与缺失清单

先给结论：这个项目的架构分层是清楚的，问题不在「乱」，而在「自建的纪律体系与代码实际状态之间已经出现裂缝」——评审体系产生了大量通过记录，但其中一部分是把缺陷「登记后冻结」，而不是修复。下面按影响面排序。

ARCH-01 · 自建门禁体系冻结了 86 条已承认的缺陷，且门禁口径与自身基线自相矛盾

现状（有据）：.gates-baseline.txt 由 python -m homesdk.gates AutoForge --update-baseline 生成，文件头写明口径是「只准减少，不准新增」。实测该文件当前有 86 条生效条目：

自相矛盾的那一条（可直接核对）：.gates.toml 的 critical_globs 段开头写着—— 
# ── 关键模块：这里的 `except Exception: pass` 是硬错误，不许进基线 ──────────

    "src/autoforge/af_executor.py", ...
    "src/autoforge/af_service.py",     # 会话与仿真编排（`_SESSIONS` 家族）
    "src/autoforge/af_mqtt_bridge.py", # 跨仓说话的一张嘴：吞异常就等于对端静默失联
]
而 .gates-baseline.txt 里就有一条：

即：被门禁配置明确声明为「不许进基线」的关键模块，在基线里有一条同规则条目。这不是我的推断，是两个仓库内文件的直接对账结果。要么基线是在该规则加严之前生成的且此后未重跑校验，要么校验本身对 critical_globs 不生效。

缺什么：缺「基线条目与门禁口径的一致性校验」。当前 check_gates_coverage.py 只钉「工作流引用的门必须在 gates.sh 里」，没有钉「基线里的条目不得违反 critical_globs 的硬约束」。

会导致什么：① 关键模块的静默失败长期合法存在（af_mqtt_bridge 那类「跨仓说话」的模块吞异常，表现就是对端静默失联，而门禁不会拦）；② 任何人下次想加严规则时，会先看到基线里「已经有先例」，加严阻力被人为抬高；③ 86 条这个数字会给人「已经治理好了」的印象，而它实际是欠债台账。

建议：给门禁加一条自检——遍历基线条目，凡命中 critical_globs 的直接判红并列出；同时对 fake-ok-const 与 except-pass-broad 分别设上限阈值，让「只准减少」从口号变成 CI 断言。

ARCH-03 · CI 交付链路：解释器版本与自述环境要求不一致，「真 vhass 仿真」在 CI 上不可能按本机口径跑

现状：.github/workflows/ci.yml 的四个作业全部使用 python-version: "3.11"（:16、:35、:56、:88 附近各一处）。而 README.md 的快速开始明写：

& "<python3.14>" -m venv .venv314

同时 pyproject.toml 的 dev extra 包含 pytest-homeassistant-custom-component 且未钉版本；CI 的安装步骤是 pip install -e ".[dev]"。测试配置又用 addopts = "-p no:homeassistant" 默认禁用该插件，vhass 标记的用例在非 POSIX / 插件缺席时 skip。

由此推出（标明置信度）：

  • 确定：CI 上跑的是与本机不同的解释器（3.11 vs 3.14），且 vhass 这一族用例在 CI 上走的是 skip 分支。README 里那句「回归基线 1300 passed / 51 skipped / 7 subtests passed（本机 Windows 全绿）」是本机读数，不能代表 CI。
  • 确定：CI 里那道被反复强调的「逻辑闸」——forge sim 的 vhass 仿真——在 CI 上没有真仿真可用，只跑内置 FakeHA。

缺什么：缺「CI 解释器与项目自述最低环境一致」的校验；缺仿真依赖的版本上界/锁定；缺把 vhass 用例设为必跑的独立作业（当前它们可能永远是绿的 skip）。

会导致什么：仿真面（项目最核心的差异化能力）实际上没有持续集成保护。一旦 af_vhass/ 或 FakeHA 与真 HA 语义漂移，CI 不会红；而项目自己在 docs/HA_SEMANTIC_DIFF.md 里维护着「8 处有意偏离」，说明语义对齐是被严肃对待的目标——目标与保障手段之间有落差。

ARCH-04 · 交付面依赖仓库内随附的私有 wheel，且没有私有源策略

现状：docker/homesdk/homesdk-0.3.2-py3-none-any.whl 被直接提交进仓库。pyproject.toml 注释说明它是私有包、未上 PyPI，安装方式是在 CI 与部署时 pip install docker/homesdk/*.whl。更关键的是 af_executor / af_runtime 硬依赖 homesdk.consent（其作用之一是 G4 canary 的同意/否决闸门）。

缺什么：缺私有包索引（或 vendor 目录的校验和清单）、缺该 wheel 的来源与可再生性说明、缺「本地开发怎么装、装不上怎么报错」的统一入口。

会导致什么：.gitignore 里为它开了一条白名单（!docker/homesdk/*.whl），说明它曾差点被忽略规则挡掉——这种「靠白名单保住交付物」的形状很脆弱。更实质的问题是：一个承载安全闸门语义的包以二进制形式固化在仓库里，没有源码可比对、没有构建流程可复现，审计者（包括你自己将来）无法确认「闸门逻辑」是否与预期一致。此外 wheel 是 py3-none-any，安装时不受 Python 版本约束，但它的运行时行为并未在 3.11/3.14 两侧都验证过。

ARCH-05 · 信任边界：写面/live 面在设计上是 fail-closed，但边界外有两个可绕过的入口，且公开读面的安全性完全外挂在「可信 LAN」这一条网络前提上

现状：README.md §4.1 把这件事写成了显式前提，态度是诚实的：

  • --host 0.0.0.0 保留（因为 DB 跨机器调 AF，绑 loopback 会打断联动环）；
  • 因此 /api/* 的公开读端点（/api/health、/api/metrics 等 scope=None 的门）按裁定维持公开，判据是「只读面不能反过来依赖令牌系统」；
  • 写/live 面 fail-closed，本地放行只有 AF_ALLOW_NOAUTH=1。

缺陷：这条设计的完整性依赖「没有任何绕过 requires() 的路径」，而实际存在两条（BUG-01 的 login 旁路、BUG-02 的逃生舱放大）。此外 /api/auth/register 是匿名的先到先得（af_api.py:986-1009），在 0.0.0.0 暴露 + 未注册的初始状态下，谁能最先到达这个端口，谁就成为管理员。

缺什么：缺「信任边界清单」这一份可核对的资产——即「哪些端点匿名、哪些要什么 scope、各自的网络前提是什么」的单表。当前这些信息分散在 60 多个路由装饰器里，靠读代码才能还原，因此任何一次改动都可能悄悄改变边界（BUG-02 就是这么发生的：3 行代码就把一条边界抹掉了，而没有任何测试或文档对账失败）。

建议：从 build_app() 的路由表生成一份「端点 × scope × 匿名性」的清单并对打进 CI（形状检查：新端点必须显式声明 scope，默认拒绝），让边界成为可 diff 的产物而不是可读的代码。

ARCH-06 · 进程模型与并发归属：三套互不相识的同步原语 + 无 supervisor + 无优雅停机

现状（分类清点）：

原语用在哪覆盖面
threading.Lock/RLock进程内共享状态（af_auth.py 5 处、af_config.py:44、af_pending.py:42、af_service.py:851/1549、af_telemetry.py:48 …）较广，但已出现漏网点（BUG-03 的 subjects()）

缺什么：

  • 缺统一的状态归属模型：哪一份状态归哪个进程、由哪把锁保护，没有成文约定，只能逐个模块推断。项目有 import-linter 契约锁「分层不能反向依赖」，但没有等价物锁「共享可变状态的归属」。
  • 缺 supervisor：serve 是常驻进程，watch 是它拉起的子进程（af_service.start_watch 用 subprocess.Popen），但没有任何进程管理组件负责「子进程挂了要拉起、父进程挂了子进程要收」。子进程用 start_new_session=True 脱离了父进程的会话，父进程死掉后子进程会变成孤儿继续跑。
  • 缺优雅停机：src/ 全树 atexit / signal.signal 命中数为 0。所以本报告 BUG-06 提到的问题不是「某处忘了清理」，而是整个运行时没有停机钩子这个概念。对一个把「实例跨进程/崩溃恢复」当卖点的系统来说，正常关闭与崩溃走同一条路径，等于自愿放弃了一半的持久化保证。

会导致什么（「现在能跑但长起来会痛」的部分）：单机单实例时这些都不显形。一旦按 README 描述的跨机形态铺开（DB 在一台、AF 在另一台、WebUI 在第三台），就会同时遇到「租约时钟偏移」（BUG-10）、「孤儿 watcher 与新 watcher 并存」（BUG-04/06）、「谁该负责重启」（无 supervisor）三个问题，而它们互相放大。

ARCH-07 · 可观测性：有留痕纪律，但没有指标后端、没有追踪、没有分级日志约定

现状（这是优点，先给信用）：项目对「不能静默」这件事执行得很认真——_keep() 环形诊断缓冲、counts["forbidden_seen"] 计数、af_audit.py 结构化审计、af_metrics.py 指标回灌 MA、af_telemetry.py 遥测。多处 except 都带 # noqa: BLE001 + 注释说明为什么吞，属于有意识的降级。

缺什么：

  • 无日志分级约定：全仓 logger.warning 与 logger.info 混用，没有「什么级别代表需要人介入」的统一口径；af_api.py 里大量失败是以 {"ok": False, "error": ...} 返回而非记日志，导致HTTP 500/403 的成因不进日志，只能靠调用方回报。
  • 无请求级追踪：没有 request id / trace id，跨「HTTP → service → store → 子进程」的一条链路无法在日志里串起来。start_watch 那种「最长 15 秒、多次轮询」的路径一旦出问题，只能靠时间戳猜。
  • 指标面只出不给：/api/metrics 是公开端点，但没有配套的采集/告警约定（scripts/metrics_push_cron.sh 存在，属人工 cron）。
  • 环形缓冲有容量上限但没有 TTL（项目自己在 af_bounded_caches.py 的 docstring 里把这件事列为待裁项：诊断型只写清单「没有诚实的 TTL 可填」）。

会导致什么：故障定位依赖「现场还在」——进程重启后诊断环形缓冲清空，.forge/ 下的 sidecar 文件成为唯一线索。这解释了为什么项目里会积累出大量 _check_now.py / _restart_watch.py 之类的一次性排查脚本。

  1. 分层与依赖方向是本仓最扎实的部分，不要动。 af_ir/ 作为唯一真相、af_atomic/af_flock 作为零依赖底座、import-linter 锁 L0→L2 反向依赖、grimp 锁全量反向依赖——这套设计解决的是真问题，且门禁确实在跑（.atomic-write-baseline.txt 被清到 0 条就是证据）。
  2. 最大的系统性风险不在代码，在「纪律与事实的间距」。 86 条冻结基线 + critical_globs 与基线自相矛盾 + README 里程碑用 ✅ 标注实际不通的方案，这三件事共享同一个根因：记录缺陷的机制强于修复缺陷的机制。第 2 节里的 BUG-01/02 之所以能长期存在，正因为它们不在任何一张清单上——体系的可见范围之外。
  3. 第二个系统性风险是「单机思维」。 全局变量、墙钟租约、PID 杀进程、无 supervisor、无优雅停机——每一条在单机上都是可接受的工程取舍，但项目已经在往跨机形态走了（README §4.1 亲口描述 DB 跨机调 AF）。这里需要一次显式的「多进程/多机假设」评审，而不是逐条打补丁。
