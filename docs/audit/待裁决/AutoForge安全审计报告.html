项结论要点与依据
一、鉴权与授权 有问题 87 条路由分四档：15 条完全没有鉴权依赖（其中 4 条只挂单写者租约守卫：build / bind / sim / spec.compile）、30 条 read、39 条 write、3 条 live；外加速查内置的 /docs、/redoc、/openapi.json 共 3 条也无鉴权。 无管理员时 /api/auth/register（986-1010）与 /api/auth/login 的兼容分支（1020-1038）都不带任何守卫，直接 issue_for_agent(username, ("read","write","live")) ⇒ 零凭据换全权限（运行时实测 register 返回 200）。没有管理员档：任何 write 令牌即可吊销他人令牌、覆写 HA 凭据、删自动化。令牌档位由 scopes 决定，蕴含表只允许 read ← write（af_api.py:248-252），read 无法自我提升。
二、凭据与密钥 有问题 来源：env（AUTOFORGE_API_TOKEN / AUTOFORGE_TOKENS / AUTOFORGE_REVOKED_TOKENS）→ secret 文件目录（默认 /run/secrets）→ 兼容 env；HA/API 凭据另有 {store}/credentials.json。生成用 secrets（令牌 af_ + token_hex(20)）；管理员口令 PBKDF2-HMAC-SHA256 100000 轮 + 16 字节盐。 落盘权限写的是 os.chmod(tmp, 0o600)，而 Windows 上 chmod 不改 ACL（F-10）。真正的火在仓库根：issued_tokens.json.tmp（26 条）与 issued_tokens_clean.json（1 条）是明文令牌注册表，未被 .gitignore 覆盖（F-03）。令牌不进错误响应（R-57）、不进 /api/auth/subjects、/api/credentials 只回掩码；?token= 会进访问日志，有掩码 filter 兜（F-09）。
三、路径穿越与任意读写 安全 所有以 name 为参数的端点都经 GraphStore._dir() 白名单化：alnum + - _ 之外一律替换为 _，再 strip 首尾 _（af_store.py:227-230）⇒ ../、绝对路径、\、盘符 E:、UNC 全部无法存活。/api/store/export|import 走请求体内的 JSON bundle，不接路径。/api/asks/pending 只读固定文件 {root}/pending_asks.json。 静态托管另有一道：resolve() + is_relative_to(root)，并显式规避了 startswith 把 /mimo 与 /mimo-secret 当同一棵树的陷阱（af_api.py:1434-1440）。
四、工具参数到命令执行 有问题 没有 shell 注入面：全 src 只有一处 subprocess（af_service.py:2550），参数是固定列表、无 shell=True、无字符串拼接，forge 从 PATH 解析，--ha-url 取自环境变量。真正到达「执行」的路径是 IR 动作层（HA service 调用 / MQTT 发布 / inbox 投递 / 走白名单的出站 HTTP），其风险分级与设备 ACL 是第一轮的既有结论，本轮不重复计分。 本轮新增的两点：① /api/sim、/api/build、/api/bind、/api/spec/compile 这四条连鉴权都没有（F-04 同族，见总览「一」），其中 /api/sim 是吃 CPU/内存的仿真入口，属于零凭据资源耗尽面；② 面板上的「风险审批」只覆盖待批队列（/api/pending/*，只在服务层注册、MCP 面不注册，af_api.py:501），而 /api/live/run 与 /api/undo 是绕过队列直达真机的另一条通道 —— 它的闸是四重（见「误报排除」），但不经过人工审批队列。

F-01 零凭据换全权限令牌：没有管理员时 register / login 兼容分支直接签发 read+write+live 严重

# 或者走登录兼容分支（无管理员时，用户名/口令非空即可）

事实一（无 TLS）。uvicorn.run(app_, host=host, port=port, log_level="info") 没有任何证书参数（af_cli.py:1465），全仓无 TLS 配置项。
事实二（令牌进 URL）。SSE 端点 GET /api/mcp/pair-request 因为 EventSource 发不了自定义头，令牌经 ?token= 传递（af_api.py:1108-1136，注释自己写明「代价：会整条落进 uvicorn 访问日志」）。 仓内确实挂了一个掩码 filter（af_cli.py:1379-1422，把 token=… 替成 token=***），但它只保护本进程的那条 logger：令牌在到达 uvicorn 之前已经经过浏览器历史、反向代理/网关日志、以及同网段的抓包。注释也如实写了「反代/nginx 那一半属部署侧」。
事实三（跨机器链路）。README 声称的「DB 跨机器调 AF」在本仓里的实现就是普通 HTTP + Authorization: Bearer（af_mcp.py 的 HTTP MCP 与全套 /api/*），没有第二层鉴权、没有 mTLS、没有请求签名。同时 AUTORFORGE_TRUST_PROXY 默认关闭（af_api.py:316-323——这个默认是对的，防 XFF 伪造），副作用是：如果前面真站了个反代，_client_ip() 看到的是反代自己的地址，于是 limiter.check(f"ip:{...}") 把所有调用方合并进同一个 1000/min 的桶 ⇒ 单个滥用者能把这个桶吃干，其他人一起被 429（自伤式 DoS），而按 IP 的归因与封禁同时失效。
攻击者视角。同网段的任意主机（例如 NAS 上的另一个容器、被入侵的 IoT 设备、访客 Wi-Fi 上的终端）都能被动拿到 bearer 令牌；拿到后按 1.6 的清单做全套动作。这是本报告里「真暴露在网络上会发生什么」最直接的一条。

F-10 「看起来设了权限」：POSIX 0600 在 Windows 上不改 ACL 低（Windows 侧中）

事实。凭据落盘统一走 _atomic_write_text：先 os.chmod(tmp_path, 0o600) 再写、再 os.replace（af_auth.py:78-113，chmod 在 91 行）；af_config._atomic_write 同一手法（af_config.py:112-123）。Windows 上 chmod 是 no-op 式的存在：它不改 NTFS ACL，也不读/写 icacls。代码里也标注了「Windows 无 0600 语义」，但没有替代实现。
实际保护是什么。等于父目录继承下来的 ACL：默认情况下只有 lidicn 与该机管理员可读。.env（4 个令牌类键）、.forge/credentials.json（ha_token）、.task/…/.auth/*.json 全都如此。
影响。本机任何以该用户身份运行的进程（包括这一堆常驻的 node/cmd/codex-bridge、编辑器插件、以及任何被这些工具间接执行的代码）都能读到全部令牌与 HA 长期令牌；提权到本机管理员同样能读。这不是「取巧绕过」，而是「没有任何一层是它自己的」：一旦某个以该用户运行的组件被攻破，凭据即刻失守。
修复方向。Windows 档改用 icacls <file> /inheritance:r /grant:r "%USERNAME%:R"（或 win32security）显式收紧；或把凭据放到只有服务账户可读的目录并对目录设 ACL；NAS/Linux 档保持 0600 即可。同时把这条写进 README 的权限说明，避免「设了 0600 就安全」的错觉。

F-11 af_secrets 声明的「credentials.json 优先」优先级链根本没有实现 低

声明。af_secrets.py:1-12 的 docstring 写：读取优先级是 credentials.json（af_config 内的文件存储）> secret 文件 > 环境变量；docker-compose.api.yml:34 也照抄了这条链。
实现。load_secret()（af_secrets.py:26-39）只做两段：secret 文件 → 环境变量，整段代码里没有任何 credentials.json 的读取。而 TokenRegistry._load_env()（af_auth.py:165-193）读 AUTOFORGE_API_TOKEN / AUTOFORGE_TOKENS / AUTOFORGE_REVOKED_TOKENS 用的就是 load_secret ⇒ API 令牌永远不可能来自 credentials.json。真正读 credentials.json 的是 af_config，而且只服务 ha_token / api_token 这两个键（af_config.py:93-103）。
为什么要算一条发现。它属于本轮点名的那一类：「声明了但没接线」比「写错了」更危险 —— 运维会照着文档把令牌写进 credentials.json，然后鉴权静默不生效（甚至更糟：以为配了令牌所以是 fail-closed 的 403，实际因为「一个令牌都没读到」而走进 registry.enabled == False 那条分支）。这不是猜测，docker-compose.api.yml:75-78 的注释就在抱怨一次同族事故（键名写错 ⇒ 值被喂给一个没人读的空位、鉴权照旧失败且不留原因）。

4.1 tick_watchdog_pass：tick 自愈机制零调用点（已知三条之三，仍然成立）

定义与宣告。af_live.py:83-109 定义了 tick_watchdog_pass(*restart=None)，返回 alive/running/held_safe_halt/stopped/restarted/unrecovered 六档，唯一自愈分支是「意外终止」，并明确不重启 SAFE HALT（安全红线）；它还被导出到模块的 __all__（af_live.py:51）。 文档把它记成已完成项：docs/ADM联动执行记录-AF.md:180 写「④ tick 线程自愈，区分原因重启（裁定 C）」，并以 tests/unit/test_af_live.py 的三条腿作为证据； af_tick_supervisor.py:222-224 的 docstring 更直接：「主线程 watchdog（af_live.tick_watchdog_pass）仅在意外终止时重启本线程」。
实际调用点。git grep -n tick_watchdog_pass 的全部命中：af_live.py:51（导出清单）、af_live.py:83（定义）、af_tick_supervisor.py:223（docstring 里提到）、docs/ADM联动执行记录-AF.md:180（记账）、tests/unit/test_af_live.py:310/319/327/334（测试）。生产代码里零调用点。
为什么这比「写错了」危险。读代码的人（包括评审、包括未来的自己）看到 docstring 与记账表，会认为「tick 线程有自愈」。事实上没有任何循环在巡检它：_ticker_thread（af_live.py:64）一旦意外退出，没有任何东西会调用 tick_watchdog_pass 去发现并重启它。 同时那条安全红线（SAFE HALT 绝不被自愈抵消）是只由单元测试保证的属性 —— 单元测试直接调这个函数并断言 calls == []，而生产里根本没有调度者，于是「红线成立」这个结论在真实运行中既无法被触发、也无法被验证。这是典型的「测试绿了、机制不在」的假绿。
攻击者视角。直接可利用性低（需要先能让 tick 线程意外退出），但后果是静默的可用性塌陷：真机 watch 的 tick 线程死后，服务照常回 200、health 也不一定报，自动化悄悄停摆 —— 对「家居自动化」这类场景，安静地不执行比报错更糟。所以它的准确定性是声明的可用性保证不成立，而不是一个远程漏洞。
可达性判定。确定成立（零调用点由 grep 现读确证）。
修复方向。要么真接线（在 tick 线程的宿主循环/健康巡检里按固定周期调 tick_watchdog_pass(restart=…)，并把返回档位落进 /api/health），要么把 docstring 与记账表改成「本机制位已就绪但未接线」。 并对同类做一次结构性扫尾：给所有「已导出但零调用」的公开函数出一张清单（__all__ 减去实际引用点），因为这类残留靠读代码发现不了。

4.4 接线正确、但需要点名的两处（反例，用来划清边界）

  • 单写者租约（只读降级）是接线了的，但挂法不一致。_write 在降级时被整体替换为 503 阻塞器（af_api.py:441-448），因此绝大多数写端点在降级实例上会被拒；_readonly_guard 另挂在 6 条「不通过 _write」的端点上（build/bind/sim/spec.compile 与 live.run/undo）。 /api/user/auth-codes 刻意使用未被重绑的 _write_scope（:426-430），以便降级时仍按「明文只在 write 面」的口径供读 —— 这是有意设计，注释里写清了理由，不算漏。 也就是说这条机制不是「中间件统一挂」，而是逐端点手动挂：将来新增写端点如果忘了用 _write，就会在降级实例上被放行。这和 F-06 是同一个失效模式，建议用同一个结构性门禁（遍历路由断言守卫存在）覆盖。
