4.1 subjects() 并发修改（确认 · 运行时复现）

复现输出：  iterations≈129 | error=RuntimeError | detail=dictionary changed size during iteration | tokens≈238

代码位置：af_auth.py:307-312 def subjects()（返回 list(self._tokens) 的遍历未持锁）；签发侧 af_auth.py:316-340 issue_for_agent 在 :331 持 self._lock 写入 _tokens（锁在 :159、字典在 :153）。HTTP 入口：af_api.py:972（令牌/主体列表）、:1174（api_agents_list）、:1284。

af_api.py:959 是同步 def 端点 ⇒ FastAPI 把它放进线程池执行，所以不是冻结事件循环，而是占住一个工作线程最长 15 秒。并发若干次即可压满线程池，使其余同步端点排队。本轮未做计时复现：该路径需要导入 af_service，而实测这一项已超出 40 秒执行窗口。

4.4 停机是硬终止，而非优雅停机（部分确认）

af_service.py:2484   os.kill(pid, 15)  # SIGTERM

本机实测（Windows）：child pid=36024
                     poll_before = None
                     after os.kill(pid,15) -> poll_after = 15       ← 硬终止
                     graceful_exists = False                          ← 子进程 atexit 未执行
全仓 grep：src/ 内 atexit / signal.signal 零命中（唯一命中是上面那行注释）

结论：在 Windows 上这条等价于 TerminateProcess，任何"停止前落盘 / 上报 offline"的语义都不存在；"PID 复用导致误杀无关进程"是 Linux 侧的问题，本机无 Linux，未复现。这就是本条标"部分确认"的原因。

结论：可以，而且不区分严重级别。

  • 放行判定只有一条：指纹是否出现在基线里。failed 只看 active（不在基线内）与 stale，完全不看 level。哪怕是 critical 文件里的 ERROR 级违规，只要指纹进了基线就永久安静。
  • --update-baseline 把当前全部违规（active + baselined）一次写入基线 ⇒ 新引入的违规跑一次 --update-baseline 就洗白。
  • 文档口径与实现不符：.gates.toml（41 行）把 11 类路径列进 critical_globs 并声称其中的 except Exception: pass 是"硬错误（不许进基线）"，但工具里没有任何"ERROR 不许入基线"的闸。证据是现网基线自身就躺着一条：src/autoforge/af_service.py#except-pass-broad#health——而 src/autoforge/af_service.py 正列在 critical_globs 里，按 scan.py:160-163 这条本该是 ERROR。
  • 唯一兜底是 gates.sh:50-71 的计数棘轮：拿 --no-baseline --no-smoke 的全量总数跟 .gates-tally.txt 里的一个数字比大小，超过就红。它只能挡"总量上涨"，而这个上限本身就是一个可被编辑的数字（当前 97，实际 98）。
  • 顺带核实：.atomic-write-baseline.txt（13 行）是空的（0 条站点）。

一句话：基线机制 = 未获批违规的持久放行清单，--update-baseline 是它的自动填充器；真正的纪律（"只减不增""ERROR 不入基线"）目前只写在注释与流程约定里，代码没有强制。
