## 三、确证发现

### 🟠 BUG-05（中危·门禁覆盖缺口）`check_atomic_write_sites.py` 报绿，但 BUG-03/04 的裸写根本不在它射程内

这是第二轮报告里我自己提出的 P2 建议的回核查结果。先跑门禁：

```
$ python3 scripts/check_atomic_write_sites.py
✓ 原子写站点门禁干净（扫描 98 个文件、`os.replace` 站点 5 处：走 mkstemp/公共助手 3 处、
  固定名形状 0 处；授权面腿射程函数 46 个、其中落盘 6 个、裸写 0 个）
rc=0
```

**门禁判绿，但第二轮确证的 BUG-03（`af_runtime_ext.persist()` 裸 `open("w")+json.dump`）和 BUG-04（`af_metrics.flush_buffer()` 裸 `write_text`）依然存在。** 这说明门禁没有覆盖它们——不是误判，是**射程问题**。

**根因（读源码确认，见脚本头部 docstring）**：

- **判据 A 的锚点是 `os.replace(`**。它检查的是「已经在做原子替换的站点，其 tmp 名是否随机、有没有 fsync」——**只审已存在的原子写站点写得对不对**。
- 而 BUG-03/04 的问题恰恰是**压根没走原子写**：既没有 `os.replace`，也没有 tmp+rename。这种「完全绕过」的形状，判据 A 连看都看不到。
- **判据 D（授权面腿）** 射程被显式钉死为 `af_auth.py` 全部函数 ∪ 别处「写向 `.auth` 路径」的函数。`.forge/` 持久化与 metrics 缓冲不在其中。

门禁文档自己也承认这一限制：

> 豁免/基线**不覆盖**的事：本门判的是"临时文件名唯不唯一、有没有走已经修过的那条路"，是纯调用图形状。

**为什么这件事值得单列**：门禁报绿会给人一种「落盘安全已有保障」的错觉，而实际上它只保障了「已选择原子写的那部分」。真正的缺口是**没有任何一条规则去问「这个状态文件该不该走原子写」**。

**修复建议**（不必推翻现有门，补一条腿即可）：

```python
# 新增判据 E：状态落盘点必须走原子助手
#   - 射程：写入路径指向 .forge/ 或 *.json/*.jsonl 状态文件的 write_text / write_bytes /
#     json.dump / open(...,"w") 站点
#   - 判红：该站点所在函数内既无 atomic_write_text / _atomic_write / _atomic_write_text，
#           也无 os.replace + mkstemp
#   - 复用判据 C 的反空洞自证：扫不到任何落盘点就 exit 2，不许假绿
```

这条腿与现有 A 腿互补：A 管「走了原子写的走得对不对」，E 管「没走原子写的该不该走」。

## 四、并发维度核验：0 缺陷，附证据

9 条规则共命中 18 条，逐条核验后**全部为设计取舍或误报**：

| 规则 | 命中 | 核验结论 |
|---|---|---|
| C-01 可重入死锁 | **0** | 持锁调用链上的辅助方法（`_persist_revoked` 等）自身均不取锁，是刻意设计的「持锁调用」模式 |
| C-02 锁序反转 | **0** | 未见双锁嵌套 |
| C-03 async 内阻塞调用 | **0** | 未发现 `async def` 内调用同步阻塞 API |
| C-04 丢失 await | 3→**0** | 原 3 条经核验全为误报，已修正判定逻辑 |
| C-05 async 同步锁混用 | **0** | 无 |
| C-06 跨线程无锁写 | **0** | 共享状态的写入点均有锁覆盖 |
| C-07 持锁 sleep | **0** | 无 |
| C-08 部分加锁覆盖 | 6 | **误报**：6 处裸写均为 `load`/`_load`，调用时机是 `__init__` 构造期或 `set_persistence` 启动期，此刻尚无并发访问者 |
| C-09 持锁磁盘 IO | 12 | **设计正确**，见下方说明 |

### 关于 C-09：我这条规则的立论前提对本项目不成立

C-09 的规则逻辑是「持锁期间做 IO 会放大锁持有时间，应把 IO 移到锁外」。核验 12 处命中后发现：

- **其中 8 处用的是 `FileLock`**（`af_store.py` 的 `directory/".lock"`、`tags.lock`；`af_catalog.py` 的 `path + ".lock"`）—— 这是**跨进程**文件锁。跨进程锁的意义就是串行化多个进程对同一文件的写入，**IO 必须在锁内**，移到锁外这把锁就保护不了任何东西。
- **另 4 处用 `threading.Lock`**（`af_pending.py:143`、`af_config.py:122`）—— 进程内锁，持锁落盘是为了让「落盘快照」与「内存状态」保持一致，属于合理取舍。

所以本项目的 12 处持锁落盘**不是缺陷**。我的规则只对「单进程内、且持久化一致性不依赖锁」的场景成立——记此以免后续照搬该规则产生误导。

## 五、观察项（不构成缺陷）

**`af_fire_recorder.py:90` 用 ISO 字符串字典序比较租约时间**

```python
lease = existing.get("lease_until")
if lease is not None and lease >= now_iso:
    return "leased"
```

核验结论：**当前成立**。写入侧 `try_begin` 中 `now.isoformat()` 与 `(now + timedelta(seconds=lease_s)).isoformat()` 来自同一个 `_clock.now()`，格式与时区偏移完全一致，字典序等价于时间序。

但这是**脆弱契约**：一旦两侧格式出现分歧（如有人改用 `date` 而非 `datetime`、改 `timespec`、或 house 时区配置变更导致新旧记录偏移不同），字典序会静默失效且不报错。建议改用 `datetime.fromisoformat()` 解析后比较，或在写入时统一存 epoch 秒。
