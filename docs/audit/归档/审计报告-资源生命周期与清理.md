## 二、本轮最重要的事：差点把"检测器坏了"当成"代码干净"

这是十六轮里最该被记录的一次失误。

**首版结果**：AutoForge 上 0 命中。
**如果不自检**，我会写出"本项目资源管理无缺陷"的结论——而这个结论是假的。

自检样例（含 5 个已知资源问题）首版只检出 2 条（RES-03/05）。逐层调试定位到：

```python
for n in ast.walk(fn):
    if not isinstance(n, ast.Call):   # ← 遍历的是 Call
        continue
    names = _assigned_names(n)        # ← 但这个函数只认 Assign → 永远 []
    if not names:
        continue                      # ← 于是所有 fd/句柄/临时资源全部跳过
```

修正后自检 **5/5 全中**（RES-01/02/03/04/05）。

**教训**：静态分析报 0 时必须先证明检测器能检出来。第十五轮我用了合成样例自检（那次是防止"假阴性"），本轮同样的方法**直接抓出了一个真 bug——不过是检测器自己的 bug**。

## 三、结论：0 项确证缺陷，1 条形状命中经实测排除

修正后重跑：AutoForge 上 **1 条命中**（RES-02），经实测验证**不构成实际泄漏**。

### 命中的那一条

**位置**：`src/autoforge/af_service.py:2352`（`start_watch`）

```python
try:
    logf = (root / "watch.log").open("ab")     # ← 无 with
    proc = subprocess.Popen(cmd, stdout=logf, stderr=subprocess.STDOUT, ...)
except Exception as e:
    return {"ok": False, "error": f"启动 watch 失败: {e}"}
# 后续无 logf.close()
```

全文件 grep 确认 `logf` 只出现 2 次（打开 + 作为 Popen 参数），**从未 close**，且 `logf` 是纯局部变量（未保存到 `self` 或全局）。

#### 实测：CPython 引用计数使其不构成实际泄漏

```
调用 5 次后 fd 数: 7 → 7    （CPython 引用计数回收 → 持平）
显式 close 版  fd 数: 7
```

`logf` 是局部变量，函数返回后引用计数归零 → 文件对象被回收 → fd 关闭。**因此不是缺陷**。

#### 但仍建议改（低优先级）

不是因为它泄漏，而是因为：
1. 依赖"函数返回即回收"这一 CPython 实现细节，换解释器（PyPy）或出现引用环时行为不同
2. `Popen` 成功后到函数返回之间有 **15 秒轮询循环**（`:2369`），这段时间内 fd 确实被多占用
3. 显式 close 语义更清晰：子进程已 dup 了 fd，父进程不需要再持有

建议写法：`Popen` 后立即 `logf.close()`（子进程已持有自己的副本），或用 `with` 包住 Popen 调用。

## 四、正向结论：资源管理的正确实现

本轮核验了全仓库 6 处非 `with` 的 `open()`，逐处确认**均正确关闭**：

| 位置 | 实现 | 评价 |
|---|---|---|
| `af_atomic.py:43` | `dir_fd` 用 `try/finally: os.close(dir_fd)` 嵌套，外层还有 `except OSError: pass` | ✅ 教科书级 |
| `af_auth.py:105` | 同上 | ✅ |
| `af_config.py:97` | 同上 | ✅ |
| `af_flock.py:98` / `:124` | `try: ... finally: os.close(fd)`，非 POSIX 分支还先解锁再关 | ✅ 跨平台处理正确 |
| `af_service.py:2352` | 无 close（本轮唯一命中） | 实测不泄漏，建议改 |

**同时确认：**
- **RES-04 临时资源 0 命中** —— `af_service.py:2330` 用 `tempfile.mkdtemp()` 建的临时目录有对应清理（用于 `deployed_ir.json`）
- **RES-05 子进程 0 命中** —— `Popen` 后有 `proc.poll()` 健康探测（P1-19），且失败路径会 return 明确原因
- **RES-06 异常路径 0 命中** —— 无"获取在 try 内、release 在 try 外且无 finally"

**特别值得记的一点**：`af_atomic.py` 这个原子写助手（BUG-05 的主角）在**资源管理维度做得完全正确**——随机 tmp 名、fd 用 with 包裹、fsync 文件 + fsync 目录、finally 清理 tmp。它的问题从来不是"实现有 bug"，而是"没被所有落盘点采用"。这与贯穿十六轮的主线完全一致。

## 五、十六轮主线：一句话收束

前十五轮的主线是"**正确写法存在，但没变成唯一路径**"。本轮给出了最干净的一个例证：

> `af_atomic.atomic_write_text` —— 资源管理**满分**（tmp 随机名 + with + 双 fsync + finally 清理），但 `af_runtime_ext.persist()` 和 `af_metrics.flush_buffer()` 没用它。

**实现质量从来不是这个项目的短板，"把正确实现变成唯一路径"才是。**

十六轮的缺陷分布也印证了这一点：

| 根因类别 | 缺陷 | 数量 |

| 操作顺序与不可逆 | BUG-11/12/15 | 3 |
| 输入与边界 | BUG-06/09/10/16 | 4 |
| 门禁覆盖不全 | BUG-05 | 1 |
| **单点实现错误** | BUG-01/02 | 2 |

**单点实现错误只有 2 条**（BUG-01 无界增长、BUG-02 默认值语义）。其余 14 条都是"有对的写法、但没强制用"或"顺序/边界没想全"。
