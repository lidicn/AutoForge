## 三、确证缺陷

### 🔴 BUG-03（高危）`af_runtime_ext.py` — 非原子写 + 无保护读取，一次崩溃足以让服务再也起不来

**位置**：`src/autoforge/af_runtime_ext.py:78-91`（`persist`）、`:93-108`（`restore`）

**证据链**：

```python
# af_runtime_ext.py:78-91  persist()
for name, payload in (
    ("shadow_log.json", self.shadow.log.dump()),
    ("feedback.json",    {"events": self.recorder.dump()}),
    ("intervention.json", self.intervention.dump()),
    ("canary_state.json", self.canary.dump()),
    ("proposals.json",   self.proposals.dump()),
):
    with open(os.path.join(self.persist_dir, name), "w", encoding="utf-8") as fh:
        json.dump(payload, fh, ensure_ascii=False, indent=2)   # ← 直接写，无 tmp+rename，无 fsync

# af_runtime_ext.py:93-108  restore()
def _read(name: str, default: Any) -> Any:
    path = os.path.join(self.persist_dir, name)
    if not os.path.exists(path):
        return default
    with open(path, "r", encoding="utf-8") as fh:
        return json.load(fh)        # ← 无 try/except

self.shadow.log.load(_read("shadow_log.json", []))
self.recorder.load(_read("feedback.json", {}).get("events", []))
self.canary.load(_read("canary_state.json", {}))
self.proposals.load(_read("proposals.json", {}))
```

**为什么是缺陷**：

1. **写不原子**：`open(...,"w")` 会先截断文件再写。进程在 `json.dump` 中途被杀（`SIGKILL`、OOM、容器驱逐——第一轮 BUG-01 正是 OOM 场景）就会留下**半截 JSON**。
2. **读无兜底**：`_read()` 没有异常处理。半截 JSON 让 `json.load` 抛 `JSONDecodeError`，直接穿出 `restore()`。
3. **后果是启动失败，不是降级**：`restore()` 位于运行时构造路径，异常会让**整个服务起不来**。运维唯一出路是手删损坏文件，代价是丢掉全部 shadow 试运行证据与 canary 状态。
4. **项目内部不一致**：同一个 `shadow_log.json`，`af_shadow.py:167 save()` 用的是 `atomic_write_text`（注释写明"随机 tmp + fsync，崩溃不留半截文件"），而这里用的是裸写。更讽刺的是，`af_shadow.py:351 install()` 对损坏日志**有**降级处理：

   ```python
   except Exception as exc:
       # 日志损坏不影响启动，但"历史判定丢了"这件事得留下痕迹
       self.replay_load_error = f"{type(exc).__name__}: {exc}"
   ```

   同一份损坏数据，走 `install()` 能降级启动，走 `restore()` 直接致命。

**修复建议**：

```python
# 1) persist() 走项目既有契约
from .af_atomic import atomic_write_text
atomic_write_text(Path(self.persist_dir) / name,
                  json.dumps(payload, ensure_ascii=False, indent=2))

# 2) restore() 的 _read() 加降级，与 af_shadow.install() 对齐
def _read(name, default):
    path = os.path.join(self.persist_dir, name)
    if not os.path.exists(path):
        return default
    try:
        with open(path, "r", encoding="utf-8") as fh:
            return json.load(fh)
    except (OSError, ValueError) as exc:
        self.restore_errors[name] = f"{type(exc).__name__}: {exc}"
        return default      # 损坏即回退默认值并留痕，不让启动失败
```

### 🟡 BUG-04（中危）`af_metrics.py` — 单条坏数据会把指标重发永久卡死

**位置**：`src/autoforge/af_metrics.py:222`

```python
for line in lines:
    metric = json.loads(line)        # ← 在 try 之外
    try:
        self._post_with_retry(metric, ma_url, token, http_post=http_post)
        flushed += 1
    except Exception:                # ← 只兜住网络发送，兜不住解析
        remaining.append(line)
if remaining:
    buf.write_text("\n".join(remaining) + "\n", encoding="utf-8")
```

**为什么是缺陷**：`json.loads` 在 `try` **之外**，所以只有"发送失败"被兜住，"解析失败"会直接抛出。而 `flush_buffer` 的语义是**错误恢复**——负责把上次没发出去的指标重发。一旦缓冲文件里出现一行坏数据（很可能正来自 BUG-03 同款的非原子写截断）：

1. `json.loads` 抛异常 → `flush_buffer` 整体失败；
2. 因为异常在写回之前抛出，`buf.write_text(remaining)` **永远不会执行**，坏行不会被剔除；
3. 缓冲文件原样保留 → **下次调用必然在原地再次失败**，形成永久卡死（poison pill）。

对比同仓库 `af_store.py:118 read_jsonl_bounded` 的正确写法——坏行 `continue` 跳过并继续读其余行，`flush_buffer` 缺的正是这一个 `continue`。

**修复**：把解析也纳入容错并跳过坏行：

```python
for line in lines:
    try:
        metric = json.loads(line)
    except ValueError:
        continue                      # 坏行剔除，不影响其余指标重发
    try:
        self._post_with_retry(...)
        flushed += 1
    except Exception:
        remaining.append(line)
```

## 五、跨轮观察

把两轮结果放在一起看，有一个共同的根因形状：

> **写盘没有统一收口。** 项目有 `af_atomic.atomic_write_text` 这条正确的契约，也在 `af_catalog` / `af_preference` / `af_error_knowledge` / `af_shadow.save` 等处遵守了，但在 `af_runtime_ext.persist()` 和 `af_metrics.flush_buffer()` 两处绕过，而这两处恰好是**崩溃恢复链**上最不能出错的地方。

建议的收敛动作（比逐个修 bug 更值钱）：

1. 给 `scripts/check_bounded_caches.py` 同级新增一个 **`check_atomic_writes.py`** 门禁：扫描所有 `open(...,"w")` + `json.dump` / `write_text` 的落盘点，凡写 `.forge/` 或 `*.json` 状态文件的，必须走 `atomic_write_text`，否则判红。项目已有 `check_atomic_write_sites.py`，可先确认它为何没覆盖这两处（很可能只扫了部分目录）。
2. 给 `restore()` 类的批量恢复入口定一条通则：**单个文件损坏不得阻断整体启动**，损坏信息统一落到 `restore_errors` 供 `/api/health` 暴露。
