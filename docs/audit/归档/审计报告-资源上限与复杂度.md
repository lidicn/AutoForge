## 三、确证缺陷

### 🔴 BUG-06（高危）`af_ir/condition_norm.py` — CNF 归一化做笛卡尔积，宽度无任何上限

**位置**：`src/autoforge/af_ir/condition_norm.py:44`（`_to_cnf`）、`:29`（`_nnf`）

`normalize_condition` 把条件表达式转成合取范式（CNF）。对 `or` 嵌套 `and`，分配律展开必然产生**笛卡尔积**——子句数随 `or` 分支数**指数增长**，而代码中没有任何预算参数或上限常量。

#### 实测（非静态推演）

构造 `(A₁∧B₁) ∨ (A₂∧B₂) ∨ … ∨ (Aₖ∧Bₖ)` 直接调用 `normalize_condition`：

| k | 表达式深度 | 节点数 | CNF 子句数 | 耗时 |
|---|---|---|---|---|
| 8 | 4 | 41 | 256 | 0.0007 s |
| 12 | 4 | 61 | 4 096 | 0.012 s |
| 16 | 4 | 81 | 65 536 | 0.30 s |
| 18 | 4 | 91 | （预计 262 144） | **进程被 OOM Killed（exit 137）** |

**关键：k=18 时表达式深度只有 4、节点数只有 91。**

#### 为什么现有上限拦不住它

`af_ir/expr.py` 明明定义了 `MAX_EXPR_DEPTH = 32`、`MAX_EXPR_NODES = 256`，且在 `_check_expr` / `_check_operand` / `_operand_value` / `evaluate` 中都有 `_Budget` 计数。但这两个上限**约束的是深度与节点总数，而这次爆炸是由「宽度」驱动的**：

- 深度 4 ≪ 32 ✅ 放行
- 节点 91 ≪ 256 ✅ 放行
- 结果：2¹⁸ 个子句 ❌ OOM

换句话说，**加深度上限或节点上限都修不好这个 bug**，必须针对「输出规模」设限。按节点上限反推，`MAX_EXPR_NODES=256` 允许 k≈85，即 2⁸⁵ 个子句——无论多深的栈都走不完。

#### 可达性

```
verify_roundtrip(ir)          # af_fidelity.py:196，__all__ 导出，公开 API
  └─ fidelity_equal(...)
       └─ project_automation(auto)     # af_fidelity.py:95
            └─ _node_core(node)        # af_fidelity.py:117
                 └─ normalize_condition(node.expr)   # ← 爆炸点
```

`condition_equivalent(a, b)`（`:86`）同样两次调用 `normalize_condition`。

诚实说明暴露面：包内**目前没有** `verify_roundtrip` 的直接调用点（仅在 `af_nl_build.py` 文档字符串中被引用）。它属于**公开库 API 隐患**——一旦被接入 MCP 工具、CLI 或测试入口并传入外部 IR，一次调用即可打挂进程。评级依此定为 high 而非 critical。

#### 修复建议

```python
MAX_CNF_CLAUSES = 1024   # 与 MAX_EXPR_NODES 同层的宽度预算

def _to_cnf(node, budget=None):
    ...
    # 每展开一层校验累计子句数，超限即抛错或退化为「不归一化」
    if len(result) > MAX_CNF_CLAUSES:
        raise ConditionTooComplex(...)   # 或返回未归一化的结构，保结构性等价但放弃 CNF
```

退化路径是可接受的：`condition_equivalent` 本就是**尽力而为**的等价判定，判不了就报「无法判定」，远好过把进程打挂。

## 四、已核验为良性 / 低风险

| 规则 | 命中 | 核验结论 |
|---|---|---|
| RSC-02 无预算递归 | 21 | 均为**树遍历型**递归（表达式树、IR 树、JSON 结构）。深度受 `MAX_EXPR_DEPTH=32` 与上游 `Automation.from_dict` 校验约束，栈深可控。真正危险的是宽度（BUG-06），不是这些递归 |
| RSC-03 无界读取 | 7 | 多为 HTTP 响应/本地状态文件的整体读取，规模有界。`af_metrics.py:218` 与 BUG-04 同址（坏行卡死），已计入台账 |
| RSC-01 组合爆炸 | 8 | 除 `_to_cnf` 外，其余为固定小规模集合的双层推导（intent 目录、dual-track 对比），输入规模受工具注册表约束 |
| RSC-04 ReDoS | **0** | 5 处嵌套量词经核验均不含「嵌套量词 + 可回溯」的危险组合 |
| RSC-05 上限不一致 | 2 | `af_ir/expr.py` 的 `_walk` / `_walk_operand`（引用收集用）未用预算，但它们是**线性**遍历（O(节点数)），非指数——属可接受取舍，记为低风险 |

贯穿四轮的形状仍然一致：**语义层严密，跨层收口薄弱**。本轮给这个判断补上了新的注脚——项目**有**资源上限意识（`MAX_EXPR_DEPTH`、`MAX_EXPR_NODES`、`read_jsonl_bounded`、deque 边界），但上限设在**输入维度（深度、节点数、行数）**，而真正的失控发生在**输出维度（展开后的子句数）**。输入受控 ≠ 输出受控，这是本轮最值得带走的一条。
