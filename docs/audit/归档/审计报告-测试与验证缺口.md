## 三、确证缺陷

### 🟠 BUG-16（中危）`af_draft._resolve_entity()` — 恒等透传占位，中文名原样进 IR 且绕过绑定回填

**位置**：`src/autoforge/af_draft.py:139-142`

```python
def _resolve_entity(name: str, catalog: Any = None) -> str:
    """把中文名解析成 entity_id。实际应该查 catalog。"""
    # TODO: 接 af_catalog 做真实解析
    return name  # 暂时透传，后续接 catalog
```

`catalog` 参数**被完全忽略**。

#### 实测复现

```
输入 '台灯'             → entity_id = '台灯'
输入 '书房灯'            → entity_id = '书房灯'
输入 '客厅空调'           → entity_id = '客厅空调'

draft_intent({when:{entity:'前门'}, do:{target:'客厅灯'}})
  → Trigger(entity_id='前门')
  → resolved = {'前门': '前门', '客厅灯': '客厅灯'}
```

#### 为什么比"功能未完成"更糟：**它绕过了两道安全机制**

`af_service.bind_ir` 的占位符回填机制（`:2141`）只处理**以 `?` 开头**的值：

```python
def _try(node_id, field, value):
    if not isinstance(value, str) or not value.startswith(BIND_PREFIX):
        return value          # ← '前门' 无 ? 前缀 → 原样返回
    ...
    unresolved.append({...})  # ← 也进不了 unresolved 统计
```

于是透传出来的中文名：

- **不会被回填**（无 `?` 前缀，绑定机制不认）
- **不会被计入 unresolved**（同上）
- **被当作"精确 entity_id"静默放行**——而绑定机制的 docstring 明写「不启用时 IR 必须写精确 entity_id」

`resolved` 字典还把它记成 `{'前门': '前门'}`，**看起来像是"已解析"，实际什么都没做**。下游若信任 `resolved`，就会拿着中文名去操作 Home Assistant。

#### 修复建议

二选一，取决于产品意图：

1. **接 catalog 做真实解析**（TODO 本意）——失败时 fail-closed：保留 `?` 前缀占位符，交安全闸拒编译（docstring 已明确「绝不静默猜域/猜实体」）。
2. **最低成本**：让未解析的名字带上 `BIND_PREFIX`（`?前门`），这样它至少会进入 `bind_ir` 的回填/`unresolved` 统计，不会再被当成精确 entity_id 静默放行。

### 一个跨轮的呼应：BUG-16 与 BUG-08 落在同一个模块链上

BUG-08 是 `af_catalog` 的缓存失效缺陷，BUG-16 是 `af_draft` 的 `_resolve_entity` **本该接 `af_catalog` 却没接**。也就是说：`af_catalog` 是实体解析的权威数据源，而它自己有陈旧读缺陷（实测 16/30），同时它的下游消费者又因为 TODO 未完成而根本没用上它。

**这解释了为什么这个 TODO 一直没被修**：即使接上了，拿到的也可能是陈旧数据（BUG-08）。两个缺陷互相掩盖。
