## 三、确证缺陷

### 🔴 BUG-07（高危）`af_runtime_plugins.py` — 同一个 `restore()`，两条安装路径给出**相反**的失败语义

**位置**：`src/autoforge/af_runtime_plugins.py:96-99`

```python
def restore(self) -> None:
    """从 .forge/ 恢复所有扩展模块状态。"""
    if self.grading is not None:
        try:
            self.grading.restore()
        except Exception:
            pass          # ← 完全静默：无日志、无审计、无返回
```

**证据链**：`self.grading` 来自 `af_runtime_ext.install(runtime)`（`:171`），即 `RuntimeExt` —— 正是第二轮 BUG-03 中 `_read()` 无异常保护、遇半截 JSON 会抛 `JSONDecodeError` 的那个对象。

于是**同一份损坏的 `.forge/` 状态，走两条不同的安装路径，结果完全相反**：

| 安装入口 | 调用 | 损坏时的行为 |
|---|---|---|
| `af_runtime_ext.install()` | `grading.restore()`（`:171`，无保护） | 异常传播 → **服务起不来**（BUG-03） |
| `af_runtime_plugins.install()` | `ext.restore()`（`:260`）→ 包裹 `except Exception: pass` | **静默吞掉 → 服务正常启动，grading/canary/shadow 状态全部为空** |

**为什么这条比 BUG-03 更值得关注**：

1. **静默丢生产状态**：置信度分级、canary 试运行、shadow 证据在重启后全部归零，且**没有任何日志、审计条目或返回值**表明这件事发生过。运维看到的是一个"干净启动"的服务，实际上它已经丢失了对历史判定的记忆。
2. **它掩盖了 BUG-03 的症状**：既然插件路径会吞掉异常，那么 BUG-03 描述的"启动崩溃"在生产中可能反而是**罕见**路径——真正常见的是静默丢状态。修 BUG-03（加降级）时如果不顺手修这里，降级逻辑根本不会被触发。
3. **代码库里已经有正确先例**：同一个文件的 `install()`（`:173-179`）在 `RuntimeExt` 安装失败时**是**记账的：

   ```python
   except Exception as e:
       runtime.audit.append({
           "kind": "runtime_ext_conf_grading_failed",
           "error": str(e),
           "at": runtime.clock.now(),
       })
   ```

   恢复路径只是没沿用这个模式。

**修复建议**：

```python
def restore(self) -> None:
    if self.grading is not None:
        try:
            self.grading.restore()
        except Exception as exc:
            # 与 install() 一致：失败必须留痕，不能静默以空状态启动
            self.restore_errors["grading"] = f"{type(exc).__name__}: {exc}"
            logger.error("扩展模块 grading 恢复失败，将以空状态启动：%s", exc)
            audit = getattr(self.runtime, "audit", None)
            if audit is not None:
                audit.append({"kind": "runtime_ext_restore_failed", "error": str(exc)})
```

## 四、正面结论：状态机实现合规

本轮专门检查了「绕过迁移表直接赋值」（ERR-06），结果 **0 命中**。核验 `af_instance.py`：

- 状态常量 `CREATED/ACTIVE/SUSPENDED/DONE/CANCELLED/FAILED/EXPIRED` + `TERMINAL_STATES`（`:41-49`）
- 唯一写入口 `_transition()`（`:400`）做两道校验：终态不可再迁移、`target not in _ALLOWED[current]` 抛 `IllegalTransition`
- 全部 7 处迁移调用（`:245/266/272/277/284/288/293`）**无一绕过**，仅 `:229` 的初始化赋值 `ctx.state = CREATED` 属构造期，合理

`IllegalTransition` 异常类确实被使用（不是定义了不用的死代码）。这是一个**设计良好的状态机**，记录为正面结论。

## 五、已核验为良性 / 可观测性缺口

| 规则 | 命中 | 核验结论 |
|---|---|---|
| ERR-01 finally 内跳转 | **0** | 无 `return`/`break`/`continue` 出现在 `finally` 中 |
| ERR-02 except 顺序遮蔽 | **0** | 未发现父类在前遮蔽子类的写法 |
| ERR-03 未定义异常名 | 11→**0** | 全部为导入名误判，逐一核验后确认为合法引用 |
| ERR-04 assert 校验 | 2 | `af_time.py:247-249` 的 `assert_clock_consistent()` —— 是**开发期自检**（"clock must be tz-aware"），非运行时输入校验，属合理使用 |
| ERR-05 except 完全静默 | 65 | 绝大多数是**有意的故障隔离**：`af_runtime_plugins.py:82` 注释明写"单个模块故障不阻塞其他模块"；`af_atomic.py:48/54`、`af_auth.py:91/102/110` 是清理路径的 `OSError: pass`。**但其中一处（`:96-99` 的 restore）不可接受**，已升格为 BUG-07 |
| ERR-06 状态机绕过 | **0** | 见第四节 |

关于 ERR-05 的 65 条：其中 64 条我判定为可接受的隔离/清理模式，**只有 1 条是真问题**。这个比例再次印证前几轮的经验——模式匹配只能定位候选，判定必须靠读源码。不过我要指出一个**系统性可观测性缺口**：这 65 处中绝大多数连 `logger.debug` 都没有。建议至少给"吞异常"统一加一条 debug 日志，成本极低，但在真出问题时是唯一的线索来源。

## 六、五轮累计

| ID | 严重度 | 主题 | 摘要 | 状态 |
|---|---|---|---|---|
| BUG-01 | high | 稳定性 | `node_visits` 实例级无界增长 + `resume()` 无步数防护 | still_open |

| BUG-03 | high | 崩溃恢复 | 非原子写 + 无保护读取，一次崩溃致启动失败 | still_open |
| BUG-04 | medium | 崩溃恢复 | 坏行卡死指标重发 | still_open |

| BUG-06 | high | 复杂度 | CNF 归一化笛卡尔积无宽度上限（实测 OOM） | still_open |

BUG-03 与 BUG-07 是**同源的两个面**：一个崩溃、一个静默。放在一起修才有效——只修 `_read()` 的降级（BUG-03）而不去掉 `except: pass`（BUG-07），降级永远不会被触发；只去掉 `pass` 而不修 `_read()`，则会把"降级启动"变成"启动崩溃"。

### 贯穿五轮的形状

> 这个项目的**控制流正确性**（状态机、锁的可重入、async 用法、图遍历的环检测）做得相当扎实，本轮 6 条规则里有 4 条零命中。薄弱处依然在**跨层收口**——而现在可以更精确地说：薄弱在**失败语义不统一**。同一个 `restore()`，两条路径一个崩、一个哑；同一个 `shadow_log.json`，`install()` 能降级、`persist()` 会致命；同样是落盘，有的模块走 `atomic_write_text`、有的裸写。代码不缺正确的写法，缺的是把正确写法变成唯一路径的约束。
