## 三、确证缺陷

### 🟠 BUG-09（中危）`af_undo.py` — 撤销时间窗用墙上时钟，时钟回拨使过期判定失效

**位置**：`src/autoforge/af_undo.py:293`（写入）、`:353`、`:379`、`:403`（判定）、`:467`（清理）

```python
# 写入（:293）
"ts": self._clock.now().timestamp(),          # 墙上时钟 epoch 秒

# revert 过期判定（:403）
if self.window_s > 0 and (self._clock.now().timestamp() - float(rec.get("ts", 0))) > self.window_s:
    return {"ok": False, "reason": "expired", ...}

# purge 清理（:467-471）
if window <= 0 or (now - float(rec.get("ts", 0))) <= window:   # 保留
```

`ts` 必须落盘（`undo_log.json`）才能跨进程/重启生效，所以**用墙上时钟是合理的取舍**——单调时钟没有跨进程意义。问题在于判定没有处理回拨。

#### 实测复现

```
落盘 ts = 1791257106.237285
（系统时钟被回拨 600 秒后）
回拨后 age = -600.0s  （负数）
revert 过期判定 (age > window_s): False  → 判为「未过期」，撤销仍可执行
purge  保留判定 (age <= window):  True   → 判为「保留」，记录不被清理
```

**结论：时钟回拨使 age 为负 → 撤销记录永不过期，永久滞留 `undo_log.json`。**

#### 影响

- **安全语义被绕过**：撤销窗口（`window_s`，默认 60s、上限 `MAX_WINDOW_S=300`）的设计意图是"超窗需重新走审批闸门"。回拨后一条几小时前的部署记录仍能被 `revert()` 回放——**风险域（climate/cover/lock）的撤销本应有时效约束，此时约束失效**。
- **`purge_expired()` 失去作用**：它存在的目的是"避免无限增长"（docstring 明写），回拨状态下一条都清不掉。
- 触发条件很现实：NTP 校正、容器/宿主时间同步、虚拟机恢复快照、手动改表。

#### 修复建议

`ts` 落盘仍需墙上时间，但判定可以对负 age 显式处理——这是最小改动且必然正确：

```python
age = self._clock.now().timestamp() - float(rec.get("ts", 0))
if age < -AGE_SKEW_TOLERANCE_S:      # 时钟回拨/跳变
    # 无法判定真实年龄 → fail-closed：视为过期，要求重新审批
    return {"ok": False, "reason": "clock_skew", ...}
if self.window_s > 0 and age > self.window_s:
    return {"ok": False, "reason": "expired", ...}
```

`purge_expired()` 同理：负 age 的记录应**清理**而非保留（无法判定年龄 ⇒ 按最保守清理，或至少记一条告警）。

更彻底的方案是落盘同时存墙上时间与进程内单调基准，但**负 age 检测**是成本最低的修复。

### 对整体判断的补充

前六轮我把根因归为三类（写入路径不统一、失败语义不统一、缓存失效不统一）。BUG-09 给出第四类：**「有意的取舍，但取舍的代价没有被处理」**。

`ts` 必须落盘所以用墙上时钟——这个决策是对的。错误在于只做了取舍、没处理代价（回拨）。这类问题比"忘了加锁"更难发现，因为代码看起来是深思熟虑的（`TimeSource` 注入、单调时钟、`MAX_WINDOW_S` 上限都有），只有把"如果时钟跳变会怎样"这个前提显式问出来才暴露。

至此四轮（06/07）都有实测复现的缺陷（BUG-06 OOM、BUG-08 陈旧读、BUG-09 时钟回拨）。**静态规则给出候选，实测给出确定性**——这是我这七轮下来最有效的一条方法论。
