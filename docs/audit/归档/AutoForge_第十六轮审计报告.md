## 一句话结论

**本轮没有新增缺陷，但发现了审计流水线本身一个此前没被识别的环境风险：外部工具在本沙箱里**每次 bash 调用都会丢失**，必须在同一次调用内先补装再扫描。**

---

## 一、开场即失败：第十四轮装的工具全部消失

第十六轮开场跑门禁直接失败：

```
[FAIL] external_tool_defects 在 dirty（已知缺陷样本）上 **0 命中** —— 规则可能已静默失效
```

排查发现 `/usr/local/bin/bandit`、`detect-secrets`、`pip-audit` **全部不存在**——第十四轮装的工具没了。

**这次是门禁救的场**：那条"0 命中要怀疑规则失效"的检查（PITFALLS N1）把"工具没了"暴露成了 FAIL，而不是安静地记为"本次无发现"。但它的报错方向是错的——**说"规则可能失效"，真实原因是"工具没了"**。诊断方向错了，修起来就是白费劲。

### 更深一层的发现：不持久是「每次调用」级别，不是「轮次之间」

补装后继续跑第十六轮扫描，中间隔了一次 bash 调用，`external_tool_defects` 又变成 0 命中。实测确认：

| 方式 | 结果 |
|---|---|
| 分开调用（先装 → 换一次 bash → 再扫） | 0 命中，status=`tools_missing` |
| **同一次 bash 调用内**（装完立刻扫） | **3 条命中，total 1083，与前两轮一致** |

也就是说，**pip 装的外部工具在本沙箱的每一次 bash 调用内有效，跨调用即失效**。这比"轮次之间重置"严重得多——意味着任何跨调用的流程编排都可能静默丢掉外部工具能力。

## 二、工作流迭代（3 项）

### W41：`external_tool_defects` 显式区分三种状态

原先工具缺失时返回 0 命中，与"扫过没问题"在输出上完全无法区分。现在输出 `status`：

| status | 含义 |
|---|---|
| `tools_missing` | 外部工具全部不可用 ⇒ **环境缺口，不是审计结论** |
| `ok` | 扫过且有命中 |
| `ok_but_no_hit` | 工具可用但确实没命中 |

门禁据此给出不同的失败原因：工具缺失时提示"跑 `scripts/ensure_tools.py` 补装"，而不是笼统说"规则可能失效"。

### W42：`scripts/ensure_tools.py` —— 工具就绪检查 + 自动补装

逐个 `shutil.which` 检查，缺的用 pip 装，装不上的如实标记原因（`semgrep` 安装期 `OSError [Errno 27] File too large`；`pip-audit` 受网络策略阻断）。

**并作为门禁第 31 项固定下来**，同时成为 `auditkit` 的 `[1/11]` 阶段——**排在自检门禁之前**。理由很直接：外部工具相关的所有结论都建立在"工具在不在"之上，工具不在，自检门禁跑出来的绿灯也没有意义。

### auditkit 10 阶段 → 11 阶段

```
[1/11] 工具就绪      外部工具随环境重置会消失，先补装再开工
[2/11] 自检门禁      ...
```

## 三、调试中踩的坑（第三次同类）

门禁读 `ensure_tools --json` 时用 `splitlines()[-1]` 取最后一行解析，而输出是 `indent=2` 的多行 JSON，最后一行只是一个 `}` ⇒ JSONDecodeError。

**这与第十五轮 `poc_outbound`、`audit_deps` 踩的是同一个坑**：按"最后一行"取 stdout 的前提是单行输出。已统一改为整体解析，失败再退回"从首个 `{` 起"解析。

三次同类事故说明这不该靠每次记住，而该靠约定——**跨进程传结构化数据一律读落盘文件，或整体解析 stdout**。

## 五、十次同类事故的完整画像

本轮是第九次。把它和前八次放一起看，形态高度一致：

| # | 轮次 | 失效源 | 表现 |
|---|---|---|---|
| 1 | 2 | 自建：`scripts/` 漏扫 | 125 条"缺陷消失"实为漏扫 |
| 2 | 4 | 自建：写盘别名缺失 | 规则安静地什么都不报 |
| 3 | 6 | 自建：RES-03 全文件正则 | "缺陷消失"实为规则失效 |
| 4 | 8 | 自建：抑制锚点用行号 | 抑制静默失效 |
| 5 | 9 | 自建：glob 跳过点目录 | 目标全程"测不到" |
| 6 | 11 | 自建：`_fetch_stub` 实体不全 | 手工与机器结论打架 |
| 7 | 12 | **补丁**：少导入 + 被宽 except 吞 | 修了但没人看得见 |
| 8 | 14 | **外部工具**：bandit 认不出间接调用 | 4 处只报 2 处 |
| 9 | 16 | **环境**：工具跨调用丢失 | 0 命中伪装成"无发现" |

**共同点全部是：表现为"结论变好 / 命中变少"，而不是报错。**

前七次失效源在我们写的代码里，第八次在外部工具的能力边界上，第九次在**环境持久性**上——超出了代码本身。这提示下一类风险可能来自更外围：依赖版本漂移、时区、文件系统行为差异等。

对应的通用纪律仍是那一条：**任何"看起来修好了"或"看起来没了"，先怀疑工具与环境，再相信结论。**
