## 〇、本轮前置：深度研究产出

委托研究已产出 `/data/workspace/audit/research/横切约束修复范式与门禁设计.md`（33KB），核心结论四条：

1. **根因确认**：十个缺陷的共同形状是「单点正确没有上升为全局不变量」。建议收敛出**不超过十条**可证明的全局不变量（状态文件必经原子写入口、env 数值必经 fail-safe 解析、模块级配置副作用只在显式加载点、自写回读缓存必须随写失效）。
2. **原子写**：`os.replace` 不等于崩溃安全——还需同挂载点 tmp、随机名、fsync 文件、fsync 目录。门禁必须覆盖**负空间**（没有用原子写的站点），且**状态路径清单为空时应判红而非假绿**。
3. **缓存**：`(mtime, size)` **即使纳秒化也不可作为强一致依据**（同一 jiffy 内同长度多次写入仍生成相同键）；同进程写后读应首选**显式失效**。这与我第八轮实测结论一致。
4. **门禁通法**：门禁必须区分「已违规 / 已合规 / **无法证明**」三态；扫描器找不到可验证锚点时**不得返回绿**，应非零退出。

研究报告已交付，可作为后续横切约束门禁设计的依据。

## 三、确证缺陷

### 🔴 BUG-11（高危）`af_store.import_bundle(strategy="overwrite")` — 删旧成功后写入前失败，归档不可逆丢失

**位置**：`src/autoforge/af_store.py:561`（调用点）、`:470-495`（`_delete_archive`）

```python
# import_bundle（:561-567）
# overwrite 策略：全部版本校验通过后才删除旧归档（避免校验失败时历史不可回滚）
if self.versions(name) and strategy == "overwrite" and not entry_has_error:
    self._delete_archive(name)      # ← 不可逆
# 合法版本仍然写入
for ver, graph_dict in validated:
    self.save_version_raw(...)      # ← 若上一行之后、这里之前失败，旧数据已不在

# _delete_archive（:477-495）
for p in directory.glob("v*.json"):
    p.unlink()                      # ① 删主体
if conf_path.exists():
    conf_path.unlink()              # ② 删置信度
with FileLock(self.root / "tags.lock", timeout=self.lock_timeout):
    ...
    atomic_write_text(self._tags_path(), ...)   # ③ 最后才写标签侧车 → 可抛
```

#### 实测复现

构造真实归档（`examples/ir/case01_day_light.json`），用 `overwrite` 导入，并让 `_delete_archive` 的最后一步（写 tags 侧车）失败：

```
导入前：版本= [1]  文件数= 1   tags= ['t1']
import_bundle 抛异常： OSError 模拟 tags 侧车写入失败（磁盘满 / 锁超时）
导入后：版本= []      归档目录存在= True
         tags 残留= ['t1']
>>> 旧归档已删除、新版本未写入 → 不可逆丢失
```

**三重后果**：① 旧版本 `v1.json` 已被 `unlink` 删除；② 新版本从未写入（异常在 `save_version_raw` 之前抛出）；③ `tags.json` 里仍残留 `demo → ['t1']` 的**孤儿元数据**。用户视角只看到「导入失败」，实际归档已消失。

#### 为什么 P1-17 没修住

代码注释明写「P1-17 修复——先删除已存在归档，再导入」和「全部版本校验通过后才删除旧归档（**避免校验失败时历史不可回滚**）」。这个修复**解决了校验失败的场景，但没解决删除成功、写入失败的场景**：

| 时序 | P1-17 前 | P1-17 后（现状） |
|---|---|---|
| 校验失败 | 旧归档已被删 ✗ | 不删，历史可回滚 ✓ |
| 删除后写入失败 | 旧归档已删 ✗ | **旧归档仍被删 ✗** |

触发条件现实：tags.lock 超时（并发导入/多进程写）、磁盘满、`atomic_write_text` 失败。

#### 修复建议

删除不可逆，所以**绝不能是第一个动作**。推荐 rename 备份法：

```python
if self.versions(name) and strategy == "overwrite" and not entry_has_error:
    backup = self._backup_archive(name)      # rename 到 {name}.bak.<ts>，不删
try:
    for ver, graph_dict in validated:
        self.save_version_raw(...)
    self.set_tags(target, ...)
    if backup:
        self._purge_backup(backup)           # 全部成功后才真删
except Exception:
    if backup:
        self._restore_backup(backup, name)   # 失败则恢复旧归档
    raise
```

最低成本方案：把 `_delete_archive` 里**写 tags 侧车那一步挪到删除之前**，或让它在失败时不抛异常（标签是元数据，删不掉可以留痕后续清理）——但 rename 备份法才真正闭合窗口。

## 四、已核验为良性（18 条）

| 规则 | 命中 | 核验结论 |
|---|---|---|
| TX-04 先删后写 | 1 | **真缺陷**，见上一节（BUG-11） |
| TX-01 多写无事务 | 11 | 10 条良性：`af_undo._save`（`tmp.write_text` + `tmp.replace` 是原子写正常形态）、`af_insight_queue.move_to`（**先写 decided 再 unlink 源，顺序正确**）、`af_shadow.save`（`dump` 是序列化非落盘）、`af_service.start_watch`（均写临时文件）、`af_api.build_app`（跨数百行装配函数，非同一事务） |
| TX-02 写入顺序违反依赖 | **0** | 无 |
| TX-03 先落盘后校验 | **0** | **正面结论**。未发现「校验可能 reject 却写在校验之前」的顺序颠倒。`import_bundle` 甚至显式做了「先全部校验后删除」（P1-17） |
| TX-05 内存/磁盘顺序 | 5 | 均为低危提示，落盘后更新内存态属常见且可接受模式（崩溃重启会重读磁盘） |
| TX-06 跨模块镜像 | 2 | 未确认存在真实镜像关系，仅为提示 |

**关于 TX-01 的高假阳性率**：11 条里 10 条良性。原因是「一个函数内有多个落盘调用」这个形状本身太宽——原子写的 tmp+replace 天然是两次调用，批量移动天然是写+删。后续若复用该规则，应先把「已知原子写形态」和「先写后删的移动语义」加入白名单。

### BUG-11 让根因图谱补上了最后一类

前八轮我归纳出四类根因（写入路径不统一、失败语义不统一、缓存失效不统一、有意取舍的代价未处理）。BUG-11 是第五类：**不可逆操作的时序**。

共同点是**失败语义不完整**——但更精确地说，是这个项目在「**先做什么、后做什么**」上缺少一条统一的规则：

| 场景 | 现状顺序 | 安全顺序 |
|---|---|---|
| `import_bundle(overwrite)` | 删旧的 → 写新的 | 备份 → 写新的 → 成功才删备份 |
| `af_insight_queue.move_to` | 写新的 → 删旧的 ✓ | 已是安全顺序 |

项目里 `move_to` 做对了（先写后删），`import_bundle` 没做对。**又一次：正确写法存在，但没变成唯一路径。**
