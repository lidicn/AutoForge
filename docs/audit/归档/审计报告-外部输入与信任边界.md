## 三、确证缺陷

### 🔴 BUG-10（高危）模块级 `int/float(os.getenv(...))` 无解析保护 —— 脏环境变量使整个包导入即崩溃

**位置**（7 处同类站点）：

| 位置 | 层级 | 影响 |
|---|---|---|
| `af_undo.py:52` `DEFAULT_WINDOW_S = float(os.getenv("AUTOFORGE_UNDO_WINDOW_S", "60"))` | **模块级** | 导入即崩 |
| `af_undo.py:57` `MAX_DEPLOYS = int(os.getenv("AUTOFORGE_UNDO_MAX_DEPLOYS", "200"))` | **模块级** | 导入即崩 |
| `af_service.py:1354` `SESSION_TTL_S` / `:1357` `SESSION_MAX` | **模块级** | 导入即崩 |
| `af_config.py:158` `_CONFIG_TTL_S` | **模块级** | 导入即崩 |
| `af_service.py:1069`、 `af_api.py:258` | 函数级 | 调用即崩（后者在 `build_app`，服务起不来） |

#### 实测复现

```
--- 设置 AUTOFORGE_UNDO_WINDOW_S=''
    import autoforge.af_undo   → ValueError: could not convert string to float: ''
--- 设置 AUTOFORGE_UNDO_MAX_DEPLOYS='abc'
    import autoforge.af_undo   → ValueError: invalid literal for int() with base 10: 'abc'
--- 设置 AUTOFORGE_CONFIG_TTL_S=''
    import autoforge.af_config → ValueError: could not convert string to float: ''
```

**关键是「模块级」**：这 5 个常量在 import 时求值，异常发生在**包加载阶段**——不是某个功能不可用，而是 `import autoforge.af_undo` 直接失败，连带所有依赖它的入口（HTTP 服务、CLI、MCP 服务器）一起起不来。运维端的表现是「改了个环境变量，服务再也启动不了，且报错栈指向 import 语句而非配置项」。

触发条件非常常见：docker-compose 里 `AUTOFORGE_UNDO_WINDOW_S=`（写了键但没给值）、写成 `"12s"` 这类带单位的值、复制粘贴带了空格。

#### 代码库里已有正确先例

`af_bus.py:25` 的 `_env_number()` 正是为这个问题写的：

```python
def _env_number(name, default, *, lo=None, hi=None) -> float:
    """读取数值型环境变量，解析失败 / 越界时回落默认（fail-safe 而非 fail-crash）。
    P1-7 修复：原实现直接 `int(os.getenv(...))`，运维写错（如 "12s"、空串、超范围）
    会让 EventBus 构造即抛 ValueError，服务起不来。"""
```

对照实测：同一个脏值下，`_env_number("AUTOFORGE_UNDO_WINDOW_S", 60.0)` 正确返回 `60.0`。

**P1-7 修好了一处，但没有把正确做法推广** —— 这正是我在前几轮反复看到的形状：`_env_number` 是好写法，缺的是把它变成唯一路径的机制。

#### 修复建议

```python
# 1) 把 _env_number 从 af_bus 提升到公共模块（如 af_env.py），全仓复用
# 2) 五处模块级常量改为：
DEFAULT_WINDOW_S = _env_number("AUTOFORGE_UNDO_WINDOW_S", 60.0, lo=0, hi=300)
MAX_DEPLOYS      = int(_env_number("AUTOFORGE_UNDO_MAX_DEPLOYS", 200, lo=1))
```

注意 `af_undo.py` 的 `DEFAULT_WINDOW_S` 上限应与既有 `MAX_WINDOW_S = 300.0` 对齐（现代码在 `:271` 再做 `min(MAX_WINDOW_S, ...)`，若 env 直接给 9999 也不会崩但语义更乱）。

## 四、信任边界：本轮核验为**良好**（正面结论）

本轮专门检查了几处最容易出事的地方，**均有正确防护**，逐条记录以免后续重复排查：

| 检查点 | 位置 | 防护 | 结论 |
|---|---|---|---|
| 归档名路径遍历 | `af_store._dir()` (`:148-151`) | 白名单 `c.isalnum() or c in "-_"` 替换非法字符，明确注释「防止 `../` 目录逃逸」 | ✅ |
| 删除前归属核对 | `af_store.assert_deletable()` (`:178`) | 遍历目录内**每一条**记录核对 `name`，混入他人记录即抛 `ArchiveNameConflict` → 409 | ✅ 且比写入路径更严格 |
| SPA 静态托管回退 | `af_api.py:1214-1219` | `candidate = (dist / full_path).resolve()` + `str(candidate).startswith(str(dist))` 双重校验 | ✅ |
| X-Forwarded-For 伪造 | `af_api.py:268` | 默认**不信任** XFF，仅 `AUTOFORGE_TRUST_PROXY=true` 时才取 | ✅ 注释明写「可伪造」 |
| MCP 工具参数异常 | `af_mcp.dispatch()` (`:905-909`) | `except Exception` 统一转 `isError=True`，且**不回传 traceback**（R-57：防路径/行号外泄） | ✅ |
| MCP 未声明参数 | `af_mcp.dispatch()` (`:880-892`) | `_undeclared_args()` 对账 inputSchema，未声明键一律拒 | ✅ 注释记录了这是 fp-authcode-bruteforce 的修复 |

**关于我在 MCP 面命中的 8 条 `int(args[...])` 无 try**（`_t_diff` / `_t_list_entities` / `_t_experience` / `_t_telemetry` 等）：经核验**不构成缺陷**——`dispatch()` 的兜底会把 `ValueError`/`KeyError` 转成结构化 `isError` 回执并落服务端日志，行为是优雅降级而非崩溃。这是**有意的单层兜底设计**，我在报告里保留记录但不升格。

### BUG-10 与 BUG-05 是同一个形状

BUG-05 是「正确做法（`atomic_write_text`）没有被推广，门禁也只守半边」；BUG-10 是「正确做法（`_env_number`）没有被推广」——两者**都带着写明修复缘由的注释**（`af_bus.py:30` 的 "P1-7 修复"、`check_atomic_write_sites.py` 的 docstring），说明作者清楚问题所在，但修复止步于单点。

这是八轮下来最稳定的一条结论：

> 这个项目不缺正确的写法，缺的是**把正确写法变成唯一路径的机制**。已有的 16 个架构门禁覆盖了架构层面，但「落盘必须原子」「env 必须 fail-safe 解析」这类**横切约束**没有对应的门禁。

建议的收敛动作（比逐个修 bug 更值钱）：新增两个门禁脚本——
1. `check_env_parsing.py`：扫描所有 `int/float(os.getenv(...))`，凡不经过 `_env_number` 判红（与既有 `check_atomic_write_sites.py` 同构）
2. `check_atomic_write_sites.py` 补判据 E（BUG-05 已有建议）
