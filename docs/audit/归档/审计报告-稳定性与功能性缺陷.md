# AutoForge 稳定性与功能性缺陷审计报告

- **审计对象**：`github.com/lidicn/AutoForge`（main，commit `f0184de9`，2026-10-05）
- **审计目标**：发现影响**稳定性**与**功能性**的缺陷（非安全漏洞视角）
- **审计范围**：`src/autoforge/` 共 98 个 Python 模块
- **审计日期**：2026-10-06
- **审计方法**：项目自带架构门禁 + 自定义稳定性规则集（22 条）+ AST 缺陷分析 + 人工源码核验

---

## 一、结论摘要

| 项目 | 结果 |
|---|---|
| 确证缺陷 | **1 项（高危）** —— 实例级列表无界增长 + 跨段循环无防护 |
| 潜在缺陷 | 1 项（低危，当前未触发） |
| 项目自带门禁 | 16 项中 **15 项通过**，1 项因沙箱无 git 无法运行 |
| 硬编码密钥 | 0 |
| 除零 / 索引越界 / 竞态锁 / 线程 | 经抽样核验**全部有防护** |

**总体判断**：AutoForge 代码质量高于同类项目平均水平。它自带 16 个架构门禁脚本（`scripts/check_*.py` + `gates.sh`），在除零、索引越界、锁的获取释放、线程 daemon 设置等易错点上**均有显式防护**，自定义规则集的 107 条命中经人工核验后绝大多数为误报。发现的确证缺陷属于**长驻服务场景下的资源泄漏**，在短命 CLI 调用中不会暴露，但在 `forge serve` 常驻模式下会持续恶化。

## 二、确证缺陷

### 🔴 BUG-01（高危）`af_executor.py` — `node_visits` 实例级无界增长，且为死代码；`resume()` 无步数防护

**位置**：`src/autoforge/af_executor.py:111`（定义）、`:133`（追加）

**证据链**：

```python
# af_executor.py:109-111
def __post_init__(self) -> None:
    self.pending_asks: dict[str, AskSession] = {}
    self.node_visits: list[str] = []          # ← 实例属性，非局部变量

# af_executor.py:133（run() 主循环内，每次进入节点执行）
self.node_visits.append(f"{auto.id}:{node_id}")
```

全文件范围内 `node_visits` **仅出现这 2 处**：一次定义、一次 `append`。**没有任何读取、清理或裁剪**。

**为什么是缺陷**：

1. **无界增长**：`NodeExecutor` 是长驻 dataclass（持有 `InstanceManager`、`AdapterRegistry`）。`node_visits` 挂在实例上，跨**所有自动化实例**、跨**所有 `run()` / `resume()` 调用**持续累积。每次执行任何一个节点就追加一条字符串（`auto.id:node_id`）。常驻模式下按天累积可达百万级条目，内存单调上涨，直至 OOM。
2. **是死代码**：追加的数据从未被读取。项目已有 `af_bounded_caches.py` 与 `scripts/check_bounded_caches.py` 门禁——说明作者**有**缓存边界意识，但这两个机制**未覆盖** `node_visits`。
3. **掩盖了真正该做的防护**：`MAX_STEPS_PER_SEGMENT = 1000` 只在 `run()` 内生效（`steps` 是 `run()` 的局部变量，每次调用重置）。而 `resume()`（`:166`）**没有步数计数**。这意味着**段间循环**（`ask → suspend → resume → ask → suspend …`）无防护——每一次 `run()` 都在 1000 步内合法退出，但整体可以无限循环下去。`node_visits` 恰恰**本可以提供跨段循环检测的数据**，却从未被读取。

**影响**：
- 短命 CLI 调用（`forge run` 单次执行）：不可见。
- 常驻服务（`forge serve` / 调度器）：内存单调增长 → OOM 重启；且理论上存在段间无限循环风险。

**修复建议**（三选一，推荐 1+3 组合）：

```python
# 方案 1（最小改动）：既然无人读取，直接删除 :111 与 :133 两行
# 方案 2：改为有界结构，保留数据供调试
from collections import deque
self.node_visits: deque[str] = deque(maxlen=1000)
# 方案 3（推荐，治本）：把 steps 提升为实例级，让 MAX_STEPS_PER_SEGMENT 同时约束 run() 与 resume()，
#            或直接用 node_visits 做跨段重复访问计数，超限即 _fail(instance, "疑似跨段死循环")
```

### 🟡 BUG-02（低危·潜在）`af_orchestrator.py` — `or` 默认值陷阱使 `max_attempts=0` 失效

**位置**：`src/autoforge/af_orchestrator.py`（`_fix_loop`）

```python
budget = max_attempts or self.max_fix_attempts
```

`0` 是 falsy，因此**显式传入 `max_attempts=0`（意图"不重试"）会被静默替换为默认重试次数**。当前所有调用方均未传该参数，故**暂时未触发**；但这是一个等待被调用的陷阱。

**修复**：`budget = self.max_fix_attempts if max_attempts is None else max_attempts`

## 五、审计方法与工具链

| 阶段 | 工具 | 说明 |
|---|---|---|
| 门禁复跑 | 项目自带 `scripts/check_*.py` | 复用作者自己的契约 |

| 密钥 | `detect-secrets` | 0 命中 |

### 方法论局限（诚实说明）

1. **静态分析误报率高**：稳定性规则集 107 条命中中，人工核验后**仅 1 条为真缺陷**（命中率约 1%）。AST 混合返回分析器首版产生 92 条高危，修正终止性判断（穿透 `with`/`try`/`if`）后降至 19 条，抽样 6 条**全部为误报**——该分析器精度不足，**其产出未被采纳为结论**。所有结论均以人工源码核验为准。
2. **动态行为未验证**：沙箱无法运行项目（`pytest-homeassistant` 等依赖不可装），BUG-01 的内存增长为**静态推演**，未实测复现。
3. **依赖漏洞未扫**：`pip-audit` 因沙箱网络受限不可用。

## 六、优先修复建议

| 优先级 | 项目 | 动作 |
|---|---|---|
| P0 | BUG-01 | 删除 `node_visits` 或改为 `deque(maxlen=N)`；将步数计数提升到实例级以覆盖 `resume()`，堵住段间循环 |
| P1 | BUG-01 复防 | 在 `scripts/check_bounded_caches.py` 中新增规则：检测所有实例级 `list` 的 `append` 是否有对应裁剪/读取，防止同类泄漏再次引入 |
