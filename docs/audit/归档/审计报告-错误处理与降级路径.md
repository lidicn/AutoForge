## 三、确证缺陷

### 🟠 BUG-13（中危）`af_conflict_runtime.py` — 降级记账自身无保护，使「故障优先」降级失效且吞掉原异常

**位置**：`src/autoforge/af_conflict_runtime.py:450`（`_audit_degraded`）、`:~300`（`dispatch` 降级分支）

`dispatch()` 的设计意图是**故障优先**：仲裁器本身出故障时，宁可放行动作也不能让整个执行链卡死：

```python
try:
    decision = self.arbiter.request(...)
except Exception as exc:                    # 故障优先：降级 ALLOW
    self._audit_degraded("request", exc, entity_ids[0], automation_id)  # ← 记账
    decision = RequestDecision.ALLOW        # ← 放行
```

而 `_audit_degraded()` 内部**没有任何保护**：

```python
def _audit_degraded(self, phase, exc, entity_id, automation_id) -> None:
    ...
    self.auditor.record(...)                # ← 无 try；审计 JSONL 写盘失败即抛
```

#### 实测复现

同时构造两个故障：仲裁器内部错误（`RuntimeError`）+ 审计写入失败（`OSError`）：

```
dispatch 抛异常: OSError : 审计 JSONL 写入失败（磁盘满/权限）
→ 本应 ALLOW 放行，动作未执行
→ 原始故障 '仲裁器内部故障' 是否保留: False
```

#### 双重后果

1. **降级反而更严格**：设计意图是"仲裁器挂了就放行"，实际是"仲裁器挂了 + 审计也挂了 → 动作被完全阻断"。**降级机制自身的失败，让系统比不降级时更保守**。
2. **真因丢失**：`RuntimeError("仲裁器内部故障")` 不在异常链上，运维只看到 `OSError: 审计 JSONL 写入失败`，会去修磁盘而不是修仲裁器。

#### 影响面

`_audit_degraded` 共有 **13 处调用点**，全部位于 `except` 分支内——也就是说**每一条降级路径都依赖这个不受保护的记账函数**：

`dispatch` / `handle_state_change` / `handle_intervention` / `_on_pending_ready` / `_retry` / `_abort` / `_safe_release` / `_note_af_actions` 等。

审计是 append-only JSONL，写盘失败很现实：磁盘满、只读挂载、权限变更、并发写。

#### 修复建议

**记账绝不能影响业务降级路径**——把它降为日志即可：

```python
def _audit_degraded(self, phase, exc, entity_id, automation_id) -> None:
    ...
    try:
        self.auditor.record(ev)
    except Exception:                      # 审计失败不影响业务降级
        logger.warning("冲突降级审计写入失败（phase=%s）：%s", phase, exc)
```

这与项目既有原则一致：`af_metrics._record_bucket` 的注释正是「遥测失败绝不影响解析本身」。

## 四、已核验为良性（含四组假阳性记录）

| 规则 | 命中 | 核验结论 |
|---|---|---|
| ERRH-05 无超时 | 623→**0** | **全为假阳性**。`NET_CALL` 正则过宽，误伤 `dict.get()`、本地 session、`_per_session.get(`。收紧后无真实缺失超时的网络调用 |
| ERRH-01 重试吞异常 | 2 | **误报**。`af_metrics._post_with_retry` 实现正确：成功即 `return`，重试耗尽后 `raise last_err`（在循环外）。规则没能识别"raise 在循环外" |
| ERRH-01 尾部 sleep | 1 | **误报**。同上，`sleep` 位于 `if attempt < ...` 内，不影响最后一次的 raise |
| ERRH-04 半开态并发 | 3 | **误报**。`af_conflict._circuit_gate` 用 `cd.trial_inflight` 标志位保证半开态只放一次探测。实测三次连续调用：`r1=None`（放行）、`r2/r3=CIRCUIT_OPEN`（拒绝）——**单探测许可生效**。虽无 `threading.Lock`，但已满足设计意图 |
| ERRH-02 降级伪装成功 | 61 | 抽样核验多处为**正确的 fail-safe / fail-closed**：`af_canary.has_drift()` 读不到即 `return True`（保守判定有漂移）、`af_flock.held_by_other()` 同理、`af_api.authenticated()` 未配置/未携带/无效均返回 `None`（fail-closed）。**降级时"返回保守值"与"伪装成功"语义相反，规则无法区分** |
| ERRH-06 无清理 | 1 | `af_live.__init__` 为低危提示，未确证资源泄漏 |

**关于 ERRH-02 的 61 条**：这是本轮精度最差的部分，也是最值得记的一条教训。`return True`（保守）与 `return True`（假装成功）在语法上完全一样，**判定只能靠读上下文语义**。我把它们全部保留在产物 JSON 中标记 low，未升格。

### BUG-13 是第七类根因，也是最微妙的一类

前六类根因（写入路径、失败语义、缓存失效、取舍代价、操作顺序、跨层契约）都是"做错了什么"。BUG-13 是**"兜底机制本身不设兜底"**：

> 降级路径、记账路径、遥测路径这些"辅助设施"，它们的失败**不应该**影响主流程——但项目里它们往往与主流程共用同一个不受保护的调用点。

同类形状在前面几轮出现过：
- BUG-07：插件 `restore()` 的 `except: pass`（兜底本身吞掉了故障）
- BUG-04：`flush_buffer` 里坏行卡死重发（恢复机制自身被脏数据卡死）
- BUG-13：降级记账失败反而阻断降级

三条都是**"为处理故障而写的代码，自身成了故障源"**。这类问题在静态规则里极难识别（它们看起来就是正常的错误处理代码），只有把"如果这行也失败会怎样"显式问出来才暴露。
