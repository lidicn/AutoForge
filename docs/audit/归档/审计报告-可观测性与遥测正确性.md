## 三、确证缺陷

### 🟠 BUG-14（中危）`af_conf.ConfidenceStore.samples` — 无界增长且落盘；同文件 `events` 却有上限

**位置**：`src/autoforge/af_conf.py:87`（声明）、`:109/114/119`（`record_*` 追加）、`af_feedback.py:235`（`emit` 追加）、`af_store.py:618`（落盘）

```python
@dataclass
class ConfidenceStore:
    values: dict[str, float] = field(default_factory=dict)
    samples: dict[str, list[tuple[str, float]]] = field(default_factory=dict)   # ← 无上限
```

每次 `FeedbackRecorder.emit()` 都会：

```python
self.conf.samples.setdefault(automation_id, []).append((kind.value, after))
```

全仓库 grep 确认：**没有任何一处对 `samples` 做 `del` / `trim` / 尾部裁剪**。

#### 实测复现

```
emit 3000 次后：
  FeedbackRecorder.events     =   3000  (有 max_events=20000 裁剪)
  ConfidenceStore.samples     =   3000  (无任何裁剪)

落盘 47.0 KB —— 仅 1 个自动化 / 3000 条样本
回灌后 samples 长度 = 3000 → 重启后继续在此基础上累加

  推算    10,000 条 →      0.2 MB
  推算   100,000 条 →      1.5 MB
  推算 1,000,000 条 →     15.3 MB
```

#### 为什么值得单独记一条：**同一条数据链上，两端处理相反**

| | `FeedbackRecorder.events` | `ConfidenceStore.samples` |
|---|---|---|
| 数据来源 | 每次 emit 追加 | **每次 emit 追加（同源）** |
| 上限 | `max_events=20000`，超了就 `del self.events[:...]` | **无** |
| 是否落盘 | 否（纯内存） | **是**（`dump_confidence` → `{name}.conf.json`） |
| 重启后 | 归零 | **全量回灌后继续累加** |

**落盘的那一份反而无界，不落盘的那一份有界。** 结果是内存与磁盘双向单调增长，且 `load_confidence()` 每次启动把全部历史读回内存。

#### 与 BUG-01 的关系

BUG-01（`node_visits` 实例级无界增长）是同一形状，但 BUG-01 还掩盖了跨段循环防护缺失，所以定 high。BUG-14 纯粹是增长，定 medium。

#### 修复建议

**同文件内已有正确先例**——`af_feedback.py:243`：

```python
self.events.append(event)
if len(self.events) > self.max_events:
    del self.events[: len(self.events) - self.max_events]
```

照此给 `samples` 加 `max_samples`（建议与 `max_events` 同量级），在 `append` 处裁剪即可。注意 `samples` 是按 automation_id 分组的 dict，裁剪应对**每个 list** 分别生效，而不是限制自动化数量。

### BUG-14 是「横切约束未推广」的又一个样本，但角度不同

前几轮我反复说「正确写法存在但没变成唯一路径」。BUG-14 更具体：**正确写法就在同一个数据链的另一端**。

`FeedbackRecorder.events` 和 `ConfidenceStore.samples` 由**同一次 `emit()` 写入**，一个加了上限、一个没有；一个不落盘、一个落盘。这不是"没人想到要有界"，而是**想到了一处、漏了另一处**。

这类问题靠"记住要加边界"防不住，只能靠**横切约束门禁**——正如第九轮研究报告的结论：把「所有按周期/按事件累加的容器必须有界」变成可机器判定的不变量。
