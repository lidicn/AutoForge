## 二、🔴 BUG-20（high）配对码/授权码 `create()` 写盘前不重读 → 抹掉其他实例刚写入的码

**位置**：`af_auth.py` —— `PairCodeStore.create()`（`_persist` 前无 `_load`）

### 同类方法对照（RMW-01 命中）

| 类 | 方法 | 写盘 | 重读 |
|---|---|---|---|
| `PairCodeStore` | `consume` | Y | ✓ |
| | **`create`** | **Y** | **✗ 缺** |
| | **`mark_pushed`** | **Y** | **✗ 缺** |
| `AuthCodeStore` | **`create`** | **Y** | **✗ 缺** |
| | **`revoke`** | **Y** | **✗ 缺** |
| | **`consume`** | **Y** | **✗ 缺** |
| | **`record_failure`** | **Y** | **✗ 缺** |

**`consume()` 的注释明写「跨进程同步：MCP 写入、API 读取」**——作者清楚跨进程问题，给读路径加了 `_load()`，**唯独漏了写路径**。

### 实测复现（完整配对流程）

```
场景：MCP 长驻实例 + WebUI(API) 独立实例

  WebUI 生成并展示给用户的码: 14420149
  MCP 再建码后磁盘: ['52491498']
  用户看到的 14420149 还在吗: False

  agent 用 14420149 兑换: 失败（码无效）
  >>> 用户看到弹窗里的码被判无效 —— 配对流程走不通
```

`AuthCodeStore` 同形实测：API 的 `26825269` 被 MCP 的 `create` 抹掉。

### 为什么比"数据丢失"更糟：症状与原因分离

用户视角：**弹窗显示了 6 位码 → agent 输入 → 提示"码无效"**。这时无论重试多少次都失败（每次 create 都会再抹一次），且日志里没有任何错误——`consume` 只是返回 `None`。

这是十八轮里**唯一一个直接破坏核心用户流程（agent 配对）的确证缺陷**。

### 与 BUG-08 / BUG-19 的关系

三者是同一根因的三个投影：

| 缺陷 | 形状 |
|---|---|
| BUG-08 | 写盘后**不失效读缓存** → 读到陈旧值 |
| BUG-19 | 凭证库**只增不减** + 持锁全量重写 |
| **BUG-20** | 写盘前**不重读** → 用陈旧快照覆盖别人的写入 |

方向相反（一个写后不失效、一个写前不重读），但都是**内存状态与磁盘真相源失去同步**。

### 修复建议

`create()` 开头补 `self._load()`，与 `consume`/`get`/`pending_events` 一致。注意 `PairCodeStore.mark_pushed` 与 `AuthCodeStore` 的 `revoke`/`consume`/`record_failure` 同样缺，应一并补齐。

## 四、二十个缺陷的根因版图（十九轮收束）

| 根因 | 缺陷 | 数量 |
|---|---|---|
| **内存状态与磁盘真相源失去同步** | BUG-08、19、**20** | 3 |
| 跨层收口不统一（写盘/异常/降级） | BUG-03/04/07/13/14 | 5 |
| 操作顺序与不可逆 | BUG-11/12/15 | 3 |
| 输入与边界 | BUG-06/09/10/16/17 | 5 |
| 门禁覆盖不全 | BUG-05 | 1 |
| 单点实现错误 | BUG-01/02/18 | 3 |

**第一组（内存 vs 磁盘同步）是本轮新识别出来的，且三个成员中有两个是 high。** 它们分布在三个不同模块（`af_catalog`、`af_auth`×3、`af_conf`），说明这不是某个模块的局部问题，而是**缺少统一的"持久化层契约"**。

这也解释了为什么 BUG-05 那条建议（建横切门禁）如此关键：项目有 16 个架构门禁，但**没有一条管"内存状态与磁盘怎么同步"**。
