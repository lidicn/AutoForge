## 二、本轮的核心方法：从"找 bug"转向"找 bug 的形状"

前十六轮是**逐主题扫描**（每轮换一个维度）。本轮换思路：既然已经确证 16 个缺陷，就把它们**抽象成模式**，问"还有哪些地方是同一个形状"。

| 规则 | 抽象自 | 搜索的形状 |

| PAT-01 | BUG-08 | 写入函数未失效同类读取缓存 |
| PAT-03 | BUG-15 | 解析结果未经 isinstance 校验即使用 |
| PAT-04 | BUG-10 | 模块/类级裸 `int()`/`float()` 解析 |
| PAT-06 | BUG-13 | except 分支内的调用未被内层 try 包裹 |
| PAT-07 | BUG-01/14 | 实例级容器 append 无裁剪 |

**工具有效性已验证**：PAT-04 首跑即命中 `af_config.py:158`、`af_service.py:1354/1357`、`af_undo.py:52/57` —— **正是 BUG-10 已知的 5 处**。说明抽象出的形状与原缺陷一致。

## 四、本轮最重要的精度教训：PAT-06 的 73 条假阳性

PAT-06（"except 分支内的调用未被内层 try 包裹"）首版报 **73 条**。核验后发现**绝大多数不是缺陷**，两轮收紧降到 19 条：

**第一轮：排除日志类**。73 条里大量是 `logger.warning()` / `logging.getLogger()` ——标准库日志设计上永不抛出，不是 BUG-13 同类。→ 29 条。

**第二轮（关键）：识别"被调方自带兜底"**。剩下的里，`af_conflict._emit()` 和 `af_version._audit()` **内部就有 try/except: pass**：

```python
# af_version.py:449-455
try:
    _af_audit_write(audit, **details)
except Exception:
    pass    # 审计是旁路（fail-open）      ← 被调方自己兜住了
```

而 BUG-13 的真身 `ConflictService._audit_degraded()` **没有**这层兜底。

**两者的调用点形状完全相同**（都在 except 里、都无内层 try），**唯一区别在被调方内部**。→ 19 条（其中 12 条是 BUG-13 已知的 13 处）。

**这条教训值得单独记**：

> 判断"这个调用要不要包 try"，**判据不是调用点长什么样，而是被调方会不会抛、自己有没有兜底**。这与第十轮的结论（"判据不是用了 `default=str`，而是这条数据会不会被反序列化回来"）是同一条原则——**判据在被调方的语义里，不在调用点的语法里**。

## 五、语义正确性专项：0 命中（自检证明检测器有效）

`semantic_defects.py` 在 AutoForge 上 **0 命中**（98 文件）。合成样例自检 3/3 命中（SEM-03 可变默认参数、SEM-05 不可比较排序键、SEM-04 字符串 `is` 比较）——检测器有效。

确认 AutoForge **不存在**以下问题：

- 浮点直接相等比较（`sum(hist) == 0` 是 int 直方图，非浮点）
- 可变默认参数（`def f(x=[])`）
- 字符串用 `is` 比较
- 不可比较类型的排序键
- `list` 做成员判定（O(n) 语义错用）
- 计数表达式可能为负（`len()` 恒非负）
- 文本读取未指定 encoding（`af_adapters/http.py:87` 显式 `decode("utf-8", errors="replace")`）

**连续三轮（15/16/17）语义类专项 0 确证缺陷**，结合第十六轮的发现，可以更确信地说：这个项目的**单点代码正确性**是扎实的。

本轮最有价值的不是新发现 2 个 bug，而是**方法本身验证了贯穿十七轮的判断**：

**十八个缺陷，没有一个是"开发者不知道正确写法"，全部是"知道，但没让正确写法成为唯一路径"。**
