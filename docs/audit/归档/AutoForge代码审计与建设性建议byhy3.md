# lidicn/AutoForge 深度代码审计与建设性分析

## 摘要：架构目标已成形，但生产化前仍缺少可验证的执行与恢复证据

本次审计以仓库公开默认分支为对象，通过项目文档、目录树、近期提交记录及公开 issue/PR 状态建立证据链。审计结论明确区分三个层次：**公开文档声明**、**由模块语义推导出的高风险疑点**、**未获得源码逐行验证而无法确认的缺陷**。在现有证据范围内，未发现可由公开 issue 或 PR 直接佐证的已确认漏洞；公开页面显示 issue 与 PR 均为 0 且禁止创建 issue，但这只能说明公开反馈渠道没有可观察记录，不能证明不存在问题。[1][2]

AutoForge 的目标是“自然语言生成自动化、机器验证正确性、人只审查自然语言”，并以 Graph/JSON IR 为唯一事实来源；系统至少包含 `forge build`、`forge sim`、`forge run(--live)`、`forge conf`、`forge diff`、`forge store`、`forge spec` 等入口。其模块边界已较为清晰，但**清晰不等于隔离安全**：IR 同时承担审批对象、执行契约和持久化状态，任何 Schema 验证、版本迁移、反序列化或语义兼容缺陷都可能跨越 build、run、persist 三个边界，成为系统性故障源。[3][5]

当前最值得优先处理的是执行路径的可证明性，而不是继续增加 AI 能力。建议以“真实 IR 快照 + 崩溃恢复演练 + 真机 dry-run 契约测试”建立最低验证闭环；随后再强化 Web API 鉴权、命令白名单、并发控制和可观测性。若不能证明崩溃后状态不偏离、并发调度不重复动作、未批准 IR 不会进入 live 路径，则智能家居自动化场景中的功能正确性与人身安全预期就无法成立。

## 审计范围与证据分级

**本次审计能确认的是系统公开契约、目录结构和近期演进，不能替代对源码的逐行核验。** 公开仓库页面确认默认分支为 `main`，最近一次推送为 2026-09-29；截至该日期，公开 issue 与 PR 页面均显示 0 条，且 issue 创建受限。[1][2] 近期提交标题包括“预测性触发 PreTriggerService、af_evo 真 IR 内联、ask 通道消费闭环”“经验库接进 af_predict”“group 复合 IR 版本语义”“下发后撤销与设备态回滚”等。它们共同表明项目正处在从执行能力向预测、经验复用和人机闭环扩展的阶段。[4]

源代码目录树公开列出 `src/autoforge` 下的核心模块，包括 IR 模型、TimeSource、StateProvider、EventBus、InstanceManager、HA/HTTP/Mock 适配器、NodeExecutor、Scheduler、StaticScanner、NL 渲染、审计、置信度、灰度、故障注入、版本化存储、AF-Spec、服务层、HTTP 路由、Runtime 和实例持久化模块。[5] 本报告对这些模块采用以下证据分级：

| 证据等级 | 定义 | 本报告中的处理 |
|---|---|---|
| A：已确认 | 可直接从公开仓库文档、目录树、提交记录或 API 响应核验 | 可作为事实依据，但仍需结合本地运行时验证其实现和契约 |
| B：高风险疑点 | 模块名称和已声明语义表明存在敏感路径，但审计环境未能读取逐行源码 | 仅作为必须测试或审阅的重点，不宣称具体代码存在漏洞 |
| C：建议 | 由架构特征、运维责任链和同类系统风险推导 | 提供优先级、验收方式和实施方向，不代表当前代码违反约束 |

**审计边界是本报告最重要的使用前提。** 本报告没有宣称某具体源文件行号存在 bug，也不能利用第三方搜索摘要、README 文档或提交标题反推实现细节。尤其是当前 `main` 处于持续演进状态，提交标题中的“闭环”“消费”“回滚”等词只能证明相关能力被列为目标或已实现，不能证明其在异常路径、并发场景和真实设备交互下均正确。

## 架构边界已经建立，但单一 IR 同时成为事实源、执行契约和状态载体

**AutoForge 的架构价值在于把自然语言、IR、静态检查、仿真、真机预检和运行时分成不同环节，但价值成立的前提是各环节不越过边界。** 仓库文档将流程划分为“安全闸（静态扫描）—逻辑闸（仿真加时间旅行）—内存态 Runtime”，并提供 `forge build`、`forge sim`、`forge run` 等命令。[3] 这种设计的核心不是工具数量多，而是让“人类可读的意图”与“机器可执行的逻辑”尽可能处于可审计的一一映射关系。

模块树显示，系统并未把业务逻辑直接嵌入 CLI 或 Web 层，而是存在相对明确的职责划分：`af_service.py` 被定义为服务层纯逻辑，只暴露 API 能力，不依赖 Web；`af_api.py` 是只读 HTTP 路由层；`af_runtime.py` 负责组装依赖；`af_persist.py` 负责实例持久化与崩溃恢复。[5] 如果实现遵循该边界，测试工作就可以分层进行：无网络单测验证 IR 语义，内存内测试验证调度和执行，Web 契约测试验证接口，仿真测试验证自动化逻辑，仅在最后才执行真机 dry-run。

```text
自然语言 / AF-Spec
        │
        ▼
JSON IR（Schema 校验、版本、签名/审批）
        │
        ├── StaticScanner：构建期安全闸
        ├── VHASS 仿真：逻辑与时间旅行
        ├── live_preflight：真机预检
        │
        ▼
Runtime：TimeSource / StateProvider / EventBus / Executor / Scheduler
        │
        ▼
HA、HTTP、Mock 适配器（副作用边界）
        │
        ▼
实例状态、审计日志、版本化存储、崩溃恢复
```

*图 1：基于仓库公开目录树和 README 的 AutoForge 数据流与模块边界。该图是审计推导，不代表逐行反编译结果。数据来源：仓库 README、模块树 [3][5]*

**真正的架构风险在于 IR 跨越了三层责任。** IR 同时是审批对象、执行契约和持久化状态，任何 Schema、版本迁移、反序列化或语义兼容性缺陷都可能同时影响 build、run 和 persist。具体而言，如果某一版本写入新字段，而旧版本继续读取并默认补全，就可能产生“内容相同但语义不同”的自动化；如果审批快照没有绑定 IR 版本、哈希和签名，运行时也可能执行与审批者看到的对象不完全一致的逻辑。

这一风险并非断言当前代码存在问题，而是由架构职责推导出的高价值审查面。真正需要防止的不是“字段缺失”这种一般错误，而是同一份 IR 在审批、模拟、运行和持久化阶段被不同解释。现有模块已经具备处理这些问题的位置，关键在运行时能否保证对象在跨阶段传播时不发生静默语义漂移。

## IR、Schema 与审批快照是首要审阅目标

**若 IR 是唯一事实源，则其解析、版本控制和审批快照必须达到最高可信等级；任何默认值或隐式迁移都应被视为潜在一致性风险。** README 明确声明 Graph/JSON IR 是唯一真相，自然语言由其确定性渲染；表达式函数库使用纯函数白名单，并限制求值深度与单次节点数。[3] 这一设计方向能够减少图灵完备表达式带来的滥用与资源风险，但目前证据无法证明验证器本身已经完整覆盖以下环节：

| 待验证环节 | 必须回答的问题 | 不通过时的影响 |
|---|---|---|
| 未知函数 | 是否能在编译期拒绝，而不是运行期跳过或默认无操作 | 恶意或错误 IR 可能执行未审查逻辑 |
| 未知字段 | 是否显式拒绝，还是忽略后静默补默认值 | 审批对象可能与运行对象不一致 |
| 负时间、空时间窗、溢出 | 是否进行类型与范围校验 | 调度、触发或重试行为可能异常 |
| NaN、Infinity、过大数字 | 是否限定 JSON 数字和边界值 | 求值、阈值判断或持久化可能出错 |
| 空列表、深层嵌套 | 是否遵守节点数和深度约束 | 可能绕过资源限制 |
| 循环、重复边 | 是否校验图结构 | 可能出现重复执行或调度死循环 |
| 无效实体引用 | 是否在执行前解析 | 可能延迟暴露为运行时失败 |

这些问题不要求阅读某一特定文件即可确定，但任何具体行号上的结论都必须基于源码反编译。`af_ir`、`af_scanner.py`、`af_executor.py` 和 `af_spec.py` 应成为审阅入口；测试必须覆盖深度上限、节点上限、未知函数、未知字段、负数、空集合、NaN、Infinity 和版本字段等输入。[5]

**未知字段的默认忽略往往比显式错误更危险。** 如果 Schema 使用 `additionalProperties: true`，或者反序列化器自动忽略未知字段，则旧客户端可能接受并运行新版本创建的 IR；如果采用自动补默认值，又可能把未批准字段带入执行路径。建议 IR 解析器默认拒绝未知字段，采用显式 `version` 和 `schema_ref`，并通过兼容迁移函数将旧 IR 升级为新 IR；禁止在持久化后反向覆盖原对象。

`af_store.py` 负责版本化存储、置信度持久化和 diff，这使 IR 同时承载“待执行意图”与“历史治理记录”。[5] 如果执行引擎直接读取最新对象，而审批链保存的是旧对象，则系统可能处于“IR 已更新但人类尚未重新批准”的中间状态。验收时应在对象上分别记录 `approved_hash`、`version`、`approved_at`、`valid_from` 和 `valid_to`；只有在所有字段匹配时才允许进入 `forge run --live`。这样即使状态更新，也不会自动获得运行授权。

## 执行器与调度器的正确性取决于中止、重复执行和时钟边界

**NodeExecutor 的“挂起、边优先级、canary”能力若缺少失败边界，会把正常中断放大为重复动作。** 目录树将 `af_executor.py` 定义为 NodeExecutor，职责包括求值段、边优先级、挂起和 canary；`af_scheduler.py` 负责 4 种模式和配额。[5] 从功能描述看，执行器需要处理同步副作用，因此必须明确以下问题的答案：

1. 节点失败时是中止整图、跳过当前分支、重试，还是进入人工流程？
2. canary 失败时能否立即停止后续节点，还是只记录结果？
3. 执行器重启后，未完成的挂起节点如何恢复？
4. 崩溃发生时，已经完成和尚未完成的动作如何区分？
5. 边优先级改变是否会导致同一次触发多次执行同一动作？

由于无法访问 `af_executor.py` 和 `af_scheduler.py` 的逐行实现，上述问题不能据文档直接判定为缺陷。但它们已经足以证明：执行状态机至少需要覆盖 `pending`、`running`、`succeeded`、`failed`、`cancelled`、`rolled_back`、`unknown` 等状态，不能只用“成功”和“失败”概括。

**持久化恢复是稳定性上风险最高、也最缺少公开证据的模块。** `af_persist.py` 描述为 P1 实例持久化与崩溃恢复模块，`persist=true` 时实例跨进程和崩溃恢复。[3][5] 智能家居场景中的常见故障模式包括进程被信号杀死、磁盘空间不足、写入中断、同一持久目录被多个进程打开，以及恢复期间再次触发自动化。

建议恢复路径采用如下事务模型：

| 阶段 | 必须保证的属性 | 不满足时的风险 |
|---|---|---|
| 写入前 | 先写入临时文件，再原子替换 | 崩溃可能留下半写入状态 |
| 写入中 | 使用校验和或序列号识别完整性 | 恢复可能读取截断数据 |
| 写入后 | 保证目录、临时文件和目标文件的同步语义 | 原子重命名可能不成立 |
| 恢复时 | 比较快照版本、checksum 和 monotonic epoch | 可能恢复陈旧或重复状态 |
| 运行时 | 检查进程租约或文件锁，避免多 Runtime 接管同一实例 | 可能产生双主调度 |
| 恢复后 | 只恢复明确的已提交点，并将 `unknown` 状态转为人工确认 | 可能把未确认副作用误判为已完成 |

当前公开文档没有给出“崩溃后最多执行一次”或“幂等恢复”的可验证承诺，因此这是高风险疑点，不是已确认 bug。验收应采用 Chaos 测试，在 `fsync` 后、状态转换中和恢复初期分别 `SIGKILL` 进程，并校验数据库校验和、图状态、审计日志、设备目标状态以及重复执行次数。

## 副作用适配器必须先守住 dry-run、幂等性和命令边界

**HA 适配器是否真的只读，决定了 StaticScanner 和 Shadow 模式能否构成有效安全闸。** `af_adapters` 包含 HA 的 `dry-run`、HATransport 和 HAStateProvider，以及 HTTP 和 Mock；StaticScanner 被定义为安全闸，`live_preflight` 用于真机预检。[5] 但文档没有公开 `live_preflight` 的拒绝条件、执行者身份、目标范围、审批要求、并发策略及失败回退。

这意味着安全结论必须同时验证以下内容：dry-run 是否真正不触发任何服务端 action；live 模式是否检查 IR 的批准快照；失败请求是否会静默落入非 dry-run 分支；HTTP 适配器的超时和重试是否可控；Mock 是否可能通过配置被误接为真实执行器。在缺少实现证据时，任何“扫描器已拦截”或“适配器只读”的判断都只能视为待验证声明。

**设备动作的可撤销性应成为一等执行约束。** 最近提交提到“下发后撤销与设备态回滚”。[4] 如果撤回依赖设备当前状态，而该状态已经由同一自动化改变，则撤回条件本身可能失效；如果回滚动作与新一轮触发并发执行，还可能出现“撤销—重新下发”抖动。

建议将每个副作用动作声明为 `idempotency_key`、目标实体、命令类型、前置状态、预期状态、超时、重试策略和补偿动作。`Executor` 应先在仿真中证明补偿路径，再进入 live canary。若设备协议不支持查询、不支持事务，或无法证明回滚成功，则相关动作应自动降级为 `ask`，而不是继续执行。该设计的核心不是减少功能，而是让系统在不具备安全撤销条件时主动缩小自主范围。

## 静态扫描、灰度与置信度机制之间仍存在控制断层

**安全闸必须拥有独立、可版本化的执行权限，而不能被 LLM、配置或运行参数绕过。** README 明确说明 `forge build` 经过静态扫描，`forge sim` 经过仿真和时间旅行，`forge run` 进入内存态 Runtime。[3] 但“安全闸”是否构成不可绕过控制，取决于其执行位置和权限来源。

如果 `af_scanner.py` 只是 CLI 的一个提示步骤，运行时仍可直接加载 IR，那么控制只是建议，而不是安全边界；如果它由 Runtime 在 load 阶段强制调用，并能读取固定的、可验证的策略版本，才可能构成执行前闸门。因此，必须在 Runtime 启动时明确配置策略版本，拒绝未知或低于最低要求版本的 IR；Scanner 的输出和拒绝原因必须进入结构化审计，而不能只打印到控制台。

**置信度可以降低自主等级，但不能替代授权和执行策略。** `af_conf.py` 的公开片段描述了分级自主：置信度不低于 0.85 可自动部署；0.60 至 0.85 进入 Shadow；低于 0.60 只能提出 ask 提案。置信度还会随时间指数衰减，负样本使置信度下降 0.25，不同 band 存在优先级。[6] 这说明置信度属于模型行为策略，而不是权限系统。

| 风险变量 | 需要避免的行为 | 建议控制 |
|---|---|---|
| 模型输出 | 被错误当作授权结果 | 置信度不覆盖审批状态、IR 签名或 RBAC |
| 时间戳 | 时钟回拨使衰减结果异常 | 记录评估时间并校验单调时钟边界 |
| 人工拒绝 | 被记录为普通负样本后触发过激惩罚 | 区分原因码，避免自动降低所有相关能力 |
| 连续负样本 | 自动带宽带快速下降 | 加入平滑、冷却和人工复核 |
| 旧样本 | 长期影响新设备类型 | 按设备类型、动作类型和 IR schema 版本分桶 |
| 模型身份 | 用户无法判断执行来源 | 保留 model、prompt、policy 和 IR hash 的不可变关联 |

**灰度必须同时约束行为变化、设备影响范围和回滚成本。** `af_canary.py` 涉及漂移检测和回滚。[5] 如果灰度指标只看 HTTP 成功率，可能忽略设备状态错误；如果回滚只切换控制流而不撤销已经产生的设备动作，则“回滚成功”并不等于环境恢复。

建议 canary 设置三个独立指标：IR 执行成功率、副作用设备状态与目标状态一致率、告警和安全闸拦截率。任一硬指标越界，都应停止后续动作并转入 `ask`；只有确认已发出动作可以补偿时，才能自动执行补偿。否则，系统应保留现场并等待人工介入。

## Web API 的“只读”边界需要独立验证

**HTTP API 的攻击面不能由模块名称推断，必须逐路由验证身份、作用域和传输控制。** `af_api.py` 被描述为只读 HTTP 路由层，`af_service.py` 为无 Web 依赖的纯逻辑服务层。[5] 但该描述没有说明路由是否真正只读、是否支持写操作、是否提供敏感文件读取、是否拥有身份认证，以及外部客户端能够查询到什么状态。

安全审阅至少应覆盖：

- 是否启用 HTTPS，或是否限制为本地、Unix socket 和反向代理；
- 是否存在认证、授权和按项目隔离；
- 路径参数、实体 ID 和 IR 导入是否做正则、类型和长度校验；
- 错误信息是否泄露文件路径、配置、堆栈或内部拓扑；
- 列表接口是否具备分页、速率限制和搜索超时；
- 审计日志是否记录请求者身份、决策结果和关键字段，同时避免记录令牌；
- 上传、导入和导出是否限制文件大小、类型、扩展名和内容；
- 是否将生产 API 与开发调试入口隔离。

目前不能因为模块名为 `af_api.py` 就断言其安全。建议先补充请求身份、项目级 RBAC、CSRF 或同源策略、请求体大小限制、审计日志、CORS 白名单和明确的退出码；再添加默认关闭的管理端点。若 API 需要远程访问，应使用双向认证或反向代理，并禁止直接暴露内部 Runtime 端口。

## 并发、资源限制和异常传播尚未形成可验证契约

**双硬顶限制是有价值的第一道防线，但资源控制仍缺少跨请求、跨进程和后端调用的一致性。** README 说明系统设置 `MAX_EXPR_DEPTH=32` 和 `MAX_EXPR_NODES=256` 双硬顶，并在编译期拒绝未知函数或参数数量错误。[3] 这一设计能够限制单条表达式复杂度，但现有公开信息没有说明以下边界：

| 边界 | 当前未证实内容 |
|---|---|
| 请求层 | 是否存在并发请求数、每请求 CPU 和内存限制 |
| 调度层 | 是否限制每设备、每图、每用户并发执行数 |
| 图结构层 | 是否限制总节点数、边数和 fan-out |
| 外部调用层 | HTTP、HA 和仿真是否统一设置超时、连接池与重试上限 |
| 持久化层 | 数据库写入是否设置事务、超时和背压 |
| 进程层 | 多次 `forge run` 是否锁定或拒绝同一工作区 |

如果这些边界不存在，攻击者或异常自动化仍可能通过大量并发图、深层递归、慢速设备响应、指数级边 fan-out 或磁盘满写放大资源消耗。当前证据只能支持“已声明表达式级资源限制”，不能支持“整个 Runtime 已具备资源隔离”。

**事件总线的去重、节流和熔断必须在可见状态中暴露，而不能只作为内部统计。** `af_bus.py` 被定义为 EventBus，包含去重、节流、熔断和精确订阅；`af_time.py` 负责生产时间和仿真时间。[5] 系统应明确区分以下概念：

- 生产时间由可信单调时钟或墙钟生成；
- 仿真时间可注入，但不能污染生产时间；
- 事件重复时，去重键应覆盖事件类型、源、目标、payload hash 和时间窗口；
- 熔断后必须能恢复，不能无限拒绝或无限重试；
- 精确订阅不能产生跨项目或跨用户的事件泄漏；
- 时间跳跃不应自动重放历史事件。

建议为 EventBus、Scheduler、Executor 和 Adapter 建立统一指标，包括 `events_total`、`events_dropped_total`、`dedup_hits_total`、`throttle_hits_total`、`circuit_open_total`、`executions_total`、`executions_failed_total`、`retries_total`、`action_duration_seconds`、`inflight_actions`、`canary_rollback_total` 和 `unknown_recoveries_total`。没有这些指标，运维人员无法区分“系统没有动作”和“系统因熔断、去重或调度冲突没有动作”。

## 测试、CI、部署与可观测性仍需补成发布证据

**仓库存在 `.github/workflows`，但现有证据无法证明门禁覆盖了运行时、安全和端到端恢复。** 目录树显示 `.github/workflows` 存在。[5] 在提交和 README 均未提供工作流细节的情况下，不能确认 PR 检查是否包含类型检查、单元测试、集成测试、端到端仿真、Schema 兼容性测试、依赖审计、secret scanning、Docker 构建、版本发布、性能预算和恢复测试。

建议 CI 至少分为五道门：

1. `pre-commit/format/lint/typecheck`；
2. 快速单测；
3. 带固定 seed 的属性测试；
4. 仿真端到端测试；
5. 真机 dry-run 和故障恢复测试。

所有构建应锁定 Python 版本、依赖哈希和 `forge` 版本；发布包应生成 SBOM，并对 `src/autoforge` 和关键依赖进行签名或哈希验证。若 `pre-commit`、依赖或 CI 脚本本身可以修改生产路径，应将其纳入单独的代码审查与发布控制。

**测试体系应以不变量为核心，而不是只验证正常成功路径。** 建议建立以下不变量，并通过随机 IR、故障注入和属性测试持续验证：

- 批准 hash 不一致时，不得进入 live 执行；
- Schema 校验失败时，不得产生外部副作用；
- 单次事件不得重复触发同一设备动作；
- canary 拦截后，不得继续影响目标设备；
- 崩溃恢复后，不能执行未持久化的动作；
- `forge sim` 与 `forge run` 在同一 IR 和同一时间窗口下，应得到一致的纯逻辑结果；
- `ask` band 不得降级为 shadow 或 auto；
- shadow 模式不得调用非只读副作用。

现有 `af_audit.py` 和 `af_fault.py` 提供了审计与故障注入基础。[5] 建议将故障注入从“能否抛出异常”升级为“能否在指定故障条件下继续维持不变量”，并自动生成最小反例。

## 产品体验应与风险控制策略联动

**自然语言“所见即所得”的价值来自可追溯映射，而不是让 LLM 直接生成可运行动作。** README 的“自然语言由 IR 确定性渲染”方向有助于防止自然语言与执行逻辑漂移。[3] 产品体验应进一步展示以下内容：

- IR 版本与 diff；
- 审批状态；
- 静态扫描结果；
- 模拟轨迹；
- 预测触发依据；
- 执行链路；
- canary 指标；
- 回滚与补偿状态；
- 未知设备或被拒动作的待人工处理队列。

当前公开信息不能证明上述信息已经完整展示，因此只能将其作为产品建议。

**低置信度不应只是阻断执行，而应生成可编辑、可比较、可批量批准的提案。** 置信度衰减和负样本回灌可能带来另一个问题：用户频繁拒绝后，系统可能整体变得保守，却无法说明原因。[6] 建议在拒绝或回滚时，明确记录原因码，例如“目标设备不可达”“状态漂移”“canary 指标越界”“IR 版本不兼容”或“人工拒绝”。原因码应关联受影响规则，并提供“按原因码批量批准或禁止”的能力。

这比仅展示“置信度过低”更有利于产品可理解性。它将抽象模型分数转化为可治理对象，使用户能够判断问题是出在设备、IR、策略还是模型先验，而不是把系统行为简化为不可解释的置信度变化。

## 优先修复清单

**P0 任务的目标是消除系统级不确定性，而不是修复单一代码行。** 由于源码无法逐行访问，每项任务均附可复现定位方法与验收条件，不虚构行号。

| 优先级 | 定位目标 | 必须完成的工作 | 复现或验证方法 |
|---|---|---|---|
| P0 | `af_ir`、`af_store.py`、`af_runtime.py` | 冻结 IR Schema；在 Runtime 强制检查 `version`、签名和 `approved_hash`；禁止未知字段 | 构造未知字段、降级版本和篡改 hash，验证 build/sim/run 均拒绝 live 执行 |
| P0 | `af_persist.py`、`af_runtime.py` | 采用临时文件加校验和加原子替换的快照；比较 epoch 与锁；将未知恢复状态转为 `ask` | 在快照写入、`fsync`、状态转换和重启过程中重复 `SIGKILL`，检查幂等性与数据完整性 |
| P0 | `af_adapters`、`af_scanner.py`、`live_preflight` | 拆分只读接口和写接口；强制 dry-run 合约测试；live 路径执行项目鉴权与批准检查 | 将 Mock 适配器配置成真执行器，验证系统拒绝运行；测试目标实体越权 |
| P0 | `af_api.py`、`af_service.py` | 默认关闭远程访问；增加身份、RBAC、速率限制、审计、路径边界和错误脱敏 | 使用路径遍历、大请求、越权 ID、重复提交和未授权调用进行 API 测试 |
| P1 | `af_executor.py`、`af_scheduler.py` | 建立显式动作状态机；实现幂等键、超时、死信、补偿和 per-device in-flight 限制 | 构造适配器慢响应、重复事件、节点异常和时钟跳跃，验证不重复执行 |
| P1 | `af_conf.py`、`af_canary.py` | 将置信度与授权隔离；按设备类型和动作类型保存先验；设置行为、状态一致性和拦截率指标 | 注入模型偏差、漂移和负样本风暴，验证系统不会自动提权 |
| P1 | `af_bus.py`、`af_time.py` | 固定去重键、订阅隔离和熔断恢复语义；隔离仿真时钟与生产时钟 | 使用重放事件、跨项目订阅、时间跳跃和后端超时测试事件路径 |
| P1 | `.github/workflows`、发布配置 | 将 Schema 兼容性、故障注入、真机 dry-run、SBOM 和依赖审计加入门禁 | 故意破坏 IR 契约或提交漏洞依赖，验证流水线拒绝合并 |
| P2 | `af_audit.py`、`af_fault.py`、日志 | 增加结构化 trace ID、指标、事件溯源和最小反例导出 | 通过 Grafana、日志或告警面板观察失败链路，并重放问题 IR |
| P2 | 产品 UI、CLI | 展示 IR diff、置信度依据、模拟轨迹、canary、回滚和 ask 提案 | 让目标用户完成创建、审批、回滚和批量处理任务并收集成功率 |
| P2 | 项目治理 | 在 README 补充威胁模型、版本支持矩阵、配置示例和 secret 清单；建立公开 issue 模板与安全联系人 | 由独立人员按照文档完成一次从部署到恢复的演练 |

## 最终判断

**当前证据支持“架构合理、验证不足”，不支持“已确认存在具体漏洞”。** AutoForge 已将自然语言生成、IR、静态扫描、仿真、真机预检、Runtime、持久化和审计划分到不同模块，方向上有利于正确性、安全性和可维护性。[3][5] 但智能家居自动化对错误执行、重复执行、未授权执行和崩溃后状态一致性的容忍度很低；而当前公开材料不足以证明 `af_persist.py`、`af_api.py`、`af_executor.py`、`af_adapters` 和 `af_scanner.py` 在异常路径和并发条件下已经满足这些要求。

下一版本发布前，应把 P0 修复作为硬门禁：IR 必须验证并绑定审批；持久化必须原子、可校验、可幂等恢复；live 动作必须受到独立批准、目标范围和补偿策略约束；Web API 必须在默认安全边界内运行。完成这些工作后，再扩展预测、经验库和 ask 通道，才更有可能在不牺牲可靠性和安全性的前提下提高自动化自主性。
