## 三、四条根因（本区间的主脉络）

### 3.1 「同族只修一半」——本区间兑现 8 次，本季累计第 7 次

这是本区间最该记住的一条。同一个代码形状在项目里出现 N 次，历轮只修了其中一处，其余 N−1 处继续裸奔：

| 次 | 已修 | 漏掉的 |
|---|---|---|
| 1 | AF71c（sidecar 顶层形态） | **AF84** 图文件那一侧 |
| 2 | AF64（`af_service.enable_by_tag`） | **AF92** CLI 的第二份实现（docstring 自己写着"同源逻辑"） |
| 3 | 第 45 轮修了 `_load_revoked_file` / `_load_issued_file` | **AF93** `PairCodeStore._load` / `AuthCodeStore._load` |
| 4 | 第 71 轮修了 `af_service.py:448` | **AF89** 同文件 1312 / 1338 两处（一字不差） |
| 5 | **AF96**（`stop_watch` 读 sidecar） | **AF97** `start_watch` 两处 |
| 6 | **AF97** | **AF98** 同一份 sidecar 的第三处 `FileLock.holder()` |
| 7 | AF58 的 hint 分支 | **AF96** 的 else 分支（要求 `holder.get("owner")` 为真，读不出来时必落 else） |
| 8 | **AF102**（`DeviceCatalog._load`） | **AF103** 上游 `load_entity_health` 自己先 stat，从未走到 AF102 那处 |

第 8 次是**新变体**：不是漏了同族，是**漏了同族的上游**——补丁装在下游，但上游先短路，AF102 的告警在这条链路上**一次都没触发**（实测坐实）。

第 98 轮为此做了 W195 扫描器（同函数内"一条降级分支有留痕、另一条静默" ⇒ 后者是没修的那一半），并用 AF96、AF101 做**已知阳性自检**。此前全靠人读。

### 3.2 「读不出来 ⇒ 归空容器」——判据是"读路径终点"

同一个形状出现 11 次，但**不是每一处都是缺陷**。第 90 轮给出的分辨方法：

> 看函数在链条的哪一端。写路径中间 ⇒ 后面有拒写护栏替它说话（不修）；**读路径终点 ⇒ 再也没人发声（修）。**

例：`af_experience._load` 与 `PairCodeStore._load` 代码一字不差，前者 `_save` 的拒写护栏会替它抛异常 ⇒ 假阳性；后者是读路径终点 ⇒ AF93。

### 3.3 「形状不对 ⇒ 穿出」

五条（AF81、AF85、AF88、AF89、AF95）的共同形态：`json.loads` 的返回值**没有形状校验**就当 dict 用，而 `AttributeError` / `TypeError` / `KeyError` 不在捕获元组内 ⇒ 穿出 ⇒ 端点 500。

第 91 轮额外记了 `AF-GAP-116`：`X not in obj` 被当作形状判定——对 dict 是键判断、对 list 是**成员判断**、对 str 是**子串判断**、对 None 直接 `TypeError`。建议在所有此类处前置 `isinstance`。

### 3.4 「判不了就当作没有」的余波

第 57–60 轮发现的 AF76–AF79（我自己的补丁把"读不出来"放行，导致整档覆盖抹数据）在本区间继续扩散：第 87–100 轮的 AF91–AF103 都是它的同族，只是**危害从"抹数据"降级为"静默 + 诊断方向反"**——写侧已有拒写护栏，剩下的是读侧不说话。
