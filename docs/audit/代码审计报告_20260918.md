## 一、P0：人工确认门可以被「拒绝」回答通过

### [P0-1] ✅ `classify_answer` 把「不要」「别开」「不好」判为**同意**

- **位置**：`src/autoforge/af_executor.py:53-59`（消费方：审批等待路径 `af_service.py:1137`）
- **证据**：
  ```python
  _YES_WORDS = ("是","好","要","开","嗯","yes","y","ok","okay","确认","开吧","来吧")
  _NO_WORDS  = ("不","否","别","不用","不要","算了","no","n","cancel")
  def classify_answer(text):
      ...
      if any(w in lowered for w in _YES_WORDS): return "yes"
      if any(w in lowered for w in _NO_WORDS):  return "no"
  ```
  **yes 分支先判、且用子串匹配**：`"不要"` 含 `"要"`、`"别开"` 含 `"开"`、`"不好"` 含 `"好"`、`"不用了"` 含 `"用"...`（不命中但 `"不"` 前已命中 `"要"` 类）。因此自然语言里最常见的拒绝形式全部返回 `"yes"`。
- **失败场景**：审批问「是否打开车库门？」用户答**「不要」**→ 系统记为已批准 → 走 `HAAdapter(dry_run=False)` 真实写入。这不是普通 bug，这是**审批机制的反向失效**：它把最该拦住的答案变成放行信号，而且日志里会显示「用户已确认」。
- **修复方向**：① 先判 no（否定优先级高于肯定）；② 用整句/分词精确匹配而非 `in` 子串；③ 无法明确判定时返回 `"unknown"` 并**重新询问**，绝不默认 yes；④ 补 `test_classify_answer.py` 覆盖 `"不要/别开/算了/不/嗯不行"`。

### [P0-2] ✅ 审批回答的函数签名不匹配 → `TypeError` 被吞 → 证据文件被删

- **位置**：`src/autoforge/af_live.py:293-306` 调用 `runtime.executor.answer(ask_id, text=text, room=room)`；定义 `src/autoforge/af_executor.py:171 def answer(self, room, text)`
- **证据**：三个实参对两个形参（且无 `ask_id` 形参）→ `TypeError`；外层 `except Exception: pass`，随后 `f.unlink(missing_ok=True)` 删除 pending 审批文件。
- **失败场景**：用户在设备端（HA 通知按钮/文本回复）回答审批 → 答案被丢弃、审批记录被销毁 → 该次高危写入既没执行也没留痕，用户以为「我已经说过不要了」，而系统里那条自动化仍在待批队列的其它入口（见 P0-3）中可被别的路径批准。**审批证据链被主动销毁**，事后无法追责谁批的。
- **修复方向**：统一签名（`answer(room, text, ask_id=None)`）；删除「先 unlink 再校验返回值」的顺序，改为成功消费后才清理；`except Exception: pass` 换成 `logger.exception` + 保留文件。

### [P0-3] 回答错 ask_id 时会落到「任意房间里最旧的待批项」

- **位置**：`src/autoforge/af_service.py:1127-1134`
- **失败场景**：两个待批问题并存（一个开阀、一个开灯），用户回答的是后者，ask_id 不匹配 → 系统把这条答案给**最旧的**那个（开阀）。与 P0-1 叠加即为：一句「不要」可以批准一个用户从未看过的问题。
- **修复方向**：id 不匹配就报错并回显当前所有待批项；禁止任何 fallback-to-oldest。

## 二、P0：安全闸（StaticScanner）可被绕过

### [P0-4] ✅ `live_run` 不实例化扫描器，`allow` 来自请求体

- **位置**：`src/autoforge/af_service.py:1218-1260`
- **证据**：该函数只做「环境变量 + token + `confirm` 标志 + `targets - allow`」，**全程不构造 `StaticScanner`、不调用 `live_preflight`**；`targets` 只取 `auto.writes()`；`allow` 由调用方在请求里提供。
- **失败场景**：任何拿到 API token 的调用方可自行声明 `allow=["lock.front_door"]`，把「白名单」变成「我自己写的跳过清单」。文档/README 所声称的「IR 编译 → L0-L3 分级 → Tier-0 ACL → 影子写拦截 → 爆炸半径」链路，在实际执行入口**一条都没跑**。
- **修复方向**：`live_run` 必须先 `scan()` 并对 `ERROR` 级诊断硬拒绝；`allow` 只能做**减法**（从服务端算出的可写集合中再收窄），且该集合来源必须是配置/DB 而非请求体；给 `live_run` 加一条「未扫描即拒绝」的断言测试。

### [P0-5] ✅ `target:` / `device_id` 参数不参与目标解析 → 所有实体级闸门失效

- **位置**：`src/autoforge/af_ir/models.py:245-256`（唯一的目标解析：`self.params.get("entity_id")`）；`src/autoforge/af_adapters/ha.py:79`（`payload = json.dumps(dict(params or {}))`，整个 params 原样 POST 给 HA REST）
- **证据**：HA 原生支持 `{"target": {"entity_id": [...]}}` 与 `{"device_id": [...]}`。扫描器、爆炸半径、Tier-0 ACL、低置信度影子写拦截全都只看 `params["entity_id"]`；执行时 `target`/`device_id` 却被完整发给 HA。
- **失败场景**：IR 里写 `params: {target: {entity_id: "lock.front"}}`（或一个 `device_id`）→ 扫描器看到的是「零目标、零风险」→ 诊断全绿 → 批准后 HA 实际锁了/开了用户从未被展示过的实体。**这是整套闸门最彻底的一条绕过**，且完全合规于当前 schema。
- **修复方向**：`models.py` 增加统一的 `resolved_targets()`，同时解析 `entity_id` 与 `target.{entity_id,device_id,area_id}`（`device_id`/`area_id` 需服务端查 HA 展开成实体列表）；扫描器只信任展开后的实体集合；加集成测试断言 `target:` 写法必被拦。
- **关联**：子审计指出**没有任何一个测试使用 `target:` 形式**（见 §八），所以这条绕过不会被现有测试暴露。

### [P0-6] ✅ `api_mcp` 端点无鉴权依赖，且以「字母序第一个主体」的权限并集执行

- **位置**：`src/autoforge/af_api.py:609-627`；`src/autoforge/af_mcp.py:46-51 _build_current`、`:54-57 _guard`
- **证据**：`api_mcp` 的 handler 没有 auth 依赖，直接 `dispatch(name, args, store, None)`；`_build_current` 取 `subjects()[0]`（按字母序）并把其 scopes **并集**作为当前主体；`_guard` 在 `current is None` 时**直接 return（放行）**。
- **失败场景**：未认证请求可调用全部 MCP 工具，且权限判定是 fail-open：没有主体 → 不检查。多租户下等价于「以最宽主体身份执行」。
- **修复方向**：`api_mcp` 加与其它路由相同的 auth 依赖；`_build_current` 必须由 token 反查主体（不可由顺序决定）；`_guard` 在 `current is None` 时 `raise PermissionDenied`（默认拒绝）。

### [P0-7] Tier-0 区域规则永远不匹配：`catalog` 从未注入

- **位置**：`src/autoforge/af_scanner.py:224-258,758-791`
- **证据**：区域相关规则需要 `self.catalog`，构造/调用链中没有任何地方写入它（子审计结论）。
- **失败场景**：文档承诺的「Tier-0 设备/区域 ACL（如：任何自动化不得写门锁、不得动安防区域）」实际是死代码，写入门锁的自动化照常通过。
- **修复方向**：在 service 层构造 scanner 时注入 catalog（来自 HA 状态快照），并在 catalog 缺失时**拒绝执行**而不是跳过规则。

### [P0-8] CLI live 路径不做 Tier-0，且白名单可静默变成全目录

- **位置**：`src/autoforge/af_cli.py:446,511`（`_gate(...)` 从不传 `guard_path`）、`:451-460`（`allow = {... if live_allow else _known_entities(entities)}`）
- **失败场景**：① 未传 `guard_path` → Tier-0 检查缺席；② 未显式给 `--live-allow` 时，白名单退化为「HA 里所有已知实体」，即**默认全开**，而 CLI 输出仍显示「已按白名单校验」。
- **修复方向**：`guard_path` 必填；`live_allow` 缺失时报错退出而非放开；退出码需反映闸门结果（见 P1-13）。

## 三、P0：认证与密钥

### [P0-9] ✅ 无恒定时间比较 + 空 token 表 = 默认全放行

- **位置**：`src/autoforge/af_auth.py`（全文件 grep `compare_digest|== token|token ==|startswith` **无匹配**）、`:158-161`（`enabled = bool(self._tokens)`）
- **证据**：`enabled` 为 False 时所有校验被跳过（默认允许）；且没有任何一处使用 `hmac.compare_digest`。
- **失败场景**：① 部署时忘了发 token → **整台 API 无认证**，而这不是报错而是「正常运行」；② 现有测试 `test_no_tokens_all_open` 把该行为固化为**预期结果**（见 §八），使未来任何「改为默认拒绝」的尝试都会被测试拦下。
- **修复方向**：无 token 时 fail-fast 拒绝启动（或只绑 `127.0.0.1` 并在启动日志里用 ERROR 级横幅声明）；比较改 `compare_digest`；把该测试改为断言「无 token 时返回 401/启动失败」。

### [P0-10] CORS 全域 + 限流键可伪造 + 限流表无界

- **位置**：`src/autoforge/af_api.py:269-274`（`allow_origins=["*"]`）、`:200-203`（取 `x-forwarded-for` 首段）、`af_auth.py:209-228 RateLimiter`
- **失败场景**：`*` 允许任意站点带着用户浏览器发起写操作（配合 cookie/无鉴权端点即为 CSRF 面）；限流完全信任客户端可伪造的 `X-Forwarded-For`，攻击者换头即绕过；`self._hits` 只增不减 → 长运行进程内存泄漏（DoS 自伤）。
- **修复方向**：CORS 白名单化；限流键用可信代理层设置的 `request.client.host` 或反代真实 IP 配置（Caddy `trusted_proxies`）；`_hits` 加 TTL 清理或改滑动窗口。

### [P0-11] ✅ 默认 HA 地址硬编码 + 跟随重定向携带 Bearer + 服务名未校验拼进 URL

- **位置**：`src/autoforge/af_adapters/ha.py:35`（`DEFAULT_HA_URL = "http://192.168.2.200:8123"`）、`:78-90`（`url = f"{base}/api/services/{domain}/{service}"`）、`:189-224`（`dry_run: bool = True` 默认，但被调用方以 `False` 打开）
- **证据**：① 生产库口令写默认指向某台内网机器（换环境即静默连不上，且泄露内网拓扑）；② `urllib` 默认 opener **会跟随 3xx 并在重定向后继续携带 `Authorization`**；③ `domain/service` 来自 IR 字符串，未做字符校验即拼 URL 路径。
- **失败场景**：一个被攻陷或误配的 HA/网关返回 302 到外部主机 → **HA 长期令牌外泄**；`service` 里含 `../` 或 `?` 可改写请求路径/注入查询。
- **修复方向**：无默认地址（未配置即报错）；禁用重定向或重定向时剥离凭据；`domain/service` 过 `^[a-z_]+$` 正则；统一 `httpx` 客户端并显式 `follow_redirects=False`。

### [P0-12] 已吊销 token 在 stdio MCP 会话中继续有效；主体 scope 取并集

- **位置**：`src/autoforge/af_auth.py:194-199`
- **证据**：`serve_mcp` 构造 auth 时不传 `revoked_path`；scope 合并用并集。
- **失败场景**：吊销一个泄露的 token 后，已启动的 MCP stdio 进程仍能用它写 HA；多 scope 主体互相放大权限（与 P0-6 的 `_build_current` 叠加更严重）。
- **修复方向**：`revoked_path` 必传并周期性重读；scope 取交集或按请求显式选择；会话建立时校验、并在每次工具调用时重校验。

### [P0-13] 待批审批的提交人由调用方自报，批准时不做身份比对

- **位置**：`src/autoforge/af_pending.py:96-107`（`agent = agent_key or submitted_by`，`submitted_by` 来自入参）、`approve_pending`（不比较提交者与审批者）
- **失败场景**：A 提交的高危项，任何持有审批权限的主体都能批（审批人身份可伪造/不可归因）；审计链里「谁提的」这一列是调用方随口填的。
- **修复方向**：`submitted_by` 从认证主体推导，忽略入参；`approve_pending` 记录审批者并要求与提交者不同（若产品要求双人复核）。

## 四、P1：扫描器与运行时的 fail-open

### [P1-1] ✅ 置信度为 None 时直接返回（不报诊断）

- `src/autoforge/af_scanner.py:611,628`（`conf is None → return`）
- **失败场景**：拿不到置信度（新实体、状态缺失）时按「无问题」处理，与影子写/低置信拦截的设计意图相反。**未知即安全**是闸门系统最典型的反向。
- **修复方向**：`conf is None` → 报 `LOW_CONFIDENCE_UNKNOWN` ERROR 并阻断。

### [P1-2] `requires_confirm` 由 IR 自己声明，L2 检查因此可自我豁免

- `src/autoforge/af_scanner.py:374`（`if level == "L2" and not node.requires_confirm:`）
- **失败场景**：LLM 生成的 IR 里带上 `"requires_confirm": true`（或扫描器误判该字段已被满足）即跳过该诊断。确认要求应当**由服务端风险分级决定**，而不是由被审计对象申报。
- **修复方向**：删除该短路，改由 `(level, domain, target_count)` 的服务端策略表决定是否强制人工确认。

### [P1-3] 分支枚举不含 `yes`/`no` → 条件图不完整

- `src/autoforge/af_scanner.py:506-510`
- **失败场景**：`ask`/`choice` 节点的 `yes`/`no` 分支后继不被纳入可达性与环检测 → 藏在 yes 分支里的写不被爆炸半径统计，成环也检不出。
- **修复方向**：枚举所有出边 kind；为「不可达节点」单独报诊断。

### [P1-4] ✅ 跨自动化检测把「实体依赖图」与「事件依赖图」分开算，永不做并集

- `src/autoforge/af_scanner.py:930-968`（`deps` 与 `emit_deps` 各自 `_cycles_in`）
- **证据**：A 由 `switch.X` 触发并 `emit event.LAMP`，B 由 `event.LAMP` 触发并写 `switch.X` —— 这条 4 节点环在两张图里都不是环（`deps` 缺 emit 边，`emit_deps` 缺写边）。仓库内 `examples/ir/case_lamp_sync.json` 正是这个拓扑，其 `meta.expect` 写着「用 emit 事件解耦……避免跨自动化实体读写成环（ENTITY_DEP_CYCLE 会被安全闸拦截）」——**示例文件本身就在闸门盲区里**。对照 `examples/ir/invalid_case08_cycle.json` 是纯实体环，所以测试通过，掩盖了盲区。
- **修复方向**：`full = union(deps, emit_deps)` 后再查环；把 `case_lamp_sync` 这类混合作为 invalid 用例补进测试。

### [P1-5] 时间触发不看 `auto.enabled`

- `src/autoforge/af_scheduler.py:283-298`
- **失败场景**：用户在 UI 里停用一条自动化，它仍在时钟到点时执行写操作。停用是安全操作，静默不生效最危险。
- **修复方向**：`_fire_time_triggers` 与其它触发路径共用同一个 enabled 判定；补「停用后不触发」的回归测试。

### [P1-6] `op == "and"` 用单事件判 `all(_satisfied(sub, event))`，恒不成立

- `src/autoforge/af_scheduler.py:231-236`
- **失败场景**：AND 复合触发永不触发 → 用户改回 or，或引入定时器兜底，反而多出执行路径。
- **修复方向**：AND 需基于「最近状态快照集合」判定，而非当前单个事件。

### [P1-7] `_still_holds` 在 `pending.to is None` 时返回 True

- `src/autoforge/af_scheduler.py:252-260`
- **失败场景**：无明确目标态的挂起判定被当作「仍然成立」，导致重复执行/延迟执行。fail-open 同族。
- **修复方向**：`None` → 返回 False（保守）并记录一次诊断。

### [P1-8] `normalize_trigger` 丢弃 `sun.offset`

- `src/autoforge/af_time.py:316-328`
- **失败场景**：「日落前 15 分钟」被静默归一成「日落时刻」，所有基于 offset 的照明/安防自动化时间偏移。
- **修复方向**：字段透传，未知字段应报 `UNKNOWN_FIELD` 而非丢弃。

### [P1-9] ✅ `parse_duration` 接受 `inf` / `nan` / 负值，却拒绝 HA 原生 `"00:10:00"`

- `src/autoforge/af_time.py:112-131`
- **证据**：`isinstance(value,(int,float)) → float(value)`；字符串路径 `float(number) * _UNIT_SECONDS[unit]` → `float("inf")`/`float("nan")`/`float("-5")` 全部通过。而 `"00:10:00"` 走不到数字分支 → `ValueError`。
- **失败场景**：`"inf"` 时长进 `for delay in [...]`/冷却判定 → 挂起项永不过期；`"nan"` 参与比较恒 False → 定时器静默不触发（nan 与任何值比较皆 False，这是最难查的一类 bug）。同时从 HA 复制过来的 `"00:10:00"` 直接报错，用户被迫写 `"10m"`，属可用性缺陷。
- **修复方向**：`math.isfinite` + `value >= 0` 校验；支持 `HH:MM:SS`；非法值返回诊断而非异常穿透。

## 五、P1：仿真/Canary/状态一致性——「验收证据来自假世界」

### [P1-10] ✅ 回滚依据是仿真表推导的逆操作，而非真实的 `pre_states`

- `src/autoforge/af_canary.py:24`（`from .af_vhass.fake import SERVICE_STATE`）、`:74-93 rollback()`
- **失败场景**：金丝雀失败要回滚时，用的是「仿真认为 `turn_on` 的逆是 `turn_off`」，而不是变更前的真实状态。对一个本来就 `on` 的灯，回滚会把它关掉；对一个 `valve`，`open/close` 的逆推可能恰好是危险方向。
- **修复方向**：回滚只依据变更前抓取的 HA 真实状态快照；`fake.SERVICE_STATE` 不得进入 live 路径（用 import 边界或依赖注入强制）。

### [P1-11] `canary.duration` 全仓无消费者

- **失败场景**：配置里写的观察时长被忽略 → 金丝雀实际「立即通过」，等价于没有观察期。
- **修复方向**：接入等待逻辑；无消费者即报错启动。

### [P1-12] 三套实体状态语义互相矛盾

- `src/autoforge/af_vhass/fake.py:75-86`（未知实体时**凭空编造**域默认状态）、`src/autoforge/af_adapters/ha.py:170-180`（未知实体**省略**）、`src/autoforge/af_state.py:63-65`（未知实体 **`raise UnknownEntity`**）
- **失败场景**：审批界面展示的「预计行为」来自 fake（有默认值，看起来一切正常），live 执行走 ha（无值）或 af_state（抛异常）→ 仿真通过但线上失败，或线上直接炸；而仿真结果被当作批准依据呈给人（§三 P0 链条）。
- **修复方向**：单一 `StateProvider` 接口 + 三实现共享同一契约测试（子审计指出 `HAStateProvider` **零测试**）；fake 对未知实体也必须抛 `UnknownEntity`。

### [P1-13] `simulate()` 的 `ok` 硬编码 True；CLI 失败仍退出码 0

- `src/autoforge/af_service.py:690-705`、`src/autoforge/af_cli.py:382,415,483`
- **失败场景**：任何「按返回码判断是否放行」的外部编排（脚本、CI、管家侧 `af_bridge`）都会得到成功结论。`--expect` 断言失败时退出码仍为 0，验收形同虚设。
- **修复方向**：`ok` 由诊断/断言真实聚合；CLI 断言失败必须非 0；增加一条「断言失败 → 非 0」的 CLI 集成测试。

## 六、P1：IR 表达式求值的语义错误

### [P1-14] `truthy = bool(value)` 对 HA 状态字符串恒真

- `src/autoforge/af_ir/expr.py:418-419`
- **证据**：HA 状态是 `"off"`、`"unavailable"`、`"locked"` 这类非空字符串，`bool("off") is True`。
- **失败场景**：`if: {var: "sensor.presence"}` 意为「有人在」，实际永远为真 → 有人在时不该做的动作也做了；`if not motion` 也永假。
- **修复方向**：显式 HA 语义真值表（`on/open/locked/active/home/true/1` → True；`off/closed/unlocked/idle/away/false/0/unavailable/unknown` → False；其余 → 报类型诊断，不猜）。

### [P1-15] `eq/ne` 是唯一没有类型守卫的比较

- `src/autoforge/af_ir/expr.py:390-414`
- **失败场景**：`brightness == 255` 与 `"255"` 的相等判定与 `>`/`<` 路径不一致，条件在数值/字符串间漂移。
- **修复方向**：与 `lt/gt` 共用一套 coercion + 失败即诊断的工具函数。

### [P1-16] `except KeyError: return True` 把「实体未知」当成条件成立

- `src/autoforge/af_ir/expr.py:467-475`（`not_is_on/not_is_off`）
- **证据**：`UnknownEntity` 继承 `KeyError`（子审计结论），因此被这个 except 捕获并返回 True。
- **失败场景**：实体掉线/名字写错 → 「不是 off」为真 → 触发一条本不该动的写。HA 里 `unavailable` 是常态，这条路径会被频繁走到。
- **修复方向**：`except UnknownEntity:` → 返回诊断/保守 False；`KeyError` 与业务缺键分开建模。

## 七、P1：存储、并发与运维面

### [P1-17] 版本审计写入的校验顺序颠倒，且 `report["ok"]` 永不为 False

- `src/autoforge/af_store.py:443-455`
- **证据**：`else` 分支先 `self._delete_archive(name)`，之后才 `for ver in entry["versions"]: _validate_graph_dict(...)`；返回结构里 `report["ok"]` 从未置 False。
- **失败场景**：校验失败时旧归档**已被删除**（历史不可回滚），而调用方看到 `ok: true`。G6 版本审计这个卖点（`docs/交接卡_G6版本审计.md`）因此不可信。
- **修复方向**：先校验、全部通过后再删除；`ok` 由诊断驱动；删除改「移动到 `.trash/` + 延迟清理」。

### [P1-18] `_atomic_write` 不 fsync、tmp 名固定；`save_version_raw` 无锁；目录名清洗允许 `.`

- `src/autoforge/af_store.py`（`_atomic_write`、`save_version_raw`、`_dir()`）
- **失败场景**：① 并发写同一自动化 → 两个进程用同名 `.tmp` 互相截断，rename 后得到混合内容（IR 半新半旧是执行事故，不是显示问题）；② 掉电时 rename 已提交但数据未落盘；③ `.`/`..` 通过清洗 → 目录逃逸。
- **修复方向**：`tempfile.mkstemp(dir=同目录)` + `os.fsync` + `replace` + 目录 fsync；写路径统一持锁；清洗改白名单正则。

### [P1-19] `start_watch` 用 argv 传 HA 令牌，并且用 `pkill -f` 清进程

- `src/autoforge/af_service.py:1696-1756`
- **证据**：`cmd += ["--ha-token", tok]`；`subprocess.run(["pkill","-f","forge watch"])`；随后 `for _ in range(15): time.sleep(1)` 然后 `return {"ok": True, ...}`。
- **失败场景**：① 令牌出现在 `/proc/<pid>/cmdline` 与 `ps` 输出，同机任意用户可读，也会进 shell 历史/审计日志；② `pkill -f "forge watch"` 是**模式匹配全机进程**，可能杀掉无关进程（共享主机上即误伤）；③ 轮询 15 秒后无论子进程是否活着都报 ok → 假成功（与 §五 同族）。
- **修复方向**：令牌经环境变量或 stdin 传递；用 PID 文件/进程组精确终止；返回值基于真实健康探测（子进程 poll + HTTP 探活）。

### [P1-20] 事件总线的发布通道不参与限流/熔断

- `src/autoforge/af_bus.py:157-178,203-208`
- **证据**：throttle/circuit-breaker 分支只在 `event.event is None`（即状态类事件）时生效，具名 `emit` 事件不受限；`emitted` 列表无上限。
- **失败场景**：一条 emit 风暴（结合 P1-4 的检测盲区，环状 emit 可无限自激）不会被熔断，内存与下游 HA 调用被打满。**扫描器里的 `EMIT_STORM_LIMIT` 文案与 hint 明说「风暴将触发总线熔断」**——文档与实际相反，运维会基于错误假设放开自动执行。
- **修复方向**：`publish()` 对两类事件统一限流；`emitted` 改有界环形缓冲；文案与实现对齐，并加断言测试。

### [P1-21] ✅ Docker 部署：root + 仓库源码 rw 挂载 + 默认全网卡

- `docker/Dockerfile.api:29-30`（无 `USER`，`--host 0.0.0.0`）、`docker/docker-compose.api.yml:16-17,25`（挂载 `./src` 与仓库根 rw、`env_file` 内含 HA 令牌）
- **失败场景**：容器内进程以 root 运行且能把改动写回宿主源码树 → 任何一次 RCE 或 `docker exec` 即持久化到宿主仓库，`git pull` 后又进镜像（供应链自循环）。HA 令牌进 env_file 意味着 `docker inspect` 可见。
- **修复方向**：非 root `USER`、只读挂载或改镜像内构建、令牌走 secret、`--host` 绑定具体地址并由反代终结 TLS。

### [P1-22] `api_token` 只写不读，轮换是静默 no-op；先替换文件后 `chmod`

- `src/autoforge/af_config.py:65-67,70-77`
- **失败场景**：运维执行了「轮换令牌」并拿到成功回执，但没有任何行为改变（除 `describe()` 显示外无人读取该字段）→ 泄露的旧令牌仍可用；`_atomic_write` 在 `chmod 0o600` 之前已 replace，窗口期内其它用户可读到含令牌的配置。
- **修复方向**：让鉴权层真正读取该字段；`0o600` 在临时文件上先设再 rename（`mkstemp(mode=0o600)`）。

## 九、跨项目设计根因（本项目侧）

1. **闸门与执行是两个世界，且执行不引用闸门**：P0-4/5/7/8 的共同形状是「扫描器的输入 ⊊ 执行器的输入」。任何安全属性只有在**执行入口**再断言一次才算存在。建议在 `live_run`/`HAAdapter` 里加 `assert_scanned(auto_id, digest)`，把扫描结果作为带签名的凭据强制消费。
2. **fail-open 默认遍布判定层**：`conf is None → return`、`current is None → 放行`、`no tokens → 全开`、`KeyError → True`、`to is None → True`、未登记域 → `high_risk: False`、断言失败 → 退出码 0。这是一个**系统性默认值选择**，不是个别疏忽。整仓应统一一条原则：**未知即拒绝**，并把它写进代码规范与 lint 规则。
3. **同一事实存在两份互相矛盾的权威表**：✅ `af_adapters/base.py:56-63`（`_L3_DOMAINS = {"shell_command","command_line","python_script","hassio","supervisor","rest_command"}`、`_L2_DOMAINS` 含 `lock/cover/climate/alarm_control_panel/valve/water_heater/number/select`、`_L1_DOMAINS` 含 `scene/script/siren/tts`、`_L0_DOMAINS = {"notify","persistent_notification","logbook"}`、未知域 → `L2_RISKY`）vs `af_affordance.py:37-39,93`（`HIGH_RISK_DOMAINS` 含 `garage_door`——**它不属于任何 level 集合**；`lock` 的 note 写「必须 L3 白名单」而 base.py 归为 L2；`:184` 未登记域 → `high_risk: False`）。
   → **同一实体在两条代码路径上得到相反结论（车库门尤甚：affordance 说高危、base 里没有它、未知域判 L2 但 affordance 判不高危）**。分级表必须唯一，且由 base 生成、affordance 只读引用。
4. **「假成功」是产品级缺陷而非日志问题**：`simulate(ok=True)`、`report["ok"]` 永真、CLI 退出码 0、`start_watch` 无条件 ok、canary 无观察期即通过、审批「用户已确认」被反向判定污染——审批链的每一步都在生产**不可信的证据**。人对这些证据的信任就是系统真实的安全边界。
5. **参数即真相的错觉**：`allow`、`targets`、`submitted_by`、`requires_confirm`、`entity_id`/`target` 全部来自被审计方/调用方。安全决策的输入必须由服务端推导，请求只能收窄不能扩权。
