## 一、AutoFlow 是什么（一句话）

agent 与 Home Assistant + Node-RED 之间的**唯一中介层网关**：独占凭证，agent 用 DSL/raw flow 描述场景，
网关负责 编译 → 静态 lint → vhass 孪生重放 → 人批准 → 部署+快照 → 可回滚。
~4.4 万行 Python，50+ 模块，219 个测试文件，NAS Docker 单容器部署。

**生态四件套定位**（ROADMAP 终版拍板，AF 应记住这是出资人自己的边界划定）：

| 项目 | 分工 |
|---|---|
| **AutoForge** | agent 创作工厂（现在的本项目） |
| **AutoFlow** | 人主导的安全部署 + 验证 + 回滚网关（明确不追 agent 主导创作） |
| doubao-butler | 连接执行 |
| memory-agent | 记忆创造力 |

## 二、值得照搬的（按 ROI 排序）

### 1. agent 三级身份制：normal / expert / developer（★直接回答上轮三问）

autoflow 用 `path + mode 双因子`做了完整的三级 agent 身份（ARCHITECTURE.md §5）：

| mode | 面板 | 能力 |
|---|---|---|
| `normal` | /mcp | 只走编译器路径（propose_dsl），上线须 WebUI 人批 |
| `expert` | /mcp-white | + 原生手写部署刀 + 仿真 |
| `developer` | /mcp-admin | + 运维刀（重启网关/自更新/任务池重置）+ 测试杠杆，**仅限网关自身运维身份** |

配套两条铁律（都是出资人自己定的）：
- **MCP 不暴露 approve——杜绝 agent 自己批准自己**；
- 部署刀只在 expert 面，运维刀只在 developer 面。

**对 AF 的意义**：上轮"开发者 agent / 管理面 / 运维面"三问，这就是设计现成的答案，而且是被
autoflow 两轮审计验证过的形态。AF 只需把 `af_deploy`（运维刀）这类新工具挂 developer 档，
AutoClaude 保持 normal 档，开发者 agent 身份制即落地——不需要发明新概念。

### 2. 受控自更新（方案 C）的三道护栏——AF 的 host_update.sh 正缺

autoflow `self_update.py` 的完整状态机（吸收过 2026-09-28 事故）：

1. **ref allowlist**：只认 `v*` tag 或 40 位 SHA，默认回退最新 v* tag，**绝不接受任意分支**；
2. **活树体检**：detached HEAD / dirty（已跟踪文件）即拦截——事故教训原文："NAS 活树曾长期
   scp 手工部署，`checkout -f` 会把 docker-compose 端口绑定等 NAS 特有配置整片冲掉，
   **拿升级按钮当格式化键**"；
3. **硬约束**：备份 tar → fetch（带镜像兜底）→ `checkout -f <pinned>` → py_compile →
   失败回滚**不重启**；**永不跑 `git clean -f` / `git reset --hard`**。

**对 AF 的意义**：AF 的 host_update.sh 现在是 `git reset --hard github/master` + 无 allowlist +
无 dirty 预检 + 本轮刚踩过"锁块自毁"（d865f26）。autoflow 的三道护栏每一条都对应 AF 的一个
现实风险，照搬成本一个下午。特别地：AF 用 reset --hard，宿主 repo 的 NAS 特有文件若被跟踪
就会重演"格式化键"事故。

### 3. 白箱 E2E 验证闭环（先验证后部署 + 自动回滚零残留）

`autoflow_run_e2e_trace`：真实部署到 staging → 合成触发点燃 → 逐节点 trace → 与期望路径
（节点 id 数组 / HA 状态后置断言）比对 → **自动回滚零残留**；verdict 三态（通过/断点/拦截）+
断点速查表 runbook 形态（agent 拿着表自己改，重验上限 3 轮）。

**对 AF 的意义**：AF 的 vhass 仿真 + verify_conf_grading.py harness 已在概念上等效，但缺
**期望路径/后置断言比对**与**逐节点 trace**两个形态。`af_simulate` 若补 expected_postconditions
断言参数，AF 的"试演"就从"能跑"升级为"验证了应当如此"——这正是 AF IR 已有的 expect 节点
语法（case11_expect）与运行期证据的接线点。

### 4. 分层披露与 token 预算（AF 的 MCP 面正在长向 45 工具的年纪）

autoflow 审计实测：/mcp 45 工具 69KB schema ≈ 2 万 token/轮，20 轮对话 40 万 token 纯工具目录；
get_skill 一次 56KB。反例正面都有：Pro 版用轻量 skill（~3K token）+ REST 实现 5-10 倍省 token。

**对 AF 的意义**：AF 现在 31 个 MCP 工具，方向一致。趁早立三条便宜的规矩：
- 新工具必须报 payload 实测（docstring 占比审计发现 64%）；
- 列表类出口禁止 limit=0 全量倾倒（AF 的 af_list_graphs 要查一眼）；
- docstring 写给 agent 的操作指引，不写给人看的论文。

### 5. 文档体例：过期事实剔除表 + 「工具清单不写死」纪律

autoflow 架构文档 §0.1 专设「合并时剔除的过期事实」表（旧说法 vs 现状，防旧知识复活）；
工具清单**明文不写进文档**（"把清单抄进文档必然过期——这正是两份旧架构文档都失准的原因"），
用 `autoflow_whoami` 实时返回身份+能力+可调工具。

**对 AF 的意义**：AF 的台账/发布钉体系是同族强化版（行号钉、形状钉），但"过期事实剔除表"
这个体例值得抄进 AF 的台账文档——本轮进程模型清单手工段行号位移就是一次小型复发。

### 6. 测试纪律：离线全套硬门槛 + live 测试全部离线化

autoflow 219 个测试文件，run_tests.py 单命令，离线全套是**硬门槛**（任一失败不进冒烟），
原 6 个 live 测试全部改造成 FakeNR/FakeHA 桩 + 本地 vhass + 进程内 TestClient。

**对 AF 的意义**：AF 已同向（FakeHA、虚拟时钟、verify harness）。差距在 AF 全量单测要
35-55 分钟且出现过 4 个"测试运行期间改码"的假红——AF 需要一个能快速全跑的分层
（快圈=门禁+发布钉，慢圈=全量），autoflow 的 smoke/live 分层是现成参考。

### 7. 经验数据管道与竞技场三回路（远期资产，记录在案）

- experience → error_knowledge → 智能推荐的单向管道；**失败回执附历史同类错误**（knowledge_feedback）；
- 竞技场三回路：失败回执带经验库、种子态健康检查（B20 纪律代码化）、排行榜效率系数
  （node_count ≤6 满分 ≥12 触底——**惩罚臃肿**）；
- examiner 校准回路（被拒题目 few-shot 注入自校准）。

**对 AF 的意义**：AF 的 experience.json/insight_proposals 已有雏形但没闭环。"失败时先查同类
历史错误再返回"是单点小改动、agent 体验提升明显，值得排期。竞技场本身**暂缓**（见远离清单）。

### 8. RBAC 声明式权限矩阵 + fail-closed 默认

三角色（viewer<admin<owner）+ `PERM_RULES` 按 (methods, path_prefix, role) 登记、最长前缀优先；
**未登记路径 GET=viewer、其余一律 admin**；owner 专属只有三处（用户管理、self-update、update-check）。

**对 AF 的意义**：AF 现在只有 scope（read/write/live）没有路径级矩阵——问题册 gap #6
（DELETE /api/automations、watch stop/start 不设防）的根治方案就是它。照搬矩阵形状，
把写路径逐一登记，未登记写路径默认拒绝。

## 三、要远离的（autoflow 用真实代价换来的反例）

### 1. 多 agent 三方外包协作（FFL）——两天成立两天解散

2026-09-06 成立（PM+前端+后端+测试+审查员五角色、主仓库/dev 仓库双仓 PR 流、结构化工单），
2026-09-08 即解散，回归单 agent 主导。工单模板再精致也没撑住。

**结论**：AF 的「出资人指挥 + 单 agent 主导 + DCD 裁定制」是对的，**不要再做多 agent 团队
协作**，除非出现真需求。autoflow 的工单/协作目录现在全是废墟留档。

### 2. 「修了 A 的后果没修 A」——结构性根因不修，修五次表面后果

autoflow 审计点名的模式：实例级锁修了读后写竞态（后果），没修"每次工具调用 new Gateway"
（根因），于是速率熔断形同虚设、缓存全被架空、埋点数据本身是错的（而 v3.0 删工具决策还要
靠这份错数据）。审计原话："这是『修了 A 的后果、没修 A』第 4 次"。

**AF 同族案例**：gap #9 长码一次性（v2.5 无差别 consume）、配对令牌 24h（BUG-19 无差别 TTL）——
同一根因都是"审计修复把一种凭据的语义套到另一种凭据上"，本轮已各修一次。
**要立的规矩**：修审计发现前先问「根因是哪个共享语义/共享生命周期」，分类修，不打补丁雨。

### 3. 静默失效面

135 处 `except: pass`（编译/部署/闸门关键路径在列）+ env 前缀双轨（`AUTOFLLOW_` 拼写错误的
25 个变量 vs 正确拼写 13 个，用户按正确拼写设置**静默不生效**）+ fail-open 名不副实
（WHITEBOX_REQUIRE_E2E 声称强制验证，基建故障时仍放行）。

**结论**：AF 已有对应纪律（verify harness 的"缺项不许读成绿"、问题册 #4 吞错），保持；
再进一步：把 except:pass 计数门禁化（autoflow 审计建议的 CI 静态规则，实现便宜）。

### 4. 进程自毁类能力 + 两套更新机制并存

`restart_gateway` 用 `os._exit(1)` 绕过一切清理；nr_client 在 **import 时自改写自身源码**
（权威源可被 env/注册表劫持 = 供应链雷）；self_update 与 nr_client 自更新两套机制并存、
行为互不可预测。

**结论**：AF 的 host_update.sh 自毁（本轮）是同族事故。铁律照收：**自更新是单点，改它必须
宿主 bash -n + 标记冒烟；进程内禁止自改写代码文件；一个系统只允许一套更新机制**。

### 5. 仓库卫生崩溃

工作树里：2 份完整 src 快照目录 + 1 份 src 内 .bak + skills tar 备份 + **tmp/ 249 个文件**
（一次性 check_*.py、测试日志、中间产物）+ data 持久卷长在源码树里 + .env 在工作树。

**结论**：AF 的 worktree + 发布线纪律好得多，保持。警惕点：AF 的 examples/ir 混入 /data
（本轮已修）本质是同一类病——**运行时状态与代码树必须物理分离**。

### 6. 复杂度爬坡的天花板形态

staging(NR1990+vhass)/prod(NR1880真实) 双 NR 实例 + 固定方向 sync.py + deploy_tokens
Tab 级授权（配额/限流/节点阈值转人工）+ ACP 对等 agent 协议 + Link API http/link_out 双类 +
黑盒/白盒/双面/三 mode……护栏与面板层层叠加，gateway.py 被压成 10250 行 God Object，
审计判"不做大重构"成为永久债。

**结论**：AF 不需要双 NR 实例（vhass 仿真 + 真实 watch 够用）、不需要 Tab 级授权码矩阵
（分型 long/short 够用）。**每加一层护栏/面板前，先问它防的那口锅 AF 会不会真背**。

### 7. 竞技场（v2.0 主线）——探索性资产，暂缓移植

设计漂亮（分区/自由命题/三层判重/创造力评分/排行榜），但 AF 主线（四档流程）尚未收口，
问题册还有 #3-#8/#10 待办。冻结在 autoflow 仓里留档，等 AF 的经验闭环（第 7 条照搬项）
落地后再评估是否借"效率系数惩罚臃肿"这一个点。

## 四、对照定位：AF 已经继承了什么、超越了什么、还缺什么

### 已继承（无需动作）
闸门思想、agent 不直连设备、人审唯一批准口（MCP 无 approve）、vhass 孪生、
经验收集、原子写+备份、fail-closed 默认、诚实铁律（AF 的"缺项不许读成绿"同源）。

### AF 已超越（不用回头学）
- **意图通道**：af_draft 中文意图 2 调用直达（autoflow 的 DSL 仍要 agent 学语法）；
- **分档引擎**：影子/金丝雀/conf 置信度（autoflow 只有通过/不通过二态）；
- **发布纪律**：发布钉 + 台账门禁 + 版本里程碑（autoflow 无 check_* 门禁层）；
- **单入口更彻底**：autoflow 的黑盒/白盒遗留挣扎了一整版才收成单入口，AF 从第一天就是单入口。

### 还缺的（= 建议排期，全部来自 autoflow 现成设计）
1. agent 三级身份制（developer 档 = 上轮运维面问题的答案）；
2. host_update.sh 三护栏（allowlist / 活树体检 / 禁 reset --hard）；
3. RBAC 路径矩阵（根治 gap #6 的旁门端点不设防）；
4. af_simulate 的期望后置断言（把试演从"能跑"升到"验证了应当如此"）；
5. 失败回执附同类历史错误（经验闭环第一刀）。

## 五、决策建议

1. **立即（一个下午）**：host_update.sh 照搬方案 C 三护栏。本轮刚踩的自毁 + reset --hard
   风险正好用 autoflow 的事故铁律封死。
2. **下轮主题**：「开发者 agent 身份制」——移植 normal/expert/developer 三档 + 运维刀面。
   这是出资人自己在 autoflow 里设计并验证过的形态，直接同名移植，配合上轮建议的
   af_deploy 工具即闭环。
3. **顺手小件**：except:pass 计数门禁；MCP 出口预算纪律；台账文档加"过期事实剔除表"体例。
4. **明确不做**：多 agent 团队协作（FFL 教训）、双 NR staging 实例、Tab 级授权码矩阵、
   竞技场移植、gateway 式巨石重构允许但立体积预算（af_service.py 超过 5000 行即触发拆分讨论）。
5. **autoflow 处置**：v2.3.12 冻结留档不再演进（ROADMAP v4.0.0 交接协议不作）；
   它的价值是**活的参照物**——AF 每次做身份/更新/权限/护栏决策时，先查 autoflow
   对应模块的注释里的事故复盘，那里面积累了 AF 还没踩过的坑。
