## 1. P1 稳定性 / 功能性缺陷

### N-P1-1 af_undo._climate 仅需切换模式时生成非法调用

af_undo.py 的 _climate()：

    def _climate(snapshot, entity_id):
        attrs = _attrs(snapshot)
        temp = attrs.get(temperature)
        hvac = attrs.get(hvac_mode)
        if temp is None and hvac is None:
            return None
        params = {entity_id: entity_id}
        if temp is not None:
            params[temperature] = float(temp)
        if hvac is not None:
            params[hvac_mode] = str(hvac)
        return (climate.set_temperature, params)   # <-- 问题点

- 当快照只有 hvac_mode 而没有 temperature（如刚开机、或该机型只回模式不回报设定温度）时，会生成
  climate.set_temperature({entity_id, hvac_mode}) —— 缺少 temperature 必填参数。
- HA 侧会以参数校验失败 / 400 拒绝，而 restore_call 的 try/except 只包住映射推导，不包住适配器语义；
  最终表现为「撤销执行了但设备没恢复」，且不产生明确错误。
- 该分支与文件头声明的 fail-closed 原则相悖：无法完整表达时应返回 None（跳过并告警），而非发一个注定失败的调用。

**修复建议**：拆分动作 —— 有 temperature 调 climate.set_temperature；仅 hvac_mode 调 climate.set_hvac_mode；
两者都有时先 set_hvac_mode 再 set_temperature。

### N-P1-2 af_undo.UndoStore.undo() 的 ok 与 restored 失真

    for entity_id, snapshot in entities.items():
        call = restore_call(entity_id, snapshot)
        if call is None:
            skipped.append(entity_id); continue
        action, params = call
        try:
            res = adapter.call(action, params)
        except Exception as exc:
            results.append(CallResult.fail(...)); continue
        results.append(res)
        restored.append(entity_id)        # <-- 无条件追加
    return {ok: True, restored: restored, skipped: skipped, results: results}

两个问题：

1. **restored 无条件追加**：即使 res 是失败的 CallResult（返回码非成功），该实体仍计入 restored。
   下游（CLI 输出、诚实报告、决策 E 的验收）若以 restored 判定「已恢复」，会系统性高估回滚成功率。
2. **顶层 ok 恒为 True**：只有 risk_domain_requires_confirm 分支才返回 ok:False。
   全量回滚失败时仍返回 ok:True。与既有报告 P1-17（版本审计 report[ok] 永不为 False）属同型缺陷
   但位于不同模块，需单独修。

**修复建议**：按 res.ok 区分 restored / failed；顶层 ok = not failed；把 failed 明细单列。

### N-P1-3 af_flock.FileLock 在进程内多线程下不互斥

    def try_acquire(self) -> bool:
        if self._fd is not None:
            return True   # 已持有（同一线程内重入语义：宽松处理）

- _fd 是**实例属性**。若同一 FileLock 实例被多个线程共享（或模块级单例被并发调用），
  第一个线程拿锁成功后 _fd 非空，其余线程调用 try_acquire() 直接 return True ——
  全部线程都认为自己持锁，临界区完全敞开。
- 文件头明确说「所有写方都经本模块拿锁才能互斥」，但注释里的『同一线程内重入』并未做线程判定，
  实际语义是「同实例内任意线程重入」，与设计意图不符。
- 该锁是 GraphStore / PersistStore / watch 协调的唯一互斥手段（advisory），
  这个洞等于这些写路径在单进程多线程场景下没有保护。
- 另外：POSIX 的 flock 以打开文件描述为单位，同进程重复 open 会自我阻塞；
  现在的 _fd 复用写法把这一层保护也绕过了。

**修复建议**：用 threading.get_ident() 记录持有线程，仅同线程可重入；跨线程一律走阻塞/非阻塞竞争。
或改为每线程独立 FileLock 实例 + 进程内 threading.Lock 兜底。

## 2. P2 功能性 / 正确性缺陷

### N-P2-1 仿真与生产的 local_now() 语义不一致

af_time.py：

    class SystemTimeSource:
        def now(self):      return datetime.now(timezone.utc)   # UTC
        def local_now(self): return datetime.now(self._tz)      # +08:00

    @dataclass
    class VirtualTimeSource:
        def now(self):       return self._current
        def local_now(self): return self._current               # <-- 与 now() 同一个值

- VirtualTimeSource 的 start 默认值是 tzinfo=timezone.utc，因此 _current 是 UTC。
- 但 local_now() 原样返回 _current（UTC），而生产环境 local_now() 返回 +08:00 本地时间。
- 后果：任何依赖 matches_at(clock.local_now(), at) 的 time 触发（at: 07:00），
  在仿真中比的是 UTC 小时，在生产中比的是本地小时 —— 相差 8 小时。
- 这意味着 B3-AF-04（naive UTC 与 aware local 混算）的回归测试在仿真里可能『通过』而生产错，
  属于典型的「测试给出假绿灯」。

**修复建议**：VirtualTimeSource 增加独立 _tz，local_now() 返回 self._current.astimezone(self._tz)；
并在 assert_clock_consistent 中新增断言：仿真不得把 UTC 当本地。

### N-P2-2 matches_at 缺输入校验

    def matches_at(local_now, at):
        ensure_aware(local_now, who=matches_at.local_now)
        hh, mm = at.split(:)                 # 三段式 07:00:00 → ValueError 解包失败
        return (local_now.hour, local_now.minute) == (int(hh), int(mm))

- at=7:0、at=07:00:00、at=07-00、at= 均会以 ValueError 直接穿透到 tick 主循环。
  既有报告已记录「tick 异常不崩线程」的加固，但这类可预防的解析异常不该依赖外层兜底。
- 未校验 0<=hh<=23 / 0<=mm<=59，at=25:99 永远不匹配且不报错，属于静默失败。

**修复建议**：解析时用正则严格匹配两位 HH:MM 并做范围校验，非法直接抛带上下文的 ValueError，
由 IR 静态闸在建图期拦下（而非运行时）。

### N-P2-3 af_undo 违反时间源契约

af_time.py 文件头强制约定：业务代码禁止直接调用 time.time() / datetime.now()。

但 af_undo.py：

    self._records[deploy_id] = {ts: time.time(), ...}     # record()
    now = time.time()                                     # purge_expired()

- 直接使用 time.time()，未走 TimeSource。
- 后果：在 vhass 时间旅行仿真中，undo 的时间窗判定（window_s 是否过期）不受虚拟时钟驱动，
  测不出「跨时钟跳变后时间窗行为」，也无法在仿真里稳定构造过期/未过期场景。
- 同型问题在 af_undo.py 内共 2 处（record / purge_expired）。
- 注：af_service.py:1708 也有 datetime.now()，但那是报告 generated_at 元数据，
  影响面小于此处的时间窗判定，可一并纳入观察。

**修复建议**：UndoStore.__init__ 注入 clock，record 用 clock.now()，purge_expired 同理。

### N-P2-4 TickSupervisor.run_forever() 默认等待器会抛异常

    _wait = wait or (
        lambda s: (stop.wait(s) if stop else (_ for _ in ()).throw(RuntimeError(no wait)))
    )

- 调用 run_forever(body)（既不传 stop 也不传 wait）时，第一次循环就会走到 throw(RuntimeError)。
- 而签名把 stop/wait 都设成可选，调用方很容易写成 run_forever(self._tick)。
- 这是个必然抛出的默认路径，不是边界情况。

**修复建议**：stop=None and wait=None 时默认 time.sleep；或把两参数中至少一个设为必填。

### N-P2-5 TickHealth 计数在锁外修改

run_once()：

    with self._lock:
        if self._health.halted: return ...
    t0 = ...
    self._health.ticks_total += 1        # <-- 锁外
    try: body()
    except Exception as exc:
        return self._on_failure(...)     # <-- 计数在 _on_failure 里改，也在锁外
    dur = ...
    self._on_success(dur)                # <-- 同上

- 只有「读 halted」在锁内，ticks_total / ok_total / fail_total / consecutive_* 全部在锁外自增。
- health_state() / snapshot() 在另一线程读取时会看到撕裂的计数（如 ok+failed != ticks_total），
  外部 watchdog 据此判断 degraded/stalled 可能误判。
- 与 N-P1-3 同属「并发原语用错」一族，但影响的是可观测性而非互斥，单独列。

**修复建议**：计数更新统一进锁；或改用不可变快照 + threading.Lock 保护 TickHealth。

### N-P2-6 af_watch 冲突计数统计错误

    total_conflict += len(evs) if any(e.kind == KIND_CONFLICT for e in evs) else 0

- 语义应为「冲突事件总数」，实际是「只要该自动化出现过一次冲突，就把它的全部事件数都累加」。
- 例：某自动化 100 条 shadow + 1 条 conflict → total_conflict += 101，真实应为 1。
- 该值直接进入诚实报告 verified_in_prod 的 summary，属于面向用户的数字造假（结果错误，非恶意）。

**修复建议**：total_conflict += sum(1 for e in evs if e.kind == KIND_CONFLICT)。

### N-P2-7 WatchAggregator 内存只增不减

    self._events: list[WatchEvent] = []
    self._by_auto: dict[str, list[WatchEvent]] = {}

    def ingest(self, ev):
        with self._lock:
            self._events.append(ev)                    # 永不裁剪
            self._by_auto.setdefault(ev.automation_id, []).append(ev)

- 两条容器都只 append、永不清理，且是模块级单例（_default），随进程常驻。
- 生产态验证事件是高频的（shadow 每次 compare 都落点），长跑必然内存单调增长。
- 这与 hy4 报告 P1-1「三处容器只增不减」是同型问题但在本模块独立存在（该报告未覆盖 af_watch），
  需按模块分别修复，不能指望一处修复覆盖。
- verified_in_prod() 每次调用都全量遍历 self._by_auto，随时间推移成本线性上升。

**修复建议**：改为环形缓冲 / 按 automation 保留最近 N 条；或只维护计数器（Counter）+ last_at，
不保留原始事件列表。

## 3. P3 次要问题

### N-P3-1 af_watch.reset() 无锁替换单例

    def reset() -> None:
        global _default
        _default = WatchAggregator()

- 在并发 record_* 期间调用 reset()，会丢失正在写入的事件（写入旧实例，读新实例）。
- 生产路径通常不会调 reset()（注释说测试隔离用），但若被 WebUI「清空统计」复用则会踩坑。

**修复建议**：reset() 改为在锁内 clear() 现有实例，或明确标注「仅测试、进程启动前调用」。

---

### N-P3-2 af_metrics.MetricsAggregator.snapshot() 的 O(N×M) 遍历

    for auto in self.runtime.graph:
        for ev in audit:
            if ev.automation_id != aid: continue
            ...

- 外层遍历全部自动化，内层全量遍历审计列表，复杂度 O(自动化数 × 审计条数)。
- 指标快照通常作为周期任务运行；随审计累积会逐步变慢（与低功耗机叠加时更明显）。
- 与既有报告的「快照全量拉取」不是同一处（那是 HA 状态快照），此处是审计聚合。

**修复建议**：先对 audit 做一次 groupby(automation_id)，再按自动化取用，降为 O(N+M)。

## 5. 建议整改顺序

1. **N-P1-3（FileLock 进程内失效）** —— 影响所有写路径的互斥假设，优先级最高，改动小、收益大。
2. **N-P1-1 / N-P1-2（undo 非法调用 + 失真上报）** —— 回滚是本项目「安全能力」的对外承诺，失真会直接误导用户。
3. **N-P2-1（local_now 仿真语义）** —— 会让 time 触发的测试给出假绿灯，属于「静默错误」，越晚修代价越大。
4. **N-P2-4（run_forever 必抛）** —— 一行修复。
5. **N-P2-7 / N-P2-6（内存增长 + 冲突计数）** —— 前者是长跑稳定性，后者是数字正确性，一起修（同文件）。
6. **N-P2-3 / N-P2-5 / N-P3-1 / N-P3-2** —— 契约一致性与性能，可排入下一迭代。
