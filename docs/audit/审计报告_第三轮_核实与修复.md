## 二、逐条核实（对照当前代码）

### 缺陷 1 · `min`/`max` 混类型抛 `TypeError` 绕过 soft-fail —— **成立**

`src/autoforge/af_ir/expr.py` 的 `_min_max()` 把未经校验的值直接交给 `min`/`max`。
`min(sensor_temp, 20) > 10`，实体状态为 HA 原生字符串时，实测：

```
修复前（把 _min_max 还原成旧实现后重跑）
  state='21.5'        -> !!逃逸 TypeError
  state='on'          -> !!逃逸 TypeError
  state='unavailable' -> !!逃逸 TypeError

executor 的 if 分支捕获元组（inspect 真实源码取回，不是凭记忆）
  UnknownEntity, ExprError, KeyError, ValueError
  含 TypeError ? False
```

报告的三道防线判断（静态闸放行 → 求值抛非受控 TypeError → 捕获列表不含它 → `_soft_fail` 被跳过）
与实测一致。`af_scanner.py:601` 只捕 `ExprError`（编译期），`af_executor.py:433` 是唯一的运行期捕获点。

### Hardening note · `floor`/`ceil` 的 `inf`/`nan` —— **成立，但报告的"不构成实际失效路径"理由不成立**

报告写："`_as_num` 拒绝所有字符串（含 `'inf'`/`'nan'`），所以 `inf`/`nan` 无法经 HA 状态字符串进入"。
实测**相反**：`type: numeric` 的强制转换走 `float(value)`，而 `float('inf')` / `float('nan')` /
`float('1e400')` 三者全部成功。

```
声明 type=numeric 的实体，状态字符串 =
  'inf'   -> !!逃逸 ValueError    '1e400' -> !!逃逸 ValueError
  'nan'   -> !!逃逸 ValueError    'on'/'':'' -> 受控 ExprError（这两条才是报告设想的形态）
```

即：只要 IR 里显式声明了 `type: numeric`（推荐写法），非有限数字照样进得来。
`ValueError` 恰好在捕获列表内，所以 soft-fail 仍生效、不构成绕过，但**可达性判断要纠正**；
且原异常消息 `cannot convert float NaN to integer` 对 `inf` 也照抄，与真因无关，排障误导。

### 报告**漏报**的一条 —— `round(x, n)` 的 `n` 非有限数字 → `OverflowError`

`_fn_round` 对位数做 `int(_as_num(args[1]))`：`round(21.5, float('inf'))` 抛
`OverflowError: cannot convert float infinity to integer`。
**`OverflowError` 不在 executor 捕获列表里** —— 这是与缺陷 1 同性质（真绕过 soft-fail）的第二条路径，
报告只记了 `floor`/`ceil` 的 `ValueError`（在列表内，不绕过），没有覆盖到这条。

### 全量扫描结果（23 个白名单函数 × 参数位 × 20 种值形态 + 6 个比较算子 × 类型矩阵）

| | 修复前实测 | 修复后实测 |
|---|---|---|
| 非受控异常逃逸 (函数×异常类) | **6**：`min`/`max` TypeError、`floor`/`ceil` ValueError、`round` OverflowError+ValueError | **0** |
| 比较算子跨类型矩阵逃逸 | 0（`_compare` 的类型守卫已在 P1-15 落地） | 0 |

报告"其余 21 个白名单函数边界 fuzz 全部受控"这一条**核实成立**；
`MAX_EXPR_DEPTH=32` / `MAX_EXPR_NODES=256` / `eval`·`exec`·`__import__` 全拒也复核过。

## 三、本次落地改动（按报告"方案 A 根治"，不动捕获列表）

`src/autoforge/af_ir/expr.py`：

1. **`_min_max()` 先统一类型再取值**：全数字或全字符串才交给 `min`/`max`；混排、含 `bool`、含
   `None`/list 一律 `ExprError`，消息里点名"实体状态请声明 type=numeric"（让作者能自己修）。
   同型字符串的合法用法（字典序）保持可用，没有为了收紧而误杀。
2. **`_as_num()` 加 `math.isfinite()` 校验**：一次覆盖 `abs`/`floor`/`ceil`/`round`/`clamp`/`sum`/`avg`，
   `OverflowError` 与"NaN→int"这两类裸异常从源头消失，错误消息说明是"非有限数字"。
3. **`_coerce()` 两条数值路径同样拒绝非有限数字**：
   - `type: numeric`：`float('inf')` 转换成功也不再放行；
   - 未声明类型：状态已是原生 `float('nan')` 时不再让 `nan > 10` **静默判假**。
     这比抛错更危险（条件永不成立且不留任何痕迹），属同族缺陷，一并收口。
4. **模块 docstring 写明不变量**：求值层只允许抛 `ExprError` / `UnknownEntity`，新增函数必须自带
   类型与有限性校验，不要把裸 Python 异常留给调用方兜。

**没有**把 `TypeError` 加进 `af_executor.py:433` 的捕获列表（报告方案 B）。理由：那是把"真正的编程错误"
也咽进 soft-fail，且加完之后这条缺陷仍然是"不可报告红"的状态。替代做法是把不变量做成能报红的门禁 ——
`tests/unit/test_expr_escape_closed.py` 里 900+ 条参数化用例扫遍每个函数的每个参数位，
外加端到端反例锁（下节）。捕获元组一旦再次缺类，测试直接变红。

`src/autoforge/af_conflict.py` / `af_service.py`（顺带，同属"时钟口径"族，非本轮报告缺陷）：
`af_conflict.SystemTimeSource.now()` 原返回 naive datetime，改为 aware UTC；
`af_service.py` 报告 `generated_at` 原来裸调 `datetime.now()`（违反 `af_time.py:4` 自定的"业务代码禁止直接
调用 `datetime.now()`"），改走 `SystemTimeSource().local_now()`。并新增 AST 级扫描测试钉住"仓内不得出现裸
naive 墙钟调用"（按 AST 取真实调用点，文档字符串里提及规则本身不误报）。

## 六、部署提示

本轮改动不改 IR schema、不改任何对外契约字段，`ir.schema.json` 无需动（铁律 #1 不适用）。
行为差异只有一条：**过去静默放行或静默判假的表达式，现在会走 soft-fail 并留 `ENTITY_DRIFT` 审计**。
升舱后如果 `ENTITY_DRIFT` 数量上升，那是真实脏数据第一次被看见，不是新引入的故障 ——
逐条检查对应实体的 IR 是否该补 `type: numeric`。

同一份改动也适用于 `--persist-dir` 真机跑：真机才有 `unavailable` / 字符串状态，正是缺陷 1 的原生土壤。

**未覆盖声明**（沿报告口径，诚实保留）：报告 19 个单元里 14 个 `out_of_scope` —— HTTP 鉴权、MCP 授权码、
`af_store` 原子写、`af_persist` 租约与崩溃恢复、`af_bus` 去重熔断、`af_orchestrator`、`af_executor` canary、
CLI 输入、`af_catalog`、`af_evo`、`af_service` 会话、`af_scanner`、`af_vhass` 仿真。
本轮只把"表达式求值 + 时间"这一面的**异常收口**做完，不等于这些面已审。
