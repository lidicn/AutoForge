## 2. 授权码体系现状（含 DCD 裁定的形状，⛔ 违反即红）

**要码的路径**（全部走同一把 `svc._auth_code_check`，⛔ 另造第二套）：

| 路径 | 入口 |
|---|---|
| MCP `af_save`（部署路径 A） | 码在 consume 后转 `reviewer="auth_code:xx***"` |
| MCP `af_live_run` / REST `/api/live/run` | `auth_code` 参数 |
| MCP `af_enable_by_tag(true)` / REST `/api/graphs/enable` | 同上 |
| **undo**：REST `/api/undo/{id}`、CLI `forge undo --auth-code` | **DCD 裁定 §〇.1**：undo 是真机回放不是"关"——授权码语义是"真机动一次就要一次码"，**与方向无关**（我"与禁用同向"的类比被裁定推翻，这条判例要记住） |
| **start_watch 手动入口**：REST `/api/watch/start`（dry_live=false）、CLI `forge watch --auth-code` | DCD 裁定 §2.2 |
| CLI `forge run --live --auth-code` | AF-603 |

**免码的路径**（每条免码都有裁定依据，⛔ 顺手收紧）：

| 路径 | 依据 |
|---|---|
| **禁用** enable(false)/disable | R4-3（出资人 2026-10-29）：关安全阀不该被钥匙挡住 |
| **serve 自动恢复** | 走 `_restore_watch_after_restart`（独立内部函数，**⛔ 参数区分——参数会漏传**；docstring 声明"⛔ 扩权仅限 serve 启动序列"）。进程重启无人可给码，加码=假武装 |
| `_ensure_watcher` / `approve_pending` 的起监听 | 走 `_start_watch_impl`（免闸实现体）——凭据语义分别在 enable 码闸与 reviewer，**码只收一次** |
| dry-live（`--dry-live`/`dry_live=true`） | 不动设备（do 只记意图），与 live_preflight 的 confirm 检查同口径 |
| 四因合一文案 | 无效码一律「授权码无效（不存在/已消耗/已过期/已锁定之一）」——⛔ 外传具体哪一因（那是授权码枚举面）。pattern 拒绝也用同形文案（AF-402） |
