## 一、口径（先说清本门判什么、不判什么）

1. **判据的射程是 git 索引（入库面），不是磁盘。** 与 `scripts/af_face.py`、`check_process_model.py`、
   `check_oneshot_layout.py` 同一口径：要防的是「进了库的东西被推上发布线之后 NAS 取到哪一条线」，不是「手边草稿」。
   由此得到两条**必须写明的代价**：
   - 在途未 `git add` 的改动**不进判据**（本门绿不等于工作树没有另一套字面——见 §五 的两面读数）；
   - **未跟踪**的同名载体（§四 那几份）**既不算交付也不算违规**，只作观察行输出。依裁甲「未进任何提交 ⇒ 不算交付」。
2. **本门判"同源"，不判"该用哪条线"。** 发布线取哪一条是出资人／DCD 的口径（权威依据见 §二 的裁定引行；
   本仓内三处工具读数并不完全一致，逐条留原文在同一节），
   本门只把 §二 那一格当唯一真源：**登记表说 `main`，则所有载体必须是 `main`**；改口径只改 §二 那一行＋各载体，
   门跟着现读走，⛔ 不在门里写死第二份分支名。
3. **本地开发分支 ≠ 发布线，这一格刻意不判。** 本仓提交在 `master` 上落、推送走 `master:main`，
   所以「本地线 = master」是登记事实而不是违规；判据 C 只吃 §二「发布线（远端）」那一格。
4. **`body.branch` 的取值域 2026-10-23 起收口为「master | v*tag」**（此前 = 无，请求体可传任意字符串、
   宿主脚本 `git fetch --force github "$REF"` 照单全收）。v1.13.0 双侧同规则校验：API 面
   `af_api.py` `api_system_update` `re.fullmatch(r"master|v\d+\.\d+\.\d+", branch)` 不符 400；
   宿主面 `scripts/host_update.sh` 读 marker 后 `case "$REF" in master|v[0-9]*.[0-9]*.[0-9]*)`
   不符拒绝并写 result。SHA 不进白名单——fetch-by-SHA 依赖服务端 `allowReachableSHA1InWant`
   配置，回滚走 v* tag（发版惯例：release commit push 后 `git tag vX.Y.Z && git push origin vX.Y.Z`）。
