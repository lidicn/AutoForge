## 2. 当前 IR 设计（emit 解耦，4 自动化）

实体：吊灯 `switch.lumi_cn_lumi_158d000239c546_aq1_on_p_3_1`，挂灯 `light.yeelink_cn_555003624_lamp22_s_2`。

| 自动化 | 模式 | 触发 | 动作 |
|---|---|---|---|
| `ceiling_state_changed` | single | 吊灯 on/off（state） | **emit** `ceiling_on` / `ceiling_off`（不写实体） |
| `lamp_follow_ceiling` | queued | 事件 `ceiling_on/off` | `light.turn_on/off`（写挂灯） |
| `lamp_state_changed` | single | 挂灯 on/off（state） | **emit** `lamp_on` / `lamp_off`（不写实体） |
| `ceiling_follow_lamp` | queued | 事件 `lamp_on/off` | `switch.turn_on/off`（写吊灯） |

- **为何必须 emit 解耦**：`af_scanner.py:549` 的 `ENTITY_DEP_CYCLE` 规则——"A 写 X 且 B 由 X 触发 → 成环"。直接 `A↔B` 双向写必然成环，被 `forge build` 安全闸判为 ERROR 并**拒绝启动 runtime**（见 §3 关键发现 2）。emit 让"实体依赖"与"事件依赖"分别无环。
- **HA 无死循环保证**：对"已是该状态"的实体调用 `turn_on`/`turn_off` 不产生 `state_changed`，故不会无限互触。
- **`queued` 跟随侧**：连按时 FIFO 排队、末态正确，不丢事件（优于 `single` 会拒重叠实例）。

## 3. 已定位的关键根因 / 发现

1. **401 是测试容器网络问题，非 IR bug**。`autoforge-test` 容器用默认 **bridge 网络**访问 `http://192.168.2.200:8123` 会拿不到 HA 鉴权（401）；加 **`--network host`** 后真机下发全部成功（`diag3.sh` 证明：`post: ceil=off lamp=on`）。**生产 `autoforge-api` 若用 bridge 网络也会有同样 401，需确认其网络可达 HA。**
2. **`ENTITY_DEP_CYCLE` 会拦停整个 `forge watch`**。直接双向 `do`（A 写 B、B 写 A）触发该 ERROR → `forge build` 安全闸拒绝启动 runtime → SSE 事件零处理、什么都不会动。`verify_final.sh` 的 `docker run` 已加 `--network host` + `--ha-token`，且当前 IR 是 emit 版（无环），故闸通过、runtime 正常启动（[A] 才得以 PASS）。
3. **自定义事件已豁免熔断/节流**（`af_bus.py` L167-175）。否则 emit→follow 联动风暴会自伤熔断，在用户连按时阻断合法同步。
4. **`not_is_on`/`not_is_off` 已就绪**：对方实体状态读取抖动（mesh 延迟/设备未响应）时不再软失败跳过动作——但当前 IR 已不读对方状态，故该能力为通用兜底。
