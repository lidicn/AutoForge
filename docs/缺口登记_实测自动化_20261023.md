# 实测自动化缺口登记 · 2026-10-23（配对恢复后首轮端到端实测）

**实测环境**：生产 NAS / v1.13.3 / 配对令牌 subject=claude-code（expert 档 read+write+live）
**场景**：房间温度 ≥28 → 开空调制冷 24℃（领普温湿度传感器 `sensor.linp_cn_blt_3_1peaoqbmd0o00_ks2bb_temperature_p_2_1001` → `climate.lumi_v3_db16_air_conditioner`）
**路线**：HTTP `/mcp` 桥（af_whoami → af_draft → af_apply → pending → WebUI 审批）

实测结果：流程主干走通（draft/build/simulate/save/入队全绿，pending 队列正常），但抓到 **5 个新缺口 + 2 个配对复盘缺口**。按严重度排序：

---

## G1（阻断级）意图通道生成的 IR 边类型错配——图跑不通且仿真谎报 ok

- **现象**：`af_draft` 带 `if` 条件生成的图，if 节点出边是 `yes`/`no`（af_draft.py:288 `edge_kind = "yes" if (i == 0 and if_entry ...)`），但执行器 `_execute` 对 if 求值 True 返回 `{then}`（af_executor.py:601 `return {"then"} if value else {"no", "default"}`）。`then ∉ {yes}` → `pick_edge` 无匹配 → 实例**静默终止**（`_terminate`）。
- **后果**：**每一条意图通道带 if 条件的自动化，条件为 True 时都到不了动作节点**。仿真回执却报 `ok: True`（simulate 的 ok 恒 True，失败只看 expect——而 expect 常缺）→「跑过了」实为空跑，正是 autoflow 复盘里「静默失效」的死法。
- **复现**：本地 PYTHONPATH 复现，`{"if": {"gte": {"var": "...", "const": 28}}}` 生成 IR → simulate → trace 停在 `i2 enter`，无 d3。
- **修法方向**：`_build_edges` 的首条 do 边 `yes` → `then`（与执行器口径对齐）；或 `_execute` if 分支返回 `{yes}`。二选一，全仓 grep 确认无其他消费者后改。**同批补判据腿测试：意图带 if → simulate trace 必须含动作节点。**

## G2（阻断级）意图侧 `var` 直填 entity_id → 表达式命名空间崩

- **现象**：`_resolve_expr`（af_draft.py:470）判定 `if "." in var_name` 就原样透传——agent 按目录返回的 entity_id 填 `var`（如 `sensor.linp_xxx`），生成 `{"var": "sensor.linp_xxx"}`，求值时 `split_namespace`（af_state.py:153）抛 `未知命名空间 'sensor'`。
- **后果**：IF_NODE_EXEC_ERROR（warning 日志），走 `_soft_fail`；真实意图（用真 entity_id 写条件）在意图通道**必然失败**。
- **修法方向**：`_resolve_expr` 改为 `_ENTITY_ID_RE.match(var_name)` 命中 → 包 `entity.` 前缀（现在判的是 `var_name.startswith("entity.") or "." in var_name`——后者把合法 entity_id 误判成已带命名空间）。一元谓词同形（af_draft.py:452 同样的判断）。

## G3（阻断级）`ha.set_state` 动作在 FakeHA 未建模——set_state 类意图仿真永远验不了

- **现象**：`set_state` 是 af_draft 意图侧一等动作（action_map 兜底 + 显式 `set_state` 写法都落 `("ha", "set_state")`），但 FakeHA `SERVICE_STATE` 表（af_vhass/fake.py:136）**没有 `(*, set_state)` 条目** → `call()` 判 unmodeled → `service_effect` 返回 None → 状态不落、只登记 unmodeled。
- **后果**：诚实报告把动作标黄（non_simulable「仿真底座未建模动作」），final_states 恒 off——「开空调」意图在仿真里**物理不可能验证**。生产 watch 走 HA adapter 是否支持 set_state 需另核（HA 侧无 set_state 服务，生产多半也是坏动作名）。
- **修法方向**：双层——① af_draft 的 action_map 给 `set_state`/「开空调」映射到 `climate.set_hvac_mode`+`climate.set_temperature`（DYNAMIC_SERVICES 已建模）；② FakeHA 补 `set_state` 动态建模（新状态= params.state）。**优先 ①，语义正确**。

## G4（高）`af_draft`/`_t_apply` 不传 catalog——resolved 全占位、agent 被迫手工填 entity_id

- **现象**：`_t_draft`（af_mcp.py:380）调 `draft_intent(args["intent"])` **不传 catalog**；服务进程明明有设备目录（GraphStore 挂着 catalog）。`_resolve_entity(catalog=None)` → 全部 `?占位` → build 报 ENTITY_NOT_FOUND → agent 被迫自己解析 entity_id 再直填（然后踩 G2）。
- **后果**：意图通道的「中文设备名自动解析」在生产 MCP 面**形同虚设**；`af_remember_entity` 沉淀的别名对 draft 也无效。
- **修法方向**：`_t_draft` 里 `_catalog(store)`（af_service 现成）传给 `draft_intent`；`_t_apply` 同查。判据腿：带别名+意图中文名 → resolved 无 `?`。

## G5（高）`af_apply` 意图字符串/未知形状直接 crash 成 INTERNAL——不是 DraftError

- **现象**：`when`/`do` 传字符串（agent 极自然的写法「房间温度大于等于28」）→ `_resolve_trigger` 的 `when.get("type")` 对 str 抛 AttributeError → dispatch 兜 ADM_ERR_INTERNAL「工具执行出错」。v1.13.3 刚给 af_draft 补的失败归因/遥测（`_telemetry`）**完全没接到**（af_draft 只捕 DraftError）。
- **修法方向**：`draft_intent` 入口对 `when`/`do`/`if` 做 isinstance 校验，str/非法形状抛 `DraftError(E_INVALID_WHEN/E_INVALID_DO, fix={shape_hint})`——复用既有 fix 回灌管道。

## G6（中）`af_apply` 丢失调用主体——审批面板显示「af_apply」而非 agent 身份

- **现象**：af_apply.py:200 `submit_pending(..., submitted_by="af_apply")` 硬编码；`_t_apply` 不在 `_TOOLS_WITH_CONTEXT`、`apply()` 不接 subject。审批人在 WebUI pending 队列看到提交人是「af_apply」，无从判断是哪个 agent 递的。
- **连带**：P0-13 自批闸的比较对象也成了 "af_apply"——多个 agent 的 apply 全落同一名字，自批检查失去主体区分度。
- **修法方向**：`_t_apply` 进 `_TOOLS_WITH_CONTEXT`，`apply(..., subject=current.subject)` 透传到 `submit_pending(authenticated_subject=...)`。

## G7（低）staging ref 进程级内存——跨进程/重启即失效，agent 长流程易踩 E_REF_NOT_FOUND

- **现象**：`StagingStore` 是进程级 dict（af_draft.py:53-74），`docker exec` 每起新进程读不到 API 进程的 staging；API 重启 ref 全失效。本次实测 `docker exec` 内 get_staged 直接 E_REF_NOT_FOUND。
- **定性**：单进程内 draft→apply 闭环无恙（HTTP /mcp 同进程）；跨进程消费（agent 分步操作、崩溃恢复）会踩。可登记不修（文档约定 draft→apply 须同会话），或落盘 staging。

## G8（中）过期剔除零告警
`_purge_expired_locked`/`_persist_issued` 把令牌从 issued_tokens.json 剔除时零日志零事件。本次配对丢失（BUG-19 TTL 误伤 24h 到点静默清库）用户面板清空才后知后觉。修法：剔除时按 label/subject 打 warning 日志（含条数与主体名，不含令牌本体）。

## G9（低）AF_ACCESS_TOKENS 空值与 AUTOFORGE_TOKENS 共存

## G10（2026-10-24 书房场景验证时发现）：canary duration 挂起会静默掐断动作链

**现场**：意图带 `do_list` 两个 climate 动作、两个节点都写 `canary: {"duration": 300}`。
仿真里第一个节点确认后正常下发（AC=cool），随后实例进 canary 观察挂起；300s 到期走
`resume("on_timeout")` → `pick_edge(d3, {on_timeout, default})`——af_draft 给中间 do 节点
**只生成 then 出边**，匹配不上 ⇒ `_terminate` ⇒ 实例 done。第二个动作（set_temperature 26）
**永远不执行**，而 AC 已经显示 cool ⇒ 「空调开了但温度没设」的静默半完成态。

**病灶定位**：`af_executor.py:711` 挂起时 kind=`canary_observe`，但 `af_scheduler.py:126` 的
分发表只认 `emit`/`wait`，其余（含 canary_observe）落 `timeout()` → `resume("on_timeout")`；
`af_draft.py` 的 `_build_edges` 不给 do 节点写 on_timeout/default 边。

**修法方向（未实施，留待批次）**：
① af_draft 给带 canary+duration 的 do 节点补 `on_timeout → 下一个节点` 边（语义：观察期满无漂移
就继续链条）；或 ② executor 的 canary 恢复分支在漂移检查通过后走 `then` 而不是让 pick_edge 扑空。

**【2026-10-24 PM 裁决：走 ①，不走 ②】**（判据腿 `tests/unit/test_canary_duration_chain_break.py` 3 条已由 db 席位落成）

- **② 被否的理由**：`af_executor.py:332` 的 `pick_edge(node.id, {kind, "default"})` 位于 `resume()`
  这一**共用唤醒路径**里——ask 应答、pending_confirm 授权、canary 观察恢复三条都走它。在这里加
  `then` 兜底会改变全部三种唤醒的选边语义，且 `af_executor.py` 在进程模型清单（生命周期/原语站点）
  与信任边界清单里都有在册锚点，改动面远超"修一条边"。
- **① 的两个现读约束**（实施时必须处理）：
  1. `pass_id` 在 `_build_edges` 的 do_list 循环**之后**才生成 ⇒ 循环内无法引用它；ask 节点的既有
     先例是 `on_timeout → pass`（[af_draft.py:387](src/autoforge/af_draft.py#L387)），但 G10 的语义
     **不能**指向 pass——那等于把后续 do 节点全部跳过，链还是断的，只是断得"干净"。
  2. 因此做法是：生成下一个节点时**回填**上一条 `on_timeout → 下一个 nid` 边（仅当该 do 节点带
     `canary.duration` 时）。`af_draft.py` 零台账锚点，`af_draft.py:337` 的 `edge_kind` 分派已建立
     "出边类型按上游种类决定"的既有模式，`on_timeout` 是同模式延伸而非新机制。
- **修好后 db 的腿 1 会红**——那是信号：按 [test_canary_duration_chain_break.py](tests/unit/test_canary_duration_chain_break.py)
  腿 1 的失败消息改成正向断言（"d4 现在跑了"）。**⛔ 不许为了让测试绿而放宽断言。**
- **配套的判据腿改进**（书房场景当时的判据只验终态 AC=cool，漏判"后半段没跑"）：断言第二个节点的
  适配器调用真的发生，而不只是终态正确。
① 更贴 IR 边纪律（图里读得出走向），② 改动面小但把走向藏进执行器。

**本轮规避**：canary 只写 `{"auto_rollback": true}`（无 duration）⇒ 立即漂移检查、不挂起、链条照常。
climate 两个动态服务的 expected_state 为 None ⇒ 记 unmodeled（诚实分层，非假绿）。

**判据腿建议**：`do_list` 两节点 + 首节点 canary duration，断言的不是「AC=cool」而是
「第二个节点的 adapter call 真的发生了」（否则正好漏掉这个病灶）。
