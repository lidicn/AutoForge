## 11 条欠账逐条定性

### A 组：真缺陷应修（1 条 ERROR + 2 条 WARN，同一函数族）

| 站点 | 违规 | 定性 |
|---|---|---|
| af_api.py:1209 `api_system_version` | except-pass-broad | **真缺陷**：读 `.update_available.json` 失败被吞——「commit/tag/branch 读不出」静默报空串，ok=True 照常返回 |
| af_api.py:1211 同函数 | **swallow-and-claim-ok (ERROR)** | 同上，谎报成功：预览文件损坏时 UI 显示空 commit 而非报错 |

修法：except Exception 改具名 `(OSError, ValueError)` + 落 `logger.warning` 具名码
`UPDATE_PREVIEW_READ_FAILED`（可观测性门 §三 同批登记）。**这与 G8（过期剔除零告警）
是同一族「静默失效」——正应该修。**

### B 组：fake-ok-const——**误报为主，逐条核对**

这些端点的 `ok=True` 是「读取成功」的回执（读端点/回执面），不是「业务校验通过」
的断言。AST 规则把所有字面量 ok=True 都算违规，本仓对回执面的既有口径是登记进基线：

| 站点 | 引入批次 | 核对 |
|---|---|---|
| af_api.py:1106 `api_auth_has_admin` | 4a20464（10-21） | `has_admin` 布尔已实际回读，ok=True 只是信封——同形端点 `api_agents_list` 在基线里 |
| af_api.py:1129 `api_auth_register` | 4a20464 | register 返回 ok=True 前已 raise 400/409，字面量是安全后缀 |
| af_api.py:1218/1225 `api_system_update_check` | 779b9ed（预检） | 读端点回执，同 `api_system_update_status` |
| af_api.py:1261 `api_system_update` | v1.13.0 | `submit_update_request` 的 ok 分支回执——失败路径已显式 409/400（本批 v1.13.0 亲手写的错误路径） |
| af_api.py:1279 `api_system_update_status` | 同上 | 读端点回执 |
| af_mcp.py:502 `_t_deploy` | bd0a1b5（v1.13.3） | 同 HTTP 面 submit_update_request 回执——失败已 `ok=False + code` |
| af_mcp.py:535 `_t_deploy_status` | bd0a1b5 | 读端点回执 |
| af_service.py:2848 `stop_watch` | 敲打 P0 批 | 孤儿锁回收成功回执，`reason=orphan_recovered` 是实际判定结果 |

**处置建议**：8 条按既有口径追加进 `.gates-baseline.txt`（`--update-baseline`），
同时棘轮 `.gates-tally.txt` 97 → 105（登记说明：1.13.x 批次发版时未同步基线，
本笔集中收账）；**A 组 1 条 ERROR 修真缺陷不进基线**。修完 A 组后总数 100 条，
上限抬到 104（B 组 8 条 + 既有 97 - A 组修掉的 2 → 实算为准）。
