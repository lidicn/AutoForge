# 进程模型清单（生命周期站点 × 同步原语 × 共享状态归属）

> 本文件由 `scripts/check_process_model.py` 把「谁拉起进程、谁负责收、哪份状态归谁」变成**可 diff 的资产**。
> 起因是第六轮审计 ARCH-06：报告说这仓「三套互不相识的同步原语 ＋ 无 supervisor ＋ 无优雅停机」，
> 且「没有等价物锁住『共享可变状态的归属』」。前两句有格已经过期（见 §五），第三句成立——本清单就是那把锁。
>
> §二 是自动段（跑 `--write` 重生成，勿手改）；§三／§四 是手工登记；§五／§六 是复测与递裁记录。

## 一、口径与射程

1. **射程**：`src/autoforge/*.py`（整棵，只 `ast.parse` 不导入）。`scripts/` 与 `tests/` 里的子进程
   **不在射程内**——它们是一次性工具与判据自身，不是常驻运行时的组成部分；这一格明写而不是静默排除。
2. **生命周期站点**＝代码里能改变进程/信号/退出时序的十四个调用形状（`KINDS`，见脚本 §头）。
   多数今天为 0，那是**基线**不是噪音：任何一枚从 0 变 1，都必须先在 §三 认领"谁负责收"。
3. **同步原语**＝`threading.Lock/RLock/Semaphore/Condition`（进程内）＋ `FileLock`（跨进程）。
   本清单只登记**站点**（在哪、绑到什么名、包围在哪个函数），不判"该不该加锁"——后者是运行时语义。
4. **模块级共享名**＝被某个函数用 `global` 改写过的模块级名字。这是"哪份状态归谁"的最小机械口径：
   它比"所有模块级可变绑定"（现读 85 枚／33 个文件）窄得多，因为后者一大半是常量表（`_TIER_RANK` 那类），
   改不动也就无所谓归属；真正会被运行期改写的是 `global` 那一小撮。
5. **门判的是对账，不是缺陷**。§二 里"函数体内没有任何 `with`"的那些行不等于 bug（写一次的懒加载单例
   在 GIL 下引用赋值是原子的），它等于"这一份状态的归属被人核看过、写在这里"。

## 三、生命周期站点登记（默认拒绝，新站点不登记即红）

字段含义：**拉起**＝这一行真的做了什么；**收**＝谁负责把它收干净；**收不到会怎样**＝那一步没发生时的现状；
**依据**＝仓内一份指得到的记录；**认领**＝`AF`／`待裁`／`DCD` 三种形状之一。

- `src/autoforge/af_service.py:2716` · kind=subprocess.Popen · 拉起：`start_watch` 用 `sys.executable -m autoforge watch …` 起一个独立 watcher 进程，`start_new_session=True` 使它脱离 serve 的会话 · 收：`stop_watch` 先按 sidecar 的 `owner`（`{hostname}-{pid}-{uuid8}`）核验 PID，核验过才 `os.kill(pid,15)`；核验不过一律不发信号 · 收不到会怎样：serve 被强杀或机器重启时没人发那枚 SIGTERM，孤儿 watcher 继续持有协调锁并按档位真下发动作；今天只有下一次 `start_watch` 的抢占或人工 `stop_watch` 能发现它，进程级 supervisor 缺位（见 §六 问 1） · 依据：docs/ADM联动执行记录-AF.md · 认领：待裁：拉起面已核验并落码（§二之九十三／九十四），收的兜底归谁等 DCD
- `src/autoforge/af_service.py:2604` · kind=os.kill · 拉起：`stop_watch` 对已核验身份的 PID 发 SIGTERM（POSIX 上是优雅收尾，Windows 上 `os.kill` 等价强杀、没有优雅语义） · 收：信号发出后按 `_WATCH_PROBE_DELAYS_S` 退避表探协调锁是否真空闲，空闲才回收诊断件；探不到就回 `exit_unconfirmed` 并刻意不升 SIGKILL · 收不到会怎样：对方可能正在写持久化，强杀会把在途写入丢在半截——所以"确认不了就不杀"是设计而不是遗漏（审计 BUG-06／07 的口径） · 依据：docs/ADM联动执行记录-AF.md · 认领：AF：语义已在 §二之九十三 落码并钉判据
- `src/autoforge/af_service.py:2682` · kind=os.kill · 拉起：`start_watch` 拉起新 watcher 之前先收上一条：PID 与 sidecar 身份两边对得上才发 SIGTERM · 收不到会怎样：核验不过就不杀，新建的 watcher 自己去抢协调锁，抢不到会如实回 `coord_lock_held_by_other`——比"照着盘上的数字动刀"安全，因为那个数字随时可能是别人的 · 收：下一次 `stop_watch` 或人工介入 · 依据：docs/ADM联动执行记录-AF.md · 认领：AF：同上
- `src/autoforge/af_cli.py:631` · kind=signal.signal · 拉起：`watch` 命令在进主循环前装 SIGTERM 处理器，处理器只做两件事——置 `stop` 事件、抛 `KeyboardInterrupt`，从而**接回既有的 `finally`**（`stop.set()` → `ticker.join()` → `coord.release()`） · 收：那个 `finally` 自己；判据 D/E 现读复核形状还在 · 收不到会怎样：审计 BUG-06 的旧实现收到 SIGTERM 直接死在半路，协调锁靠内核释放但 sidecar／PID 诊断件留旧值，下一条 watch 会把它们读成自己的现场；Windows 上这一腿不会真投递（`os.kill` 在那边是强杀），所以优雅语义只在 POSIX 侧生效 · 依据：docs/ADM联动执行记录-AF.md · 认领：AF：§二之九十三 落码，本门判据 E 钉形状
