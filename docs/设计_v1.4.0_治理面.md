## 2 调研抄法摘要（§2.6 / §2.7 / §2.9）

### §2.6 待批队列（PendingOp）+ 执行/批准物理分离
- autoflow：`ConfirmationGate.request(op)` 落 `pending/<op_id>.json`；`approve/reject` **只在 WebUI**，reviewer 硬编码 `"human"`，**MCP 面不注册 approve**；per-agent 熔断默认 20；`PendingOp` 把「执行 payload」与「展示 summary/blast_radius」**同包落盘**，批准时回放 payload。
- AutoForge 现状：`ask` 是运行时挂起（不是部署前审批）；`live_run` 三重闸是「立即执行」；`af_api.py` 无 `/pending`。
- **抄法**：新增 pending 队列（store + 3 端点 + `forge pending` 命令）。`ask` 与 `PendingOp` **不合并**（语义不同：一个管运行时问用户，一个管部署前人审批）。

### §2.7 device_guard 的 Tier 分级 + 取最严
- autoflow：JSON 注册表 `{match:{type:entity|domain|area,value}, tier:0|1}`；命中多条**取最严**（0 最严）；Tier-0=必须人审，Tier-1=放行但审计。
- AutoForge 现状：`entity_acl: Mapping[str,str]`（`rw`/`r`/`-`），`af_scanner.py:187` 静态 dict，无热更新/无分级/无 area 维度。
- **抄法**：ACL 抽成可热更新注册表 + tier 语义 + 取最严合并。
- ⚠️ 据实提示：autoflow 的 `DeviceGuardStore.match_tier()` **全仓无调用点**（拦截接线未落地）。我们抄「注册表与判定引擎解耦」的分层思路，判定引擎要在 AutoForge 的 `StaticScanner._check_entities` 真正接线。

### §2.9 凭据热重载（connection_revision 代数）
- autoflow：WebUI 改 HA 令牌 → 原子落盘（`mkstemp`+`os.replace`+`chmod 600`）+ `bump_revision(cfg)` 全局 +1；各连接层 client property 比对代数，变了丢弃缓存 client 重建；`describe()` 对 secret **只回掩码+长度（连末 4 位都不露）**。
- AutoForge 现状：`AUTOFORGE_HA_TOKEN` / `AUTOFORGE_API_TOKEN` **只从环境变量读**，改令牌必须重启进程——对 `forge watch`（常驻，`af_cli.py:300` → `af_live.run_watch`）是实际痛点。
- **抄法**：凭据落 `{root}/credentials.json`（gitignore + `0600`）+ 代数热重载，配合 `af_flock.FileLock` 做原子写。

## 4 行为增量（逐交付点）

### 4.1 待批队列（PendingOp）

**数据模型（`af_pending.PendingOp`）**
```python
@dataclass
class PendingOp:
    op_id: str            # uuid4 hex
    tool: str             # 如 "af_save"
    payload: dict         # 执行所需原参：{name, ir, note, tags, expect_version}
    summary: str          # 展示用一句话（来自工具自身 render）
    blast_radius: dict    # 复用 v1.3.0 blast_radius（实体数/跨自动化依赖）
    submitted_by: str     # agent / subject（MCP current 或 API token subject）
    submitted_at: str     # isoformat
```

**`PendingStore(root)`**
- `submit(op, max_per_agent=20)`：先查该 `submitted_by` 的待批数，≥ 上限返回拒绝（`PendingLimitExceeded`）；否则原子写 `{root}/pending/<op_id>.json`（`.tmp`+`os.replace`，复用 `FileLock` 保护目录）。
- `list(agent=None)` → 按时间排序的待批清单（审批视图：含 summary/blast_radius，不含完整 payload 明文）。
- `approve(op_id, reviewer="human")`：读 json → 调 `af_service.save_ir(**payload)` 回放落盘 → 成功删 pending 文件 + 写 audit。
- `reject(op_id, reason)`：删 pending 文件 + 写 audit（`PENDING_REJECTED`）。

**`_t_save` 改造（`af_mcp.py`）**
- 当前：`_t_save(store, args)` 直接 `store.save(...)` 落盘（注册于 `TOOLS` L442）。
- 改后：`_t_save` 不再直接落盘，而是构造 `PendingOp`（计算 `blast_radius` 复用 v1.3.0 函数），`PendingStore.submit` 落盘，返回 `{ok, pending: op_id, summary, blast_radius, note:"待审批"}`。
- **MCP 面绝不注册 `af_approve`/`af_reject`**（autoflow 铁律：agent 不能自批）。

**HTTP 端点（`af_api.py`，approve 仅在服务层）**
- `POST /api/pending/list`：列出待批（reviewer 侧读，需 `write` scope；原型无 token 时全公开）。
- `POST /api/pending/approve {op_id}`：调用 `af_service.approve`，reviewer 取自令牌 `subject`（硬编码 `"human"` 兜底）。
- `POST /api/pending/reject {op_id, reason}`。

**CLI（`af_cli.py`）**
- `forge pending list` / `forge pending approve <op_id>` / `forge pending reject <op_id> [--reason]`。

```python
    def __init__(self, rules: list[GuardRule]): ...
    def match_tier(self, entity_id: str, catalog) -> int:
        # 命中多条取最严（min tier，0 最严）；未命中返回 1（默认放行）
```

**与现有 ACL 兼容映射**
- 现有 `entity_acl` 的 `rw`/`r` → tier 1（放行但审计）；`-` → tier 0（禁止=必须人审）。
- 新增 tier-0 规则（如 `area: 卧室` 锁所有写）即「必须人审」。
- `StaticScanner` 参数由 `entity_acl: Mapping[str,str]|None` 改为 `device_guard: DeviceGuardRegistry|None`（`af_scanner.py:187`）。
- `_check_entities`（`af_scanner.py:530-550`）改造：
  - 读检查：命中任何 tier-0 → `ENTITY_GUARD_TIER0`（error，必须人审）；
  - 写检查：命中任何 tier-0 → `ENTITY_GUARD_TIER0`；否则按 `rw`/`r` 放行（tier 1）。
- **热更新**：registry 从 `{root}/device_acl.json` 加载，改文件后下次 `scan()` 自动生效（无重启）；CLI 可加 `forge guard add/list`（可选，首版可仅 WebUI/手工 JSON）。

## 5 关键约束落实（逐项对照 ROADMAP §650）

1. `ask`（运行时挂起）与 `PendingOp`（部署前审批）**不合并** → 两套独立机制，互不影响。
2. **MCP 面绝不注册 approve/reject**（含管理面）→ `TOOLS` 列表只含 `af_save`（进 pending），无 `af_approve`/`af_reject`。
3. `PendingOp` 把「执行 payload」与「展示 summary/blast_radius」**同包落盘**，approve 回放 payload → 无二次渲染漂移。
4. 凭据热重载用**代数**（`connection_revision`）而非直接戳实例 → 同进程多 Runtime 自愈。
5. `describe` 只回掩码+长度（连末 4 位都不露），防 WebUI 截图/投屏泄露。

## 7 风险与开放问题

1. **`af_save` 调用场景界定**：`af_save` 是部署前归档写，应始终进 pending；运行时写设备走 `af_live_run`（live 三重闸，不进 pending）。需确认 `_t_save` 当前内部调用（`store.save` 或 `af_service`），approve 复用时将其抽为 `af_service.save_ir`。
2. **`blast_radius` 复用点**：v1.3.0 的 `blast_radius` 计算函数需导出（确认位于 `af_service`/`af_diff`），`af_save` 进 pending 时调用。
3. **`device_acl.json` 位置**：用户策略应可入库（不放 gitignore），与现有 `_load_json_mapping`（`af_cli.py:48`）加载的 ACL JSON 兼容迁移。
4. **凭据文件权限**：`0600` 在 Windows 无严格语义（`os.chmod` 尽力），文档注明 NAS/Linux 部署侧生效。
5. **per-agent 熔断计数桶**：无 `subject` 的原型模式（MCP 未鉴权）按单全局桶或放行？设计：无 subject 不熔断（原型期宽松），有 subject 才计 per-agent。
6. **`Runtime` 不持 HA client**：凭据热重载的接入点是 `HATransport`/`HAStateProvider` 构造处与 `run_watch`，无需改 `Runtime`（`af_runtime.py:38` 确认）。
